### D-12 — Q-5 (DM 목록 매물 컨텍스트) 구현 방식 · **차단 중**

**발견**: 감사 §4 Q-5 는 "필드는 이미 API 응답에 존재하니 프론트 렌더만 하면 된다"고 적었으나 **틀렸다.**
- `_listing_context()` 헬퍼(`backend/app/routers/dm.py:40`)는 **상세조회**(`dm.py:196`)와 **생성**(`dm.py:272`)에서만 호출된다.

즉 Q-5 는 "프론트 한 줄"이 아니라 **백엔드 선행 수정이 필요한 항목**이다.

### D-21 — Q-2 상한값 재검토 · **구현됐으나 감사 의도를 절반만 충족**

구현된 상한은 **1000억 VND**(≈USD 400만)이며 `price_vnd`(create·가격수정)와 `PriceOfferProposeRequest.amount` 세 곳에 일관 적용됐다(`schemas.py:205,285,944`).

**감독 검증 결과 — 이 값은 자릿수 오입력을 못 막는다:**
- 워커가 실DB 를 조회한 결과 **실제 최고가 매물은 1억 VND**.
- 그런데 **100억 VND(10B) "소파"**(카테고리 40, 제목 "커커커")가 이미 DB 에 존재한다 — 감사가 지목한 바로 그 오입력 유형인데, **1000억 상한을 그대로 통과한다.**
- 즉 지금 상한은 **오버플로 가드**이지 오입력 가드가 아니다.

| 선택지 | 내용 | 판단 |
|---|---|---|
| (a) 현행 유지(1000억) | 극단값만 차단 | 오입력 방어는 D-3 카테고리 밴드(W2)에 온전히 미룸 |
| (b) **200억 VND 로 조임** ← **권고** | 베트남 최고가 승용차(롤스로이스급 300~600억 VND 는 중고거래 대상 아님)를 넘지 않는 선 | 100억 소파는 여전히 통과 — 하지만 전역 상한으로 잡을 수 있는 한계다 |
| (c) 카테고리별 상한 | 카테고리마다 다른 상한 | **이게 D-3(b) 규칙 밴드 그 자체다** — W2 범위. 지금 하면 중복 구현 |

**권고 (b) + 진짜 해결은 W2.** 근거: 전역 단일 상한으로 "소파 100억"을 잡는 건 원리적으로 불가능하다(같은 컬럼에 오토바이와 소파가 함께 산다). 전역 상한은 극단값만 막고, 카테고리 밴드(D-3·D-4)가 본래의 해답이다. **Q-2 를 "완료"로 적고 넘어가면 오입력 방어가 됐다고 오해하게 되므로 이 문서에 남긴다.**

### D-23 — 인앱 알림 문구의 다국어화 · **신규 발견 (2026-08-17 21시, 구현 중 발견)**

**발견**: 사용자에게 가는 인앱 알림의 **본문이 한국어로 하드코딩**돼 있다. 예: `admin_api/listings.py:245` — `body=f"'{listing.title}' 매물이 운영정책에 따라 처리되었습니다. 사유: {reason}"`. 매물 모더레이션 통보는 **베트남 판매자에게** 가는 알림이다.

알림 문구용 로케일 인프라가 코드베이스에 **아예 없다**(프론트 `translation.json` 은 화면 텍스트용이고 서버 알림 본문은 별개). 오늘 추가한 신고 결과 통보(`a20d8f9`)도 기존 패턴을 따라 한국어 하드코딩으로 들어갔다 — 워커의 판단(새 i18n 계층 신설은 과설계)은 카파시 #2·#3 에 부합하지만, **제품 관점에서는 결함이 누적된 것**이다.

**왜 중요한가**: 정본 §1 은 파일럿 문턱을 "폐루프 완결"로 정의했다. 신고자에게 알림이 **가더라도 읽을 수 없으면** 폐루프가 아니다. 서비스 대상은 호치민 현지 사용자이고 주 언어는 베트남어다.

| 선택지 | 내용 | 규모 |
|---|---|---|
| (a) **알림 본문 다국어화 계층 신설** ← **권고** | 서버측 알림 템플릿을 언어별로 분리하고 사용자 언어 설정(있으면)에 따라 선택. 기존 알림 문구 전수를 vi/en/ko 3종으로 | M~L — 기존 알림 종류 전수 조사 필요 |
| (b) 베트남어 단일 전환 | 알림 본문을 vi 로 교체(다국어 아님) | S~M — 가장 빠름. 한국인 운영자·테스터가 알림을 못 읽게 됨 |
| (c) 현행 유지 | 한국어 유지 | 0 — **파일럿 문턱을 충족하지 못한다고 판단** |

**권고 (a), 단 규모 확정 전에 전수 조사 필요.** 사용자 언어 설정 필드가 DB 에 있는지부터 확인해야 한다(미확인). (b)는 임시방편이지만 파일럿이 베트남 사용자 대상이라면 (c)보다 낫다.
**정본 반영**: 이 항목은 §5 리스트에 없다 — 파일럿 문턱 항목으로 추가할지 대표 판단 필요.

#### D-23a — 알림 생성 시점의 **언어 판정 방식** · **D-23 구현을 차단 중** (2026-08-17 22시 조사)

**조사 결과 (구현 워커, 코드 근거 확인)**: 알림 생성 시점에 수신자의 언어를 알 방법이 **없다.**
- `User`(`models.py:125`)·`NotificationSettings`(`notifications.py:88-109`) 에 언어·로케일 컬럼 **없음**(설정은 on/off 토글뿐). `source_lang`(`models.py:1034`)은 매물 번역 캐시용이며 유저 속성이 아니다.
- 프론트 언어는 `localStorage`(`frontend/src/lib/i18n.ts:8-17`, 키 `sr-lang`)에만 있고, 공통 fetch 래퍼(`api/client.ts:132-137`)가 **언어를 실어 보내지 않는다.**
- `?lang=` 쿼리 패턴(`market.py:195` 등)은 **읽기 시점에 호출자가 넘기는 번역 요청 파라미터**이고 서버에 영속되지 않는다. `notifications.py` 목록 엔드포인트엔 이 파라미터조차 없다.
- 결정적으로 모더레이션·신고결과 알림은 **관리자 요청 중에 생성**된다 — 그 시점에 수신자의 HTTP 요청이 존재하지 않는다.

| 선택지 | 내용 | 규모 | 리스크 |
|---|---|---|---|
| (1) **`preferred_lang` 컬럼 신설 + 사람이 쓴 템플릿** ← **권고** | 프론트 `changeLang()` 이 서버에도 저장. 알림 템플릿은 vi/en/ko 를 사람이 작성 | 마이그레이션 1(`init/183`) + 저장 API 1 + 프론트 훅 1 | 생성 시점 언어로 문구가 **고정** — 이후 언어를 바꾸면 과거 알림은 옛 언어로 남음 |
| (2) 디바이스 로케일을 로그인/세션갱신 시 저장 | 컬럼은 (1)과 동일 | (1)과 유사 | 앱 내 선택 언어가 아니라 디바이스 로케일 — 부정확(베트남 사용자가 폰을 영어로 쓰는 경우) |
| (3) vi 고정(다국어화 보류) | 알림을 vi 단일 | 0 | ko/en 사용자 배려 불가. 한국인 운영자·테스터가 알림 확인 불가 |
| (4) vi 로 저장 + 읽기 시점 기존 번역 캐시로 즉석 번역 | `lookup_lang_batch`/`translate_to` 재사용, 마이그레이션 없음 | 라우터 1 + 프론트 1 | **기계 번역** — 아래 사유로 비권장 |

**권고 (1)**. 알림 종류는 수십 개 수준으로 유한해 사람이 한 번 써두면 기계 번역보다 정확하고 운영 비용이 0이다. (1)의 "언어 고정" 트레이드오프는 알림이 대부분 즉시 소비되는 성격이므로 수용 가능하다고 판단한다.

### D-15 — 매물 카드에 `view_count`(조회수) 노출 여부

`view_count` 는 API 응답에 이미 있으나 카드에 렌더되지 않는다.

### D-16 — 검색 화면에 거리순 정렬 추가 여부

현재 마켓 피드는 거리순을 쓸 수 있으나 검색 화면에는 없다.

**권고: 추가.** 근거: 지역 기반 서비스 권역 개념이 이미 코드에 있고 위치 데이터가 실재하므로 **새 재료가 필요 없다**. 중고거래에서 거리는 키워드 다음으로 강한 필터다. 구현 규모 소규모.
**주의**: 검색 화면 파일들(`MarketSearch*`)은 **다른 세션이 지금 수정 중**이다. 그 세션 커밋 후 착수.

### D-17 — "최근 본 매물" 도입 여부

**권고: 지금은 안 함.** 근거: 저장할 테이블·API 가 없어 **신규 스키마부터 필요**하다. 업계 통용 패턴이긴 하나 우리 사용자층에 유효한지 검증할 계측이 없다. D-18 계측이 붙은 뒤 데이터를 보고 판단하는 것이 순서다.
