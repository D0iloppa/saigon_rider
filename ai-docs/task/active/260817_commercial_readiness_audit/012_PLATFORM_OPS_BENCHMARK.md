## §0. 한 장 요약

**벤치마크 기준**: 마켓플레이스 어드민 실무 문헌의 공통 합의는 <cite index="25-1">어드민 패널이 다섯 도메인 — 사용자 관리, 거래 감독, 콘텐츠·매물 모더레이션, 재무 통제, 플랫폼 설정 — 을 커버해야 하며, 역할 기반 접근 제어(RBAC)는 타협 불가 항목이고, 단일 슈퍼유저 계정은 어떤 규모에서든 보안·컴플라이언스 실패</cite>라는 것이다. 또한 국내 실무 문헌이 지적하는 전형적 실패 패턴은 <cite index="37-1">처음엔 간단한 CRUD였던 어드민이 어느 순간 배포 없이는 컬럼 하나도 못 바꾸는 '운영 병목'이 되는 것</cite>이다.

**5도메인 대조 판정**:

| 벤치마크 도메인 | SGR 현재 (010 근거) | 판정 |
|---|---|---|
| ① 콘텐츠·매물 모더레이션 | 신고·제재·모더레이션 도구 완성(W4), 011까지 반영 시 triage·우선순위·경보 | ✅ 충분 (010+011이 커버) |
| ② 거래 감독 | GMV 집계 + 스냅샷 보강(#4), 퍼널(#5) | ✅ 충분 |
| ③ 사용자·판매자 관리 | 제재·이력·티켓 완성 | ✅ 충분 |
| ④ 재무 통제 | 광고 결제 수동(P-6c), C2C 정산 없음 | ✅ 010 판단 유지 — 광고주 소수 구간 수동이 정답, 법무(§7-2) 선행 |
| ⑤ **플랫폼 설정 + 운영자 계정 체계** | **결손 2건 + 확인 필요 3건** | ⚠️ **본 문서의 본론** |

**핵심 발견 — 010이 스스로 담고 있던 증거**: 010 §5 완료 목록의 "Q-1 금칙어 매물 확대 `f8fa9ff`"는 **금칙어 변경이 코드 커밋·배포를 요구한다는 사실의 직접 증거**다. 금칙어는 임계값 상수(010이 하드코딩을 옳게 선택한 것)와 성격이 다른 **운영 데이터**이며, 파일럿에서 신종 사기 키워드가 등장할 때마다 배포를 기다리는 구조는 T&S 대응 속도를 개발 파이프라인에 묶는다.

**보강: 구현 3건(#22~#24) + 확인 필요 3건.** 풀 RBAC·외부 CMS·리모트컨피그 시스템은 [P2] 명시 기각(§4) — 010의 과설계 금지 원칙을 운영 계층에도 동일 적용한다.

## §1. 판정 원칙 — "상수"와 "운영 데이터"의 구분선

010 §3-1은 임계값을 백엔드 상수로 박았고 §4는 런타임 킬스위치 화면을 기각했다. **이 판단은 유지한다.** 다만 하드코딩 대상의 구분 기준을 명문화한다:

| 유형 | 정의 | 변경 주체·빈도 | 처리 |
|---|---|---|---|
| **튜닝 상수** | 가중치·임계값·계수 (신고 우선순위 가중, 랭킹 감쇠 반감기, trust_penalty) | 개발자 판단, 데이터 실측 후 드물게 | **하드코딩 유지** (010 방침) — 변경 자체가 코드 리뷰 대상이어야 함 |
| **운영 데이터** | 금칙어, 공지, 배너, 카테고리, 정책 문구 | **비개발 운영자**, 파일럿 중 수시 | **DB + 어드민 CRUD** — 배포 의존은 운영 병목 |

판단: 010의 실수는 이 둘을 구분하지 않고 "하드코딩 = 절제"로 일괄 처리한 것이다. 금칙어(Q-1)가 커밋으로 관리되는 현실이 그 결과다.

## §2. 결손 판정 — 도메인 ⑤ 상세

### 2-1. [P0] 금칙어의 배포 종속 — T&S 대응 속도 결함

**사실**: Q-1 커밋 `f8fa9ff` (010 §5 완료 목록) — 금칙어 확대가 코드 변경이었다.

**판단**: 파일럿의 목적이 "배우는 것"(010 §1-1)이라면, 배울 것 중 하나가 **현지 사기 어휘**다. 베트남어 사기 수법 키워드(선입금 유도 변형 표현 등)는 파일럿 중 실시간으로 발견될 것이고, 발견 → 차단 사이의 지연이 배포 주기와 같아서는 안 된다. 규모 S~M: `banned_keyword(keyword_norm, scope, active, created_by, created_at)` 테이블 + 어드민 CRUD + 등록 검증 로직의 소스 전환. 011 #17의 정규화 함수를 재사용하면 무성조 변형(금칙어 우회 입력)도 잡힌다 — **011과의 시너지가 공짜로 생긴다.**

### 2-2. [P0] 운영자 커뮤니케이션 채널 부재 (추정) — 공지·배너

**사실**: 010 §1-1 운영자 문턱, §2-4 어디에도 공지사항·인앱 배너 관리가 없다. 사용자 대상 일괄 커뮤니케이션 수단은 FCM 발송뿐으로 추정 — **확인 필요** (게시형 공지 존재 여부).

**판단**: 파일럿 운영 시나리오를 구체적으로 상상하면 필요성이 자명하다: ① 점검 공지 ② "이번 주말 ○○구 안전거래 이벤트" ③ 사기 주의보 ④ 정책 변경 고지(§7-2 법무 통보 의무와 직결). 이 넷 중 하나라도 코드 배포로 처리하는 순간 §1의 병목 패턴이다. 최소 구현: `announcement(title, body, type, starts_at, ends_at, active)` + 홈 상단 배너 1슬롯 + 공지 목록 화면. 규모 M. **풀 CMS 아님** — 리치에디터·예약발행·세그먼트 타겟팅 전부 비범위(§4).

### 2-3. [P1] 어드민 계정 개별화 + 행위자 감사 — RBAC의 최소 형태

**사실**: 감사 증적은 존재(002_trust B-8 인용, 010 §3-2). 그러나 어드민 **계정 체계**(개별 계정 vs 공유 계정, 역할 구분)는 010 전체에서 언급 없음 — **확인 필요**.

**판단**: 벤치마크의 "RBAC 타협 불가"를 현 규모(운영 0.5~2인)에 그대로 적용하면 과설계다. 그러나 **하한선**은 있다: ① 운영자 1인당 계정 1개(공유 금지) ② 모든 변경성 어드민 액션에 `actor_id` 기록 ③ 역할 2종만(SUPER: 설정·계정 관리 / OPS: 신고·검수·공지). 근거: 010 §3-2가 설계한 신고 폐루프의 감사 증적은 "누가 판정했는가"가 기록돼야 분쟁(이의제기 #2) 시 의미가 있고, 인력이 2인이 되는 순간(010 §7-3이 이미 예정) 소급 도입은 기존 로그 전체의 행위자 불명을 남긴다. 지금 계정이 이미 개별화돼 있다면 이 항목은 역할 플래그 추가만으로 축소된다 — 확인 후 규모 확정.

### 2-4. 확인 필요 3건 (단정 보류 — 코드베이스 대조 후 판정)

| # | 확인 항목 | 확인 결과에 따른 분기 |
|---|---|---|
| V-1 | 매물 **카테고리 정의**가 DB인가 코드 상수인가 | 코드면: 카테고리 개편(파일럿 후 확실시 — 011 #21의 0건 검색어 데이터가 개편 근거를 만든다)마다 배포 필요 → [P1] DB화. DB면: 어드민 CRUD 유무만 확인 |
| V-2 | **어드민 감사 로그의 범위** — 모더레이션 한정인가, 전체 변경 액션인가 | 한정이면: #22·#23의 CRUD에 감사 기록 포함 설계(§2-3과 한 몸) |
| V-3 | **i18n 문구**(3개 언어) 변경이 배포 종속인가 | 종속이어도 [P2] 유지 판단 — 문구는 릴리스 단위 변경이 자연스럽고, 010 부록 3(i18n 키 미커밋 사고)이 보여주듯 런타임 문구 관리는 오히려 정합성 리스크. 단 **법정 고지 문구**(§7-2)만은 #23 공지 채널로 커버 |

## §4. 하지 않을 것 — 운영 계층의 과설계 기각 (010 §4 정신 승계)

| 항목 | 기각 이유 |
|---|---|
| 풀 RBAC(권한 매트릭스·커스텀 역할) | 운영 0.5~2인. 역할 2종이 상한. 인력 5인+ 시점 재상정 |
| 외부 CMS/어드민 SaaS 도입 | 기존 admin_frontend 존재. 신규 의존 추가는 SPOF 대응 방침(010 §2-4)과 역행 |
| 리모트 컨피그 시스템(임계값·플래그 런타임 편집) | §1 구분선 — 튜닝 상수는 하드코딩 유지가 010의 옳은 판단. 킬스위치 화면 기각(010 §4)도 유지 |
| 공지 예약발행·세그먼트 타겟팅·리치에디터 | 요청 안 된 유연성. 텍스트+기간+활성 플래그가 상한 |
| 어드민 대시보드 개인화·위젯 | 벤치마크 문헌의 대규모 조직용 항목 — 현 규모 무관 |
| CS 헬프데스크 외부 도입 | 010 §3-2 기각 유지 (support.py 존재) |
| 배너 다중 슬롯·큐레이션 지면 관리 | 1슬롯으로 시작. 광고 지면(#10)과의 경합 문제가 생기는 시점 — 즉 광고주가 생긴 뒤 — 재상정 |

## §6. 결론 — 대표 보고용 3문장

1. 벤치마크 5도메인 중 4개(모더레이션·거래 감독·사용자 관리·재무)는 010+011이 이미 커버하며, 결손은 **⑤ 플랫폼 설정과 운영자 계정 체계**에 집중돼 있다.
2. 결정적 증거는 010 안에 있었다 — 금칙어 확대가 코드 커밋(Q-1 `f8fa9f f`)이라는 사실은, 파일럿 중 신종 사기 키워드 대응 속도가 배포 주기에 묶여 있음을 뜻한다. **튜닝 상수는 하드코딩(010 유지), 운영 데이터는 DB+어드민(본 문서 보강)** 이 구분선이다.
3. 추가는 3건(#22 금칙어 관리, #23 공지·배너, #24 계정 개별화)뿐이며, 풀 RBAC·CMS·리모트컨피그는 명시 기각한다 — 절제 원칙은 운영 계층에도 동일하게 적용한다.
