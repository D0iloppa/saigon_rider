## 0. 결론부터 — 위험은 **콜드 스타트 악순환**과 **거래 마무리 단절**이다

지금 코드는 "기능이 없다"가 아니라 **"공급이 들어오기 전에 수요가 먼저 지친다"** 구조다. 고리는 이렇게 돈다.

```
가입 전 아무것도 못 봄        판매 등록 장벽 3중
(전 화면 로그인 필수)   ──▶  (SMS OTP + 사진 필수 + 초안 미보존)
        │                              │
        │                              ▼
        │                      매물이 안 쌓인다
        ▼                              │
설치 직후 첫 화면이            ◀────────┘
"반경 3km 내 0건"
        │
        ▼
"빈 앱이네" → 삭제 ─────▶ 남은 매물도 안 팔림 ─────▶ 판매자도 이탈
```

첫 번째 고리는 ① 가입 전 열람 허용 ② 빈 화면에서 범위 확대 유도 ③ 판매 등록 마찰 제거로 끊을 수 있다.

두 번째 위험은 **앱이 내세울 수 있는 유일한 차별점인 “합의→만남→이동”이 일반 채팅과 수동 입력 안에 묻힌 것**이다.
가격 제안과 약속은 입력창 확장 메뉴 안에 있고, 장소는 사용자가 지도에 직접 핀을 찍으며, 완료는 판매자만 할 수 있다.
즉 거래 기능은 존재하지만 사용자가 “다음에 무엇을 해야 하는지”를 앱이 이끌지 않는다.

## 1. 방법과 한계 — 무엇을 근거로 썼나

**한 것**: pull 후 현재 코드(`a758251`)에서 사용자 여정 순서(설치→가입→탐색→문의→등록→재방문)를 따라가며
진입 게이트·기본값·빈 상태·마찰 지점을 코드로 확인했다. 모든 항목에 `파일:줄` 근거를 붙였다.
i18n 3언어 패리티와 검색 정규화는 스크립트로 실측했다.

**안 한 것 (이 문서가 답하지 못하는 것)**:
- **실기기·실사용자 관찰이 없다.** 체감 속도, 저가 Android + 4G에서의 첫 콘텐츠 시간, 실제 이탈률은 여기 없다.
- **운영 데이터가 없다.** 현재 매물 수, DAU, 문의→응답 전환율을 모른다. S-2의 심각도는 **실제 매물 밀도에 좌우**된다.
- **운영 `.env`를 볼 수 없다**(로컬 미존재). `SMS_PROVIDER_API_KEY` 설정 여부는 서버에서 직접 확인해야 한다(S-4).
- 이 문서의 판단은 "코드가 이렇게 동작하므로 사용자는 이렇게 겪는다"까지다. 그 다음(얼마나 떠나는가)은 측정이 필요하다.

## 2. 여정별 진단

### S-1. 가입 전에는 매물 한 건도 볼 수 없다 — 설치 직후 최대 이탈 지점

**지금**: 서비스 기능 라우트 전체가 `PrivateRoute`다 (`frontend/src/App.tsx:494`~`590`). 미인증이면 `/splash`로 튕긴다
(`components/auth/PrivateRoute.tsx:14-16`). 공개된 것은 스플래시·인증·법적 문서뿐이며, 사용자가 가치를 판단할 서비스 콘텐츠는 없다.
그리고 그 `/splash`에는 **히어로 영상 + "시작하기" 버튼만 있다** (`pages/auth/Splash.tsx:112-123`) —
무엇을 파는 앱인지, 내 동네에 매물이 있는지 보여주는 요소가 하나도 없다.

**사용자가 겪는 것**: 앱을 켠다 → 영상과 로고 → "시작하기" → **소셜 로그인 요구** → 닉네임·라이더 스타일 선택 →
동의 2개 → 그제서야 첫 화면. 앱이 뭘 하는지 확인하기 전에 계정부터 내놓으라고 한다.

**왜 이탈인가**: 중고거래는 "내 동네에 살 만한 게 있나"를 **먼저 확인하고** 가입하는 카테고리다.
[Chợ Tốt Xe의 공식 목록 면](https://xe.chotot.com/mua-ban-xe-may)처럼 경쟁 서비스는 재고를 공개 탐색 면으로 먼저 보여준다.
지금 구조는 설치 직후 가장 큰 이탈 구간에 가장 큰 벽을 세워 둔 것이다.

**개선**:
1. **읽기 전용 공개 범위를 연다** — 우선 마켓 목록·상세와 업체 상세를 비로그인 열람 허용. 커뮤니티 공개는 개인정보·모더레이션 정책을 별도로 결정한다.
2. **행동 시점 로그인** — 찜·채팅·가격제안·등록에서만 로그인 유도. 딥링크 목적지 보존(`returnTo`)은 이미 있으니 재사용한다.
3. 백엔드 매물 목록·상세는 이미 `optional_user_session`이고(`backend/app/routers/market.py:244, 409`), 업체 지도와
   공개 상세도 익명 조회를 지원한다(`backend/app/routers/biz.py:890-903, 1036-1041`). 프론트 게이트와 익명 UI 상태가 주 작업이다.

**검증**: 로그아웃 상태에서 `/market`, `/market/:id`, `/biz/:id` 진입 시 내용이 보이고, 찜·채팅 탭 시에만
로그인 화면으로 가며, 로그인 후 **원래 보던 매물로 돌아오는지** E2E 1건.

**주의**: 개인정보·T&S 관점에서 공개 범위는 제품 결정이 필요하다. 최소한 **마켓 목록/상세만이라도** 여는 것을 권한다.

### S-2. "내 주변 3km" 기본값 — 빈 화면에서 나갈 방법을 알려주지 않는다

**지금**: 표시 범위 기본이 GPS 기준 **반경 3km** 다 (`store/useLocationStore.ts:23`, 대표 확정 2026-08-06).
마켓 목록은 이 반경으로 필터링된다(`pages/market/MarketMain.tsx:215`). 반경 안에 매물이 없으면 빈 상태가 뜨는데,
문구는 `"Chưa có sản phẩm gần bạn / Hãy đăng sản phẩm đầu tiên!"`(주변에 상품이 없어요 / 첫 상품을 올려보세요)
뿐이다 (`pages/home/HomePage.tsx:437-438`).

**사용자가 겪는 것**: 호치민 어딘가에서 앱을 켠다 → 홈 "내 주변 인기" 비어 있음 → "최근 매물" 비어 있음 →
마켓 탭도 비어 있음. **"전체 지역으로 보면 매물이 있다"는 사실을 어디서도 알려주지 않는다.**
`locationMode: 'all'`은 존재하지만(`useLocationStore.ts:25`) 빈 상태에서 그 전환을 권하지 않는다.

**왜 이탈인가**: 출시 초기에 3km 안에 매물이 쌓일 확률은 낮다. 사용자는 "매물이 적은 동네"가 아니라
**"빈 앱"** 으로 인식한다. 한 번 그렇게 판단하면 다시 열지 않는다. **이 항목이 S-1보다 고치기 쉽고 효과가 즉각적이다.**

**개선**:
1. **빈 상태를 탈출구로 바꾼다** — 빈 결과일 때 `[전체 지역 보기]` 버튼을 문구 아래 1차 CTA로 노출.
2. **자동 확대 폴백** — 3km 결과가 0건이면 전체 지역으로 다시 조회해 결과를 보여주고
   상단에 `"3km 내에 없어 전체 지역을 보여드려요"` 배너 + 되돌리기. (위치 출처 정직화 원칙과 충돌하지 않는다 — 명시 고지)
3. **반경을 데이터 밀도에 맞춘다** — 초기에는 3km가 아니라 10km 또는 '전체'를 기본으로 두고,
   매물 밀도가 오르면 좁힌다. 상수 하나(`NEARBY_RADIUS_KM`)와 기본 모드 결정이면 된다.

**검증**: 매물 0건인 좌표로 `/dev/gps` 주입 → 홈·마켓 빈 상태에 전체지역 CTA가 뜨고, 탭하면 결과가 채워지는지.

### S-3. 판매 등록 3중 마찰 — 공급이 안 쌓이는 직접 원인

`pages/market/MarketCreate.tsx` 한 화면에 이탈 요인이 셋 겹쳐 있다.

**(a) 초안이 보존되지 않는다.**
마켓 등록 화면에는 draft 저장이 **전혀 없다**(`pages/market/` 전체에 draft·beforeunload 저장 로직 0건).
피드 작성에는 P1-7로 초안 보존이 들어갔는데(`AppShell.tsx:39-40` 주석) **매물 등록에는 적용되지 않았다.**
사진 10장 + 설명 2,000자를 쓰다가 전화가 오거나 앱이 백그라운드로 내려가면 전부 사라진다.

**(b) "완료"가 왜 비활성인지 알려주지 않는다.**
`canPost`는 사진 1장 이상 + 제목 + 지역 + 업로드 완료를 모두 요구하는데(`MarketCreate.tsx:99-100`),
버튼은 그냥 `disabled` 다(`:138`). **무엇이 빠졌는지 화면 어디에도 표시되지 않는다.**
특히 거래 희망 장소는 측위 전까지 `"위치 확인 중…"` 상태(`:234`)라, 사용자는 다 채웠다고 생각하는데 버튼이 죽어 있다.

**(c) 사진이 필수다.**
`contentIds.length > 0`이 등록 조건이다(`:100`). 그런데 **"사진이 있어야 등록됩니다"라는 안내가 없다.**
사진 필수 자체는 품질 정책으로 유효하지만, 사용자가 버튼이 비활성인 이유는 알아야 한다.

**개선**:
1. 제목·설명·가격·카테고리·사진 contentId를 `localStorage`에 디바운스 저장, 재진입 시 `"작성 중이던 글이 있어요 [이어쓰기/새로 쓰기]"`.
   (이미 업로드된 이미지는 `contentId`가 서버에 있으므로 복원이 쉽다.)
2. 비활성 버튼 대신 **누르면 부족한 항목을 알려주는** 방식으로 전환하거나, 폼 하단에
   `"사진 1장 · 제목 · 거래 장소가 필요해요"` 체크리스트를 상시 노출.
3. 사진 슬롯에 `필수` 라벨.

**검증**: 등록 화면에서 절반 입력 → 앱 백그라운드/뒤로가기 → 재진입 시 복원되는가. 빈 폼에서 완료를 눌렀을 때 부족 항목이 지목되는가.

### S-4. 판매하려면 SMS OTP — 이 경로가 막히면 공급이 0이 된다

**지금**: `/market/new`는 `VerifiedSellerRoute`, 즉 **전화번호 인증 필수**다
(`App.tsx:504`, `components/auth/VerifiedSellerRoute.tsx:15-17`). 인증은 SpeedSMS.vn 실발송이다
(`backend/app/sms_client.py:22-72`). 키 미설정 시 운영에서는 발송 자체가 중단된다(`sms_client.py:42`).

**사용자가 겪는 것**: 팔려고 FAB를 누르면 **전화번호 입력 화면**이 뜬다. SMS가 안 오면 판매를 포기한다.
베트남 SMS는 발신자명 등록·통신사 필터링 때문에 도달 실패가 드물지 않고, 건당 비용도 발생한다.

**왜 위험한가**: 사기 방지 목적은 타당하지만, **공급이 절대적으로 부족한 초기**에 판매자 쪽에만 강한 게이트를 둔 것이다.
S-3와 합쳐지면 "팔아보려다 세 번 막히는" 경험이 된다.

**개선**:
1. **운영 키 설정 여부를 먼저 확인**한다 — 서버에서 `SMS_PROVIDER_API_KEY` 존재 확인 + 실제 번호로 1건 수신 테스트. (선행 조건)
2. **인증 시점을 뒤로 미룬다** — 등록은 하게 하고, **게시 직전** 또는 **첫 채팅 응답 시점**에 인증을 요구.
   최소한 등록 폼에 도달하기 전에 벽을 세우지는 않는다.
3. **실패 경로에 사람 손을 남긴다** — SMS 3회 실패 시 고객센터 문의(이미 `/settings/support` 존재)로 유도.

**검증**: 신규 계정으로 실제 베트남 번호 OTP 수신 1건. 실패 시 사용자가 다음에 무엇을 할 수 있는지 화면에 있는가.

### S-5. 채팅이 탭에 없다 — 거래 대화가 프로필 안쪽에 있다

**지금**: 탭바는 홈·마켓·동네지도·커뮤니티·프로필 5개이고 **채팅이 없다**
(`components/layout/TabBar.tsx:73-79`). 미읽음은 프로필 탭의 **빨간 점 하나**로만 표시된다(`:78`).
DM 목록 진입은 프로필 화면 상단의 아이콘 버튼이다(`pages/profile/ProfileMain.tsx:392`).

**사용자가 겪는 것**: 구매자가 문의를 보냈다. 판매자는 프로필 탭의 작은 점을 보고 → 프로필 → 아이콘 →
대화 목록 → 대화. **3탭 이상 들어가야 답장할 수 있다.**

**왜 이탈인가**: 중고거래의 성패는 **응답 속도**다. 응답이 늦으면 구매자는 다른 매물로 간다.
앱 스스로도 응답률을 신뢰 지표로 쓰면서(`marketFormat.ts` `formatResponseRate`) 정작 응답 동선을 가장 깊이 묻어놨다.
당근·Chợ Tốt 모두 채팅은 **독립 탭**이다.

**개선**: 마켓 우선 구조라면 탭바를 **마켓·동네가게·채팅·커뮤니티·나**로 바꾸고 기본 진입을 마켓으로 둔다.
홈을 유지하는 대안에서는 모든 핵심 화면 헤더에 DM 진입점을 두어야 한다. 미읽음은 점이 아니라 **숫자 배지**로 표시하고,
`TAB_PATH_PREFIXES`에서 `/dm`을 프로필 소속에서 떼어낸다(`TabBar.tsx:17`).

**검증**: 새 메시지 수신 → 홈에서 2탭 안에 답장 화면 도달. 배지 숫자가 실제 미읽음과 일치.

### S-6. 이미지 업로드 실패가 화면에 남지 않는다 — 선택한 사진 일부가 조용히 빠진다

**지금**: 업로드 실패 시 토스트 1회를 띄우고 `uploading: false`로 바꾼다(`MarketCreate.tsx:82-85`).

**사용자가 겪는 것**: 사진 5장을 올렸고 화면에도 5장이 보인다. 등록하니 3장짜리 매물이 됐다.

**검증**: 업로드 API를 강제 실패시켰을 때 화면에 실패가 남고, 재시도로 복구되는가.

**검증**: 홈·프로필에서 동작하지 않는 재화 표시가 사라지고, 그 자리에 거래 지표가 있는가.

**"오늘의 거래 관문"** 하나로 축소한다 — ① 내 거래 상태(진행 중 대화·내 매물 반응) ② 내 주변 새 매물
③ 오늘 라이딩에 필요한 정보(날씨·침수) 딱 3블록. 업체 소식·커뮤니티 인기는 해당 탭으로 내린다.

### S-13. 스플래시가 매 실행 최소 1.2초 강제된다

### S-14. P0 — “퀘스트 앱” 약속과 실제 마켓 서비스가 충돌한다

**지금**: 베트남어 스플래시는 `"Nơi mỗi chuyến đi là một nhiệm vụ"`(모든 라이드는 하나의 퀘스트)라고 말한다
(`locales/vi/translation.json:281`). 신규 가입도 “어떤 라이더인가요?”와 출퇴근러·카페 헌터·나이트 라이더를 먼저 묻는다
(`pages/auth/ProfileSetup.tsx:24-27`, `:186-207`). 베트남어 카페 헌터 설명에는 오토바이가 아니라
`"Đạp xe"`(자전거를 타다)까지 들어 있다(`translation.json:355-363`).

그러나 실제 탭은 홈·마켓·지도·커뮤니티·프로필이고 퀘스트 탭은 없다(`components/layout/TabBar.tsx:72-78`).
퀘스트 라우트는 직접 접근용으로 남아 있지만 1차 탐색에서는 제거돼 있다(`App.tsx:510-513`). 반대로 홈·프로필에는
RP, 레벨, 스킬 포인트, 퀘스트 이력이 남아 있어 거래 서비스의 신뢰 정보와 경쟁한다.

**사용자가 겪는 것**: 라이딩 게임을 기대한 사람은 마켓을 보고, 중고거래를 기대한 사람은 가입 전에 게임형 정체성 질문을 받는다.
제품을 한 문장으로 이해하지 못하면 첫 사용과 추천 모두 약해진다.

**개선**:
1. 현재 서비스 구상서를 유지한다면 스플래시를 **“내 주변 오토바이 중고거래, 만남까지 편하게”** 계열로 통일한다.
2. 가입 시 라이더 유형은 제거하거나 프로필의 선택 항목으로 늦춘다. 필수 동의와 자동 닉네임만으로 첫 가치를 보게 한다.
3. 퀘스트 효용이 다시 검증되기 전까지 RP·레벨·퀘스트 통계를 상용 핵심 면에서 숨기고 거래·응답·인증 신뢰를 올린다.

**결정 게이트**: 대표가 실제로 **퀘스트 우선 제품**을 원한다면 문구만 바꿀 일이 아니다. 서비스 구상서, 기본 탭,
첫 1분, 재방문 루프를 전부 퀘스트 중심으로 다시 정의해야 한다. 현재 코드 투자와 문서 기준으로는 **마켓 우선**이 더 작고 일관된다.

**검증**: 베트남 사용자 5명에게 스플래시와 첫 화면만 보여준 뒤 “이 앱은 무엇을 해결하나?”를 묻는다.
4명 이상이 같은 핵심 문제를 답하지 못하면 아직 통일되지 않은 것이다.

### S-15. P1 — 가격 합의 뒤 다음 행동과 만남 보조가 숨겨져 있다

**지금**: 가격 제안과 약속잡기는 메시지 입력창의 확장 메뉴에 조건부로만 나타난다
(`pages/dm/DmDetail.tsx:667-691`). 가격 수락이 약속 게이트를 열어도 사용자가 다음 행동을 발견하게 만드는 고정 CTA는 없다.
약속은 시간과 장소명·위경도·상태만 저장한다(`backend/app/schemas.py:896-902`). 장소 선택 화면은 공용 지도에서
사용자가 직접 핀을 찍게 하는 얇은 래퍼다(`pages/dm/AppointmentLocationPicker.tsx:12-20`).

수락된 약속 카드에서 길찾기로 넘어가는 연결은 이미 있다(`DmDetail.tsx:494-514`). 즉 기반은 갖췄지만,
서비스 구상서의 핵심인 **“어디서 언제 만날지 결정하는 수고”**는 사용자가 그대로 부담한다.

**사용자가 겪는 것**: 일반 채팅으로 가격·시간·장소를 여러 번 왕복하고, 안전한 공개 장소·양측 이동시간·영업 여부는
다른 지도 앱에서 다시 조사한다. Saigon Rider를 써야 할 이유가 일반 마켓 + 메신저 조합보다 강해지지 않는다.

**개선 순서**:
1. DM 상단에 `문의 → 가격 합의 → 약속 → 만남 → 완료` 상태 스트립과 현재 가능한 주 CTA 하나를 고정한다.
2. 가격 수락 직후 `약속 잡기`를 확장 메뉴 밖으로 올린다.
3. 판매 위치와 구매자가 선택한 대략적 동을 기준으로 **안전한 공개 장소 후보 3개**를 제안한다.
4. 후보별 양측 예상 이동시간, 영업 중 여부, 주차·밝은 장소 여부를 표시한다.
5. 약속 당일 `출발`, `도착`을 DM 시스템 상태로 공유한다. 정확한 실시간 위치는 별도 동의 없이는 공유하지 않는다.

**검증**: 가격 수락 직후 처음 온 사용자가 별도 설명 없이 약속을 만들고, 지도 검색 없이 후보 하나를 골라
양측이 동일한 시간·장소·경로를 확인할 수 있는지 E2E로 검증한다.

### S-16. P1 — 판매자가 완료하지 않으면 구매자의 거래도 끝나지 않는다

**지금**: 약속이 `ACCEPTED`일 때 완료 버튼은 판매자에게만 보인다(`DmDetail.tsx:461-505`). 백엔드도 판매자 외 요청을
403으로 막고, 완료되어야 매물이 `SOLD`가 된다(`backend/app/routers/market.py:1262-1298`). 리뷰 API는 완료된 약속이
있어야 거래 참여를 인정한다(`market.py:893-930`).

**사용자가 겪는 것**: 실제 거래가 끝났어도 판매자가 앱을 다시 열지 않으면 구매자는 완료·리뷰를 진행할 수 없다.
운영 데이터에도 실제 거래가 미완료로 남아 판매자 신뢰와 전환율이 왜곡된다.

**개선**:
1. 구매자에게 `거래 완료 요청`을 제공하고 판매자에게 푸시와 DM 상태 알림을 보낸다.
2. 약속 시간이 지난 뒤 양측 모두에게 완료·취소 확인을 반복 노출한다.
3. 자동 완료는 분쟁·노쇼 정책 없이 도입하지 않는다. 판매자 미응답은 일정 기간 후 운영 검토 또는 명시적 이의 절차로 넘긴다.

**검증**: 판매자가 약속 후 앱을 닫은 시나리오에서도 구매자가 완료 요청을 만들고 처리 상태를 확인할 수 있어야 한다.

### S-17. P0 조건부 — 자체 경로 엔진 실패가 인앱 길찾기 실패로 직결된다

**지금**: 현재 HEAD `a758251`은 자체 라우팅 엔진 검증을 위해 Google Routes 폴백을 명시적으로 차단한 상태다.
자체 엔진 결과가 없으면 백엔드는 즉시 `configured=false`를 반환한다(`backend/app/routers/info_route.py:215-231`).
프론트는 인앱 경로 대신 “준비 중” 안내와 외부 Google 지도 열기를 제공한다(`pages/ride/RideNav.tsx:445-448, 743-751`).

외부 폴백 URL도 두 곳 모두 `travelmode=two_wheeler`를 사용한다(`RideNav.tsx:447, 505`). 그러나
[Google Maps URL 공식 값](https://developers.google.com/maps/documentation/urls/get-started)은 하이픈이 있는 `two-wheeler`다.
[베트남은 공식 지원 지역](https://developers.google.com/maps/documentation/routes/coverage-two-wheeled)이므로, 현재 문자열은
지원 부재가 아니라 **파라미터 불일치**다. 외부 지도가 오토바이 모드를 무시하거나 다른 방식으로 열릴 위험이 있다.

**조건**: 이 커밋이 실제 운영에 배포됐는지는 별도 확인이 필요하다. 그러나 상용 브랜치 기본값으로는 자체 엔진의 일시 오류가
곧 핵심 차별점의 중단이 되므로 출시 게이트로 다뤄야 한다.

**사용자가 겪는 것**: 가격과 약속을 앱에서 마친 뒤 마지막 이동 단계에서 인앱 미리보기가 사라지고 다른 앱으로 밀려난다.

**개선**:
1. 검증 모드를 코드의 직접 `return`이 아니라 환경 플래그로 분리한다.
2. 외부 Google URL의 모드를 공식 값 `two-wheeler`로 고치고 베트남 실기기에서 실제 선택 모드를 확인한다.
3. 운영은 `자체 엔진 → 보조 경로 제공자 → 명시적 외부 앱 열기` 순서의 회복 경로를 유지한다.
4. 엔진 성공률·p95 응답시간·폴백률을 계측하고 목표가 충족될 때만 자체 엔진 단독 전환을 판단한다.

**검증**: 자체 엔진 timeout/5xx를 주입해도 같은 약속 카드에서 한 번의 추가 탭 이내로 경로 확인을 계속할 수 있어야 한다.

### S-18. P0 운영 — 사용자가 왜 떠나는지 측정할 제품 퍼널이 없다

**지금**: 저장소에서 PostHog·Mixpanel·Amplitude·Firebase Analytics 또는 일반 `trackEvent` 형태의 제품 이벤트를
확인하지 못했다. 예외 운영자 알림과 퀘스트 GPS telemetry는 있지만, 스플래시 이탈·로그인 벽·위치 거부·빈 결과·거래 단계
이탈을 설명하지 못한다. 거래 테이블로 가격 제안·약속·완료의 일부는 사후 계산할 수 있을 뿐이다.

또한 서비스 구상서는 “한 개 구 안의 밀도로만 이긴다”고 규정하지만(`service-concept-260726.md:70, 184-187`),
파일럿 구는 미정으로 남아 있다(`:237`). UI 문제와 공급 부족 문제를 구분할 수 없는 상태다.

**사용자/사업 영향**: 개선해도 실제 불편이 줄었는지 모르며, 빈 결과를 공급 문제 대신 새 기능으로 해결하려는 잘못된 투자가 반복된다.

**최소 계측**:
- `landing_view`, `public_listing_view`, `auth_prompted(reason)`, `auth_completed`
- `profile_setup_skipped/completed`, `location_prompt_result`
- `market_results_loaded(count_bucket, ward_id)`, `chat_started`, `first_reply`
- `offer_accepted`, `appointment_accepted`, `route_result(mode)`, `trade_completed`, `review_submitted`

정확한 GPS, 메시지 본문, 전화번호는 이벤트에 넣지 않는다. `ward_id`, 결과 건수 구간, 진입 경로만으로 충분하다.

**검증**: 첫 방문부터 거래 완료까지 단계별 사용자 수·이탈률을 한 대시보드에서 보고, 0건 결과를 구역·카테고리별로
구분하며, UI 변경 전후를 같은 정의로 비교할 수 있어야 한다.

### S-19. P1 — 안전 안내가 실제 약속 시점과 분리돼 있다

**지금**: 안전거래 가이드는 홈의 일반 배너로만 접근한다(`pages/home/HomePage.tsx:562-581`). 실제 위험이 커지는
매물 상세의 채팅 진입, 가격 수락, 약속 제안·수락, 길찾기 카드에는 공개 장소·현장 확인·과도한 선입금 주의가 없다.
신고·차단은 사후 대응이지 예방 장치가 아니다.

**개선**:
1. 첫 약속 수락 전에 공개 장소, 현장 확인, 과도한 선입금 금지, 문제 시 신고를 한 번만 짧게 보여준다.
2. 추천 장소에는 `공개 장소`, `영업 중`, `밝은 곳` 같은 추천 근거를 표시한다.
3. 약속 카드에서 상대 신고·차단·안전 가이드로 바로 연결한다.

**검증**: 홈 가이드를 읽지 않은 신규 사용자도 약속 수락 과정에서 핵심 안전 수칙과 신고 경로를 확인할 수 있어야 한다.

## 3. 이미 잘 되어 있는 것 — 되돌리지 말 것

측정해 보니 다음은 현지 서비스 기준으로 **잘 만들어져 있다.** 개선 작업 중 훼손하지 않도록 명시해 둔다.

- **다국어 품질**: vi/ko/en **각 1,923키 완전 패리티**, vi 값에 한글 혼입 **0건**(스크립트 실측).
- **베트남어 검색 정규화**: 성조 제거 + `đ→d` 치환 구현(`backend/app/services/search_norm.py`) —
  성조 없이 입력하는 현지 관습에 대응. 교차언어 검색도 최근 커밋에서 처리됨.
- **현지 표기 관례**: 가격 `1.234.567 đ`(마침표 천단위·후치), 10억 이상 축약, 거리→**오토바이 N분**,
  응답률 배지, 0원=나눔 (`pages/market/marketFormat.ts`). Chợ Tốt 실측 관례를 따랐다.
- **거래 상태 무결성**: SOLD는 수동 전환 금지(서버 400) + 되돌리기 차단, SOLD 매물은 목록·지도에서 제외
  (`pages/market/MarketDetail.tsx:42-43`, 커밋 `cd32ad1`).
- **키워드 알림**: 원하는 물건을 등록해 두면 알림 — 재방문 루프의 정석 기능이 이미 있다(`MarketMain` 알림 시트).
- **성능 기반**: 초기 로드 gzip 911KB→247KB, 폰트 자체호스팅(외부 CDN 3건 제거), 청크 로드 실패 자동 복구.
- **위치 정직성**: GPS 실패 시 폴백 좌표임을 숨기지 않고 표기(`location.fallbackTitle` = "Trung tâm TP.HCM").
- **오토바이 경로 경고**: Google의 two-wheel 베타 경고 요구에 대응하는 3언어 문구와 화면 노출이 이미 있다
  (`RideNav.tsx:635-636`). 외부 URL 파라미터는 S-17대로 별도 수정하되 이 경고는 유지한다.
- **알림 전달 신뢰성**: DM 알림이 메시지 저장과 같은 트랜잭션의 outbox로 발행돼 유실되지 않는다(`routers/dm.py:414-419`).

## 4. 권고 처리 순서

### Wave 0 — 파일럿 전에 반드시 닫기

1. **제품 문장 결정(S-14)**: 마켓 우선인지 퀘스트 우선인지 확정하고 스플래시·가입·기본 진입을 통일한다.
2. **가치 선공개(S-1)**: 비로그인 마켓 목록·상세와 업체 상세를 열고 행동 시 로그인으로 바꾼다.
3. **빈 앱 탈출(S-2)**: 전체 지역 보기와 키워드 알림을 빈 상태에 연결한다.
4. **최소 계측(S-18)**: 유입→첫 매물→인증→채팅→약속→완료 이벤트를 배포한다.
5. **경로 회복(S-17)**: 운영에서 자체 엔진 실패 시 안전한 폴백을 보장한다.
6. **공급 운영(S-3·S-4)**: 파일럿 구 한 곳과 집중 카테고리를 정하고 판매 등록 초안·OTP 실발송을 검증한다.

### Wave 1 — 첫 파일럿에서 거래 성공률 올리기

1. 채팅함을 1차 내비게이션으로 올리고 DM에 거래 단계 스트립을 둔다(S-5·S-15).
2. 구매자 완료 요청과 약속 후 리마인더를 추가한다(S-16).
3. 안전 안내를 홈에서 실제 약속 시점으로 옮긴다(S-19).
4. 이미지 업로드 실패 복구, 등록 필수항목 안내, 채팅 알림 설정을 보완한다(S-3·S-6·S-9).
5. 홈의 매물 로딩을 비핵심 정보 API와 분리하고 백그라운드 DM 폴링을 멈춘다(S-8·S-10).

### Wave 2 — 차별점을 실제 서비스로 만들기

1. 안전한 공개 장소 후보와 양측 ETA를 제안한다(S-15).
2. 출발·도착 상태를 약속 카드에 연결한다.
3. 판매중·예약중·완료와 문의 현황을 보는 판매자 관리 화면을 만든다(S-11).
4. `/info`의 위치 SoT를 고치고 존치 여부를 결정한다(S-12).
5. 파일럿 데이터가 효과를 증명한 뒤에만 퀘스트, 광고, 추가 홈 카드 투자를 판단한다.

| D-3 | 초기 기본 반경 (S-2) | 3km 유지 / 10km / 전체 | 밀도가 쌓일 때까지 **전체**, `내 주변`은 사용자 선택 |
| D-4 | 판매 전화인증 시점 (S-4) | 현행 / 게시 직전 / 첫 응답 시 | 신뢰를 유지하며 **게시 직전**으로 이동 |
| D-5 | 게이미피케이션 표시 (S-7) | 현행 노출 / 숨김 / 재개 | 효과 검증 전까지 **상용 핵심 면에서 숨김** |
| D-6 | 1차 IA (S-5·S-8) | 홈 유지 / 홈 제거 | **마켓·동네가게·채팅·커뮤니티·나**, 기본 진입은 마켓 |
| D-7 | 구매자 완료 참여 (S-16) | 판매자 전용 / 요청권 / 양측 즉시 완료 | **구매자 요청 + 판매자 확인·운영 이의 절차** |
| D-8 | 운영 경로 정책 (S-17) | 자체 엔진 단독 / 이중 폴백 | 성공률 입증 전 **이중 폴백** |
| D-9 | 파일럿 지역 (S-18) | 대학가 / 신도심 / 전통 주거지 | 코드가 아닌 공급팀 결정. **한 곳만 선택** |

## 6. 상용 파일럿에서 측정할 것

아래 수치는 현재 성과가 아니라 **출시 전에 합의할 초기 제안 게이트**다. 2주 베이스라인을 확보한 뒤 재조정한다.

| 지표 | 정의 | 초기 제안 게이트 |
|---|---|---:|
| 첫 가치 도달률 | 첫 세션에서 실제 매물 목록 또는 상세를 본 사용자 / 랜딩 사용자 | 70% 이상 |
| 첫 가치 시간 | 앱 진입부터 첫 실제 매물 카드 노출까지 | p75 3초 이내 |
| 로그인 벽 이탈률 | 행동 기반 로그인 진입 후 미완료 | 40% 미만 |
| 빈 결과율 | 파일럿 구·핵심 카테고리에서 0건 결과 세션 | 20% 미만 |
| 첫 응답시간 | 구매자 첫 문의부터 판매자 첫 응답 | 운영시간 중앙값 30분 이내 |
| 가격 수락→약속 | 수락된 가격 제안 중 약속 수락까지 간 비율 | 50% 이상 |
| 약속 닫힘률 | 수락 약속 중 완료 또는 명시적 취소로 닫힌 비율 | 80% 이상 |
| 경로 연속성 | 경로 요청 중 인앱 성공 또는 정상 폴백 | 99% 이상 |
| 활성 사용자 D7 | 첫 매물 조회 또는 채팅 사용자의 7일 내 재방문 | 베이스라인 후 개선 목표 설정 |

반드시 함께 확인할 운영·정성 항목은 다음과 같다.

1. **현재 매물 수와 지역·카테고리 분포** — 3km 반경에서 실제로 몇 건을 보는가.
2. **운영 SMS 실발송** — 실제 베트남 번호의 수신률·지연·실패 후 회복 경로.
3. **저가 Android + 4G 첫 콘텐츠 시간** — 스플래시·지도·이미지 체감.
4. **신규 구매자·판매자 각 5명 관찰** — 첫 화면만 보고 서비스 목적을 같은 문장으로 설명하는가.
5. **거래 단계별 막힘 이유 인터뷰** — 가격 합의 뒤 다음 행동, 장소 결정, 완료에서 무엇을 망설였는가.

## 9. 최종 판정

### 전면 공개 — 조건부 NO-GO

가입 전 가치 확인 불가, 퀘스트와 마켓의 약속 충돌, 거래 진행·이동 회복 경로의 비가시성, 제품 계측 부재가 동시에 남아 있다.
지금 전면 공개하면 기능 결함보다 **“무슨 앱인지 모르겠다 / 볼 게 없다 / 답장이 늦다 / 거래가 끝나지 않는다”**는 이유로 이탈할 가능성이 크다.

### 한 개 구 파일럿 — P0 해소 후 GO

매물→채팅→가격→약속→경로→완료의 기술적 뼈대는 이미 있다. 새 대형 기능보다 진입 순서, 다음 행동의 가시성,
실패 회복, 한 지역의 실제 공급을 먼저 고치면 작은 변경으로 서비스 가치를 검증할 수 있다.

**가장 먼저 할 세 가지**:

1. 비로그인 매물 보기
2. 마켓 우선 제품 문장·가입·기본 진입 통일
3. 퍼널 계측과 파일럿 구 공급 운영 시작

## 부록 A. 초기 매물이 0인 문제를 어떻게 풀 것인가 (S-2 공급 측 해법)

> S-2는 UI 수정만으로 닫히지 않는다. "빈 화면에 탈출구를 준다"는 **증상 처리**이고,
> 근본은 **파일럿 구의 실제 공급 밀도**다. 여기서는 공급을 만드는 방법을 코드 가능 여부와 함께 정리한다.

### A-0. 전제 — 가짜 매물은 답이 아니다

타 플랫폼 크롤링 재게시나 봇 계정 시딩은 **문의해도 판매자가 없는** 경험을 만든다.
첫 사용자에게 최악이고, T&S 정책(신고·제재 체계를 이미 갖춘 서비스)의 자기부정이며,
나중에 지우면 더 빈 앱이 된다. 만드는 것은 **실물이 존재하는 진짜 매물**이어야 한다.

### A-1. 지역을 좁힌다 — 비용 0, 효과 최대

3km 반경의 체감 밀도는 총 매물 수가 아니라 **집중도**의 함수다.

| 시나리오 | 총 활성 매물 | 3km 반경 체감 | 결과 |
|---|---|---|---|
| 호치민 전역에 분산 | 500건 | 약 2건 | **빈 앱으로 인식** |
| 한 개 구에 집중 | 150건 | 30~50건 | **살아 있는 앱** |

파일럿 구 1개를 정하고 **시딩·홍보·오프라인 접점을 전부 그 구에만** 건다.
앱 코드 변경은 없다. §9의 "한 개 구 파일럿" 판정과 같은 결론이며, S-2의 반경 상수 조정보다 우선한다.

### A-2. 공급 시딩 3경로

**(a) B2B 물량 — 가장 빠르고, 지금 코드에 경로가 없다.**
오토바이 가게·정비소·부품점 3곳이 개인 판매자 30명보다 매물이 많고, 영업으로 모집할 수 있으며, 지속 공급된다.
업체 도메인(신청·검증·관리·소식·광고)은 이미 구현돼 있는데 **업체 계정이 매물을 등록할 경로만 없다**
(`backend/app/routers/biz.py`에 판매자 연결 없음). 필요한 작업은 업체 계정의 `/market/new` 접근과 판매자 표기의 업체 전환이다.
부수 효과로 **S-4(SMS OTP)를 우회할 수 있다** — 이미 있는 사업자 검증(`pages/biz/BizVerification.tsx`)을 판매자 인증으로 대신 쓰면 된다.

**(b) 운영 대행 등록 — 어드민에 등록 기능이 없다.**
`backend/app/routers/admin_api/listings.py`는 조회·상세·모더레이션(`POST /{id}/moderate`)뿐이고 **생성 엔드포인트가 없다.**
운영팀이 앱으로 직접 올리거나, 어드민에 등록 화면을 소규모로 추가한다.
어느 쪽이든 **"위탁 등록" 배지로 출처를 표기**하고 일반 사용자로 위장하지 않는다.

**(c) 오프라인 앵커.** 이미 DB에 있는 정비소·주유소(`info_repair`·`info_gas`)에 QR 포스터를 건다.
파일럿 구에 한정하면 물리적으로 실행 가능한 규모다.

### A-3. 수요를 먼저 모은다 — "삽니다(Cần mua)" 타입 (신규, 비용 대비 최대)

**공급이 0이어도 구매 요청 글은 생긴다.** "Honda Vision 삽니다 ~2천만동" 같은 글이 20건 쌓이면
그 자체가 콘텐츠이고, 판매자를 끌어들이는 유인이 된다. 마켓플레이스 콜드 스타트의 정석이다.

- **현재 스키마에 없다** — 매물은 판매 전용(`listing_type` 류 컬럼 부재).
- **구현 규모는 작다** — `listings`에 `listing_type: SELL|WANTED` 컬럼 1개 + 목록 필터/탭 + 카드 배지.
  검색·DM·가격제안·키워드 알림·신고·모더레이션은 **전부 기존 것을 재사용**한다.
- **덤**: WANTED에는 사진이 불필요하므로 S-3(c) 사진 필수 마찰을 이 타입에서는 자연히 비켜간다.

### A-4. 빈 화면을 재방문 예약으로 바꾼다 — 인프라는 이미 완비

키워드 알림 파이프라인은 **이미 끝까지 배선돼 있다**:
등록·삭제 API(`backend/app/routers/market.py:1016-1069`) + 매물 등록 시
`market.listing_created` 이벤트를 같은 트랜잭션에 적재(`market.py:583-588`) → 워커가 매칭·푸시.

문제는 **정작 결과 0건 화면에서 이 기능을 권하지 않는 것**이다. 빈 상태의 1차 CTA를 바꾼다:

> "'mũ bảo hiểm' 매물이 올라오면 알려드릴게요" **[알림 받기]**

이탈이 **푸시 대기 리스트**로 전환되고, 첫 매물이 올라오는 순간 대기자 전원에게 도달한다.
A-2(공급 시딩)와 곱셈으로 작동하므로 **가장 먼저 넣을 UI 변경**이다.

### A-5. 매물 없이도 열 이유를 앞에 둔다

날씨·침수·주유소·정비소·길찾기는 **매물이 0이어도 매일 쓸 이유**이며 이미 구현돼 있다.
밀도가 임계에 닿기 전까지 홈을 "오늘의 라이딩 정보 + (있으면) 주변 매물"로 두면
**앱의 초기 가치가 공급 밀도에 종속되지 않는다.** (S-8 홈 역할 재정의와 같은 방향 — 단계적으로 거래 중심으로 전환)

### A-6. 임계 밀도 — 전면 공개 판단 기준

파일럿 구에서 아래를 만족하기 전까지 전면 공개 마케팅비는 새는 돈이다.

| 지표 | 목표 |
|---|---|
| 활성 매물(파일럿 구) | **150건 이상** |
| 3km 반경 평균 노출 매물 | **20건 이상** |
| 주간 신규 매물 유입 | **20건 이상** |
| 문의→48시간 내 응답률 | **60% 이상** (S-5 개선과 연동) |

| 순서 | 항목 | 근거 |
|---|---|---|

| 병행 | **A-2(a) 업체 매물 등록 경로** | 공급 물량의 주력, S-4 우회 효과 동반 |
