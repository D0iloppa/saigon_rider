## 1. 배경 · 목적

- 광고 게재 주체로서 **비즈니스 계정**을 신설한다. 일반 이용자 계정과 구분되는 관리 대상이며, 광고 운영을 위해 **관리자 페이지에서 사람이 관리**할 수 있어야 한다.
- 현재 광고는 dev 시드 데이터로만 존재 — 소유 주체가 없다. 이를 비즈니스 계정 체계로 병합해야 한다.

## 2. 현재 상태 (사실)

- 계정: OAuth 로그인(B-2) 기반 단일 `users` 도메인. 계정 유형 구분 없음.
- 광고: 마켓/홈 피드에 AD 카드 노출 중 (dev 시드, 소유 계정 없음).
- admin: `/admin/*` 콘솔 존재 — 주유소 제보 승인 큐(`/admin/gas-submissions`, PENDING→승인/반려) 등 **수동 심사 큐 패턴 기구현**. 비즈니스 계정 심사에 동일 패턴 재사용 가능.
- 푸시/알림: noti_worker (260710 신설) — 심사 결과 통지 등에 재사용 가능.

## 3. 결정 필요 쟁점 (D1~D5)

> 각 쟁점은 리서치(§4) 반영 후 권고안 확정. 대표 결정 전까지 구현 착수 금지.

### D1. 도메인 모델 — 별도 계정 vs 일반 계정 승격
- **옵션 A**: 비즈니스 계정 별도 신설 (별도 가입·로그인)
- **옵션 B**: 일반 계정 유지 + 비즈니스 프로필 부착(전환 신청) — 로그인은 하나, "비즈 프로필"이 별도 엔티티
- 파급: 가입/로그인 플로우, 세션 체계, 프로필 화면 분기 전부 이 결정에 종속.

### D2. 계정 심사 플로우
- 신청 → **수동 승인/반려** (사람 관리) 는 확정 전제.
- 세부: 신청 시 요구 정보(사업자 정보? 가게 정보? 사진?), 반려 사유 전달 방식, 재신청 정책.

### D3. 광고 게시 플로우 — 즉시 게시 vs [요청→승인→게시]
- 계정 심사와 별개로 광고 건별 심사를 둘 것인가.

### D4. 계정 단위 — 가게 단위 vs 그룹(브랜드) 구조
- 예: "하이랜드" 브랜드 ↔ "하이랜드 벤탄점" 지점. 광고 게재·관리 단위는 지점, 이를 묶는 그룹 단위 필요성.

### D6. 웹 채널 이원화 범위 (2026-07-10 추가 발제)
- **옵션 1**: 비즈니스 랜딩 도메인(+고객센터 링크)만 신설, 신청·광고 관리는 전부 사이공라이더 앱 내

### D5. 기존 dev 광고 병합

## 4. 리서치 — 당근 비즈프로필 외 (2026-07-10, Sonnet 웹리서치)

**당근 비즈프로필**:
- **계정 관계**: 별도 회원가입 아님 — 당근 계정에 딸린 부속 기능. 계정 하나 아래 "비즈프로필"+"광고주 계정" 연결, **계정당 비즈프로필 최대 3개**. (businessdaangn.gitbook.io/business.daangn/guide/account)
- **개설 심사**: 일반 업종은 **사업자등록증 없이 즉시 자가 개설**(업체명·위치·업종·사진·전화). 농수산물 등 특정 업종만 서류 요구. 반려 사유 공식 전체 목록은 미확인(cs.kr.karrotmarket.com FAQ #11780, JS 렌더링으로 원문 추출 실패).
- **지점/브랜드**: 프랜차이즈는 일반 비즈프로필과 분리된 상위 티어 **"브랜드프로필"**(2022.6, 1호 SPC) — 본사가 기업 계정 하나로 전국 지점 통합 관리, 지점별 캠페인·위치 타겟팅. **자유 개설이 아니라 별도 제휴 기반**. 세그먼트 3단: 비즈프로필(소상공인)→브랜드프로필(프랜차이즈)→공공프로필(기관).
- **광고 플로우**: **[캠페인 생성→소재 제작→심사 요청→통과 시 자동 게시]** — 즉시게시 아님. 심사 대체로 24h 이내, 결과는 당근 채팅으로 통보. 소재 반려 기준 상세는 공식 원문 미확인(FAQ #468/#6634).
- **보조**: Grab Merchant = 한 사업자 계정이 여러 outlet 관리(멀티스토어). Facebook = Page(프로필)와 Ad Account(과금) 분리 + Business Manager 가 N:N 통합 관리 — 셀프서비스 확장형.

**확정 플로우 (D1+D2 종합 — 오해 방지용 명문화, 2026-07-10 정정)**:

```
[일반계정 가입 (기존 OAuth 로그인, 변경 없음)]
        → [프로필 탭 "비즈니스 파트너" → 신청 폼 제출]   ← 비즈니스 "가입/로그인" 없음
        → [PENDING: admin 수동 심사 (승인/반려+사유)]
```

- 일반 가입은 지금과 동일하게 무심사. **수동 심사가 붙는 지점은 "비즈 프로필 개설(파트너 신청)" 단 하나** — 당근은 이 단계가 즉시 개설(무심사)인데 우리는 초기 규모 특권으로 사람이 승인.
- 승인 후에도 그 사람의 일반 이용자 활동(구매·DM 등)은 그대로 유지 — 프로필이 "부착"되는 것이지 계정이 "전환(승격)"되는 게 아님.

**권고 종합**: 당근의 검증된 골격(계정 부속 프로필 + 광고 심사制 + 랜딩은 웹·처리는 앱)을 다운스케일하되, 당근과 달리 **비즈 프로필 개설도 수동 심사**(우리 규모 특권), 브랜드 구조는 **스키마 자리만** 선확보.

## 8. 비즈니스 랜딩페이지 기획 (D6 옵션 1 구현체, 2026-07-10 확정 추가)

**성격**: 파트너 모집 영업 도구 + 신뢰면 + 고객센터(경량). business.daangn.com 모델 — **처리 기능 없음**, 모든 CTA 는 앱으로 유도. 관리 콘솔 아님(D6).

**기술 방향**: 순수 정적 페이지(HTML/CSS 수준, SEO 위해 SSG/정적 필수 — 앱 SPA 번들과 분리). 서빙은 기존 Nginx 에 라우트/서버블록 추가. 별도 프레임워크 도입 금지(Simplicity First).

**언어**: **vi 기본**(타겟=호치민 소상공인), ko/en 보조. 앱 i18n 3종 체계와 동일 우선순위 아님에 주의 — 랜딩만큼은 vi-first.

**페이지 구조(섹션 순서)**:
1. **Hero** — 가치제안 1문장("동네 라이더에게 내 가게를 알리세요" 방향) + 주 CTA
2. **혜택 3요소** — 위치 기반 노출(지도·피드), 라이더/지역민 타겟, 심사형 광고(신뢰)
3. **작동 방식 3스텝** — 파트너 신청 → 심사(수동, 반려 가능 고지) → 광고 게시(건별 심사)
4. **광고 상품 미리보기** — 앱 피드 AD 카드 실물 스크린샷 (가짜 성과숫자·가짜 고객로고 금지 — 기존 원칙)

6. **문의** (고객센터 2층) — 이메일 + (L2 결정 시) Zalo 링크. 별도 문의 시스템 구축 안 함
7. 푸터 — 운영사 표기, 정책 링크

**CTA 흐름**: 앱 설치자 → 딥링크(신청 화면, BP-2 의 라우트 규약 따름) / 미설치자 → 스토어 링크. **앱 스토어 등록 전 배포 시**: CTA 를 "사전 문의"(이메일/Zalo)로 대체하는 프리런치 모드 — 깨진 스토어 링크 금지.

**잔여 소결정 (구현 착수 시 확인 — 블로커 아님, 기본값 제시)**:
- **L1 도메인**: **전용 도메인 `saigon-rider.com` 확보됨(2026-07-10 대표 확인)** — 기본값 `business.saigon-rider.com` 서브도메인. 앱/API 의 letantonsheriff.com→saigon-rider.com 마이그레이션(runbook §도메인 마이그레이션)과 순서 조율 필요 — 랜딩은 신규 도메인에 바로 올려도 무방(기존 트래픽 없음)
- **L2 문의 채널**: Zalo OA 개설 여부 (베트남 관례상 권장) — 미개설 시 이메일 단독 시작
- **L3 프리런치 여부**: 배포 시점에 앱 스토어 등록 상태 확인 후 CTA 모드 선택

## 9. 앱 내 UI 배선 · 신설 페이지 맵 (D1 확정 반영)

### 9-3. 고아(orphan) 방지 — 인바운드 배선 매트릭스 (**DoD**)

> **원칙: 라우트만 추가된 페이지는 미완성이다.** 각 신설 페이지는 아래 인바운드 경로가 **배선되어야 해당 패키지 DONE** — 구현 스레드의 리뷰어는 이 매트릭스로 고아 여부를 판정한다.

| 신설 페이지 | 인바운드 (기존 UI 수정 지점) |
|---|---|
| `/biz/intro` | ① 프로필 탭 "비즈니스 파트너" 메뉴(신설 행) ② 랜딩 CTA `/link?action=biz` (LinkRouter `biz` 케이스 추가) |
| `/biz/apply` | `/biz/intro` CTA (+ `/biz/status` 재신청 CTA) |
| `/biz/status` | ① 프로필 탭 메뉴(PENDING/REJECTED 분기) ② 심사 결과 알림 딥링크(인앱 알림함 포함) |
| `/biz/manage` | ① 프로필 탭 메뉴(APPROVED 분기) ② 승인 알림 딥링크 |
| `/biz/ads/new` | `/biz/manage` "광고 등록" CTA |
| `/biz/ads/:id` | ① `/biz/manage` 광고 목록 행 ② 광고 심사 결과 알림 딥링크 |

**따라서 각 패키지의 diff 에는 신설 페이지 + 위 표의 기존 화면 수정(프로필 탭 메뉴 / AD 카드 / LinkRouter / noti_worker BIZ 타입 / admin nav)이 함께 포함되어야 한다.** frontend-page-map·ADR 갱신도 각 패키지 DoD 에 포함.

### 10-2. 고객센터 운영 (3층 구조 — 시스템 최소)

1. **1층 FAQ**: 랜딩 §8 FAQ 섹션 + 앱 `/biz/intro` 에 동일 내용 아코디언. 관리 = 정적(코드 수정) — CMS 안 만듦.
