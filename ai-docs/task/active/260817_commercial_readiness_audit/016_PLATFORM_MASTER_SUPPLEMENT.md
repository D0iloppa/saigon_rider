### 1-4. 파일럿 판정 기준 부재 — 최대 공백

010 §1-1은 파일럿 목적을 **"이 동네에서 거래가 실제로 일어나는가를 측정"** 으로 정의했으나, **무엇이 성공이고 무엇이 실패인지 정량 기준이 없다.**

마켓플레이스에서 이 질문의 표준 답은 **유동성(liquidity)** — 매물이나 요청이 합리적 시간 내에 매칭될 확률 — 이다. 규모와 다르다: 매물 100만 건이어도 매칭이 안 되면 비유동적이고, 수백 건이어도 대부분의 검색이 거래로 끝나면 고유동적이다. 중요한 것은 원시 개수가 아니라 **성사율**이며, **수요측 최소 1개 + 공급측 최소 1개**를 함께 봐야 한쪽을 최적화해 다른 쪽을 굶기지 않는다. 또한 **도시 전체 평균은 특정 지역이 죽어 있는 것을 숨기므로 세그먼트별로 봐야 한다.**

→ §6-6에서 5개 지표로 정의. **개시 전 목표선 확정 필수(D-31).**

### 1-5. 최대 발견 — 베트남 오토바이 거래는 대면에서 끝나지 않는다

2차 출처(**L-6** 확인 필요)에 따르면, 2023-08-15 이후 중고 오토바이 소유권 이전이 실효적으로 집행되고 있다: **공증 매매계약 → 판매자의 번호판·등록증 회수(thủ tục thu hồi) → 매매계약일로부터 30일 내 구매자 신규 등록.** 미이행 시 판매자 과태료, 무번호판 주행 시 차량 압류·고액 벌금.

이는 세 가지를 바꾼다:
1. 매물의 **서류 상태가 컨디션보다 중요한 변수**다
2. `deal_complete`(자기신고)는 **거래의 1단계일 뿐**이다
3. **30일 기한 = 추적 가능한 후속 절차** → Chợ Tốt이 하지 않는 **SGR의 가장 구체적인 차별화 지점**

## §3. L0 — 기반: 이벤트 파이프라인

> **모든 계층의 전제.** 랭킹·모니터링·분석·재발 통계 전부가 이 위에 선다.

### 3-1. [P0] 이벤트 스키마의 근시안

**사실**: 010 #5는 "핵심 이벤트 8종이 이벤트 테이블에 쌓이고 어드민에서 일별 단계 수를 조회"로 완료 조건을 정의했다. D-18 권고는 (a) 자체 이벤트 테이블.

**판단**: 자체 테이블 채택은 옳다(PDPL 국외 이전 회피). 문제는 **스키마의 폭**이다. 카운터성 스키마는 다음을 **전부** 못 준다:

- 랭킹 v1의 입력(매물별 조회·문의 수)
- 최근 본 매물·카테고리 친화의 원료(user×item 상호작용)
- L2 오탐률 실측(플래그 매물의 실제 전환)
- 채널별 퍼널·코호트 리텐션·유동성 지표
- 향후 추천 모델의 학습 데이터

→ **파일럿 4~8주치 데이터가 통째로 재사용 불가.**

### 3-2. 보강 스키마 (공수 델타 S)

```sql
CREATE TABLE app_events (
  event_id      BIGSERIAL PRIMARY KEY,
  event_type    VARCHAR(40) NOT NULL,   -- 백엔드 Enum 검증 (D-19 방식 승계)
  user_id       BIGINT,                 -- 비로그인 NULL
  anon_id       UUID,                   -- 비로그인 열람 퍼널
  subject_type  VARCHAR(20),            -- 'listing'|'ad'|'biz'|'user'|'search'
  subject_id    BIGINT,
  surface       VARCHAR(30),            -- D-19 카탈로그 재사용
  session_id    UUID,
  acq_source    VARCHAR(40),            -- 유입 귀속 스탬프 (§6)
  props         JSONB DEFAULT '{}',     -- dwell_ms, position, query, result_count, ward
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_events_subject ON app_events (subject_type, subject_id, created_at);
CREATE INDEX idx_events_user    ON app_events (user_id, created_at);
CREATE INDEX idx_events_type_at ON app_events (event_type, created_at);
```

퍼널 8종은 `event_type`의 부분집합일 뿐이다. 010 #5의 일별 롤업 잡은 그대로 성립한다. **추가는 컬럼 몇 개와 인덱스 3개** — L급 항목의 규모는 변하지 않는다.

### 3-3. 검색 로그 — 공급 영업의 조준경

`event_type='search'` + `props.query` + `props.result_count` 를 같은 파이프라인에 적재하면 **"결과 0건 검색어 상위 N"** 을 뽑을 수 있다.

**판단**: 이것은 단순 로그가 아니라 **"수요는 있는데 공급이 없는 품목"의 직접 관측**이다. 010 §7-1이 "공급 0은 코드로 못 푼다"고 한 영역에서, 코드가 **무엇을 모아올지 정해주는** 유일한 기여다. 필드 에이전트 재가동 시 타깃 품목 리스트의 데이터 소스로 지정할 것.

## §4. L1 — 매물: 생애주기·추적·모니터링

> **판정**: 현재 SGR 매물은 **"상태 없는 레코드"** 다(**V-5**). 등록되면 존재하고 삭제되면 사라질 뿐, 그 사이에 무슨 일이 있었는지 남기는 구조가 없다.

통상 매매사이트가 실제로 돌리는 모니터링은 6계층이다.

### 4-1. 계층 ① 생애주기 — 상태 기계

```
DRAFT → ACTIVE ⇄ RESERVED → SOLD
           ↓        ↓
        HIDDEN   (해제)
           ↓
        EXPIRED (자동, 미갱신 30일)
           ↓
        BLOCKED (운영 조치) / DELETED (사용자)
```

**`RESERVED`(예약중)를 별도 상태로 두는 것이 베트남 맥락에서 특히 중요하다.** 흥정이 기본값인 시장에서 "이거 아직 있나요?"가 문의의 대다수를 차지하며, 예약 표시는 헛문의를 줄이고 판매자 부담을 낮춘다. 010이 식별한 `B-STALE`(판매 완료 매물 방치)의 직접 해법이기도 하다.

**`EXPIRED` 자동 만료는 재고 신선도의 유일한 자동 장치**이며, 삭제가 아니라 만료여야 한다 — 판매자가 되살릴 수 있어야 공급이 보존된다.

```sql
CREATE TABLE listing_state_log (
  listing_id BIGINT, from_state VARCHAR(12), to_state VARCHAR(12),
  actor_type VARCHAR(10),  -- 'user'|'admin'|'system'
  actor_id BIGINT, reason VARCHAR(40), created_at TIMESTAMPTZ
);
CREATE TABLE listing_price_log (
  listing_id BIGINT, old_price BIGINT, new_price BIGINT, created_at TIMESTAMPTZ
);
-- 끌올은 listings.refreshed_at + 카운터로 충분
```

**이 이력 없이는 계산 불가능한 것**: 매물 문의 전환율 · 거래 전환율 · 첫 문의까지 시간 · 재고 신선도 · 끌올 어뷰징 → **즉 §6의 유동성 지표 전부.**

### 4-2. 가격 이력의 3가지 용도

1. **가격 인하 알림** — 찜한 매물 인하 시 알림. 당근이 운영하는 기능이며 #18과 같은 발송 인프라를 쓴다. 흥정이 기본값인 시장에서 재방문 유도력이 크다
2. **미끼가 탐지**(`B-BAIT-PRICE`) — 낮은 가격으로 문의를 모은 뒤 인상하는 패턴이 로그에 남는다
3. **시세 산출의 원료** — §4-4 이상치 탐지의 기준선

### 4-3. 계층 ② 동일성 추적 — "같은 물건인가"

| 지문 | 방법 | 용도 |
|---|---|---|
| 이미지 | perceptual hash (pHash/dHash) — 리사이즈·재압축·경미한 크롭에 강함 | 사진 재사용 탐지 |
| 텍스트 | 정규화(#17 함수 재사용) + simhash/shingle | 문구 재사용 탐지 |

**010과의 관계**: 010은 pHash를 L2(파일럿 4~8주 후)로 유보했다. **판단 — 판정은 L2로 미루되, 지문 산출·저장은 지금 시작해야 한다.** 파일럿 기간의 지문을 남기지 않으면 L2 시점에 **비교할 과거가 없다.** 등록 파이프라인에 함수 하나 추가 수준(S~M)이고, 판정 로직 없이 인덱스만 쌓아도 손해가 없다(M3).

**세 가지 패턴**:

| 패턴 | 조건 | 의미 |
|---|---|---|
| 사진 도용 (`S-PHOTO-THEFT`) | 동일 지문 · **다른 계정** · 원본 선등록 | 판매자 피해 |
| 재등록 어뷰징 | 동일 지문 · 동일 계정 · 삭제 후 재등록 반복 | 끌올 회피, 노출 독점 |
| **물품 순환** ★ | 동일 지문 · **여러 계정을 시간차로 순환** | **업자 위장 또는 도난품 유통** |

**판단 — ★가 오토바이 마켓의 핵심이다.** 같은 바이크가 3개월 새 3개 계정을 거쳐 재판매되면 둘 중 하나다. 개별 매물 심사로는 절대 잡히지 않고 **지문 이력이 있어야만 보인다.** 업계 실무의 표현대로, 사기는 계정 간 패턴에 살며 같은 사진 세트가 여러 이름·여러 지역에서 돌고 있음을 알아야 명백해진다(M2).

**오탐 주의**: 오토바이는 동일 모델·색상 사진이 원래 비슷하고, 제조사 카탈로그 이미지를 쓰면 완전 일치한다. 따라서 ① 지문 일치는 단독 근거 불가 — 계정·시간·지역 축과 결합 ② 카탈로그 이미지 화이트리스트 필요 ③ 임계값은 실측 전 확정 금지.

### 4-4. 계층 ③ 이상 신호 탐지

업계에서 정리된 사기 매물의 전형적 신호는 **시세를 크게 밑도는 가격, 첫 메시지부터 앱 밖 유도, 추적 불가능한 방식의 선입금 요구, 여러 계정·지역에 걸친 이미지·문구 재사용, 이력 없는 신규 계정, 대면·검증 거부**다.

| 신호 | SGR 탐지 가능성 | 담당 |
|---|---|---|
| 시세 이하 가격 | 카테고리 중앙값 대비 — **가능** | #39 |
| 앱 밖 유도 | 본문 Zalo/전화 패턴 — **가능** | #22 확장 |
| 선입금 요구 | 본문 키워드(chuyển khoản trước 등) — **가능** | #22 확장 |
| 이미지·문구 재사용 | 지문 — **가능** | #38 |
| 신규·빈약 계정 | 가입 경과일 + 매물 수 — **가능** | #39 |
| 대면·검증 거부 | 채팅 분석 — **비범위** | — |

**판단**: 6개 중 5개가 **이미 가진 데이터로 탐지 가능**하다. 새로 필요한 것은 탐지기가 아니라 **신호를 하나의 점수로 모으는 자리**다.

**시세 이상치의 단계적 접근** (매물 213건 국면):

| 단계 | 기준선 | 필요 표본 |
|---|---|---|
| v0 (파일럿) | 카테고리 중앙값 대비 편차 | 카테고리당 20건 |
| v1 (전면) | 카테고리 × 모델명(정규화) 중앙값 | 모델당 10건 |
| v2 | + 연식·주행거리 보정 | 수백 건 |

표본이 적을 때 중앙값은 불안정하므로 **표본 미달 카테고리는 아예 경보를 내지 않는 것**이 정답이다.

**위험 점수 — 판정이 아니라 정렬**:
```
risk_score = w1·(가격 이상도) + w2·(계정 신규도) + w3·(지문 재사용)
           + w4·(연락처 노출) + w5·(금칙어 근접)
```
**용도는 오직 하나 — 010 #3 검수 큐의 정렬 가중치.** 자동 숨김·차단 금지(M1). 가중치는 하드코딩(B2).

### 4-5. 계층 ④ 판매자 행동 — 업자 식별

| 신호 | 임계 예시 |
|---|---|
| 등록 속도 | 주 N건 이상 지속 |
| 동일 모델 반복 | 같은 모델 3건 이상 동시 보유 |
| 다지역 게재 | 여러 구에 동일 매물 |
| 회전율 | 등록→판매 주기가 짧고 규칙적 |
| 사업자 어휘 | "bảo hành"(보증), "trả góp"(할부) 등 |

한국 중고 플랫폼에서도 동일 상품 다량 판매·여러 동네 게재는 **전문판매자(업자) 패턴 감지 대상**으로 다뤄진다.

**판단 — SGR은 업자를 배제하지 말고 라벨링해야 한다.** 당근 모델(전문판매자 제재)의 복제는 틀렸다. 근거 3가지:

1. **공급이 병목이다.** 213건 중 188건이 단일 계정인 상황에서 대량 등록자를 쫓아내는 것은 자해다
2. **베트남 오토바이 중고 시장은 원래 딜러 중심**이다. Chợ Tốt도 업자와 개인이 공존한다. 개인만 남기는 것은 시장 구조와 싸우는 일이다
3. **문제는 업자가 아니라 위장이다.** 구매자가 상대가 업자임을 알고 거래하면 문제없다. 모르고 "개인 급매"인 줄 알았다가 딜러였을 때 신뢰가 깨진다

**→ 정답은 "업자 후보 플래그 → 비즈 프로필 전환 유도".** 배제가 아니라 **양성화**이며, 그대로 **B2B 수익 경로**로 연결된다. 경쟁자가 규제 대상으로 보는 것을 SGR은 고객으로 본다.

### 4-6. 계층 ⑤ 서류·명의 추적 — 오토바이 특화

#### 제도적 사실 (법무 확인 L-6)

§1-5 참조. 공증 매매계약 → 번호판·등록증 회수 → **30일 내 신규 등록**, 미이행 시 과태료.

#### ① 서류 상태 = 가격·위험의 1차 변수

| 필드 | 값 |
|---|---|
| `paper_status` | 등록증 보유(명의 일치) / 등록증 보유(**명의 불일치**) / 미보유 / 미확인 |
| `plate_province` | 번호판 등록 지역 (타지 번호판은 이전 비용·절차 차이) |

**명의 불일치**(현 소유자와 등록증 명의가 다름 — 이전 거래에서 이전을 안 한 차량)가 특히 중요하다. 베트남 중고 시장에 흔하며, 구매자가 나중에 이전을 못 하거나 추가 비용을 떠안는 분쟁의 원천이다.

**강제 입력이 아니라 선택 표시**로 둔다(A4). 미기재 매물은 랭킹 품질 항에서 감점(#19). 010이 "컨디션 필드 후순위"로 판정한 것과 성격이 다르다 — **편의 정보가 아니라 위험 신호**다.

#### ② `deal_complete`는 거래의 1단계다

```
문의 → 약속 → 대면·인수도 → [SGR이 현재 아는 끝]
                              ↓
              공증 매매계약 → 번호판·등록증 회수 → 30일 내 신규 등록
                              ↑
                    [실제 거래의 끝 — 여기서 분쟁이 터진다]
```

§6-4 퍼널에 **12단계(명의이전 완료)** 를 추가한다. 후기를 대면 직후에 받으면 "그때는 좋았는데 서류가 안 넘어왔다"를 못 잡는다 — 별점 신뢰도의 문제다.

#### ③ 30일 기한 = 차별화 기회

- 거래 신고 시 **명의이전 체크리스트** 제공 (필요 서류·절차·기한·예상 비용)
- **D+7 / D+25 리마인더** (기존 FCM)
- 완료 확인 → 양측 신뢰 지표 반영

**판단**: 010이 규정한 SGR의 차별화 방향 — "또 하나의 마켓플레이스가 아니라 **신뢰 인프라**" — 의 가장 구체적이고 저비용인 실현이다. 코드는 알림 2건과 정적 체크리스트 화면 1개(S~M). **Chợ Tốt이 하지 않는 영역이다.**

#### ④ 도난 차량 감시 — 내부 watchlist부터

| 단계 | 방법 | 판정 |
|---|---|---|
| v0 | 도난 제보(`STOLEN_GOODS` 신고) → 내부 watchlist(번호판 일부·특징) → 신규 매물 대조 경보 | **[전면] 채택** |
| v1 | 지문 순환 패턴과 교차 | [P2] |
| ✗ | 차대번호(VIN)·경찰 DB 연동 | **비범위** — 정부 데이터 접근 리스크(UDI 판단과 동일 논리) |

**주의(L-7)**: 미확정 혐의 기반 거래 제약이므로 **경보만, 자동 차단 금지**(M1). 삭제는 반드시 사람 판정 + 이의제기 경로(010 #2) 유지.

### 4-7. 계층 ⑥ 거래 후 추적 — 자기신고 누락 보정

## §5. L2 — 발견: 검색·랭킹·매칭

### 5-1. [P0] 베트남어 검색 정규화 — 볼륨 문제가 아니다

**사실**: 010은 §1~§8 전체에서 검색을 한 번도 다루지 않았다. 현재 구현 방식은 **V-4**.

**판단 — 010 최대의 맹점.** 근거 3가지:

1. **입력 현실**: 베트남 사용자는 모바일에서 성조·다이어크리틱 없이 입력하는 것이 매우 흔하다("xe máy"→"xe may", "Hà Nội"→"Ha Noi"). PostgreSQL `unaccent`가 표준 해법이나 **기본 rules 파일은 베트남어 전체 문자(ơ, ư, đ, 성조 조합)를 완전히 커버하지 못해** 베트남 개발 관행상 rules 보강 또는 전용 변환 함수 추가가 통용된다. `đ→d` 매핑이 특히 빠지기 쉽다
2. **볼륨 무관성**: 매물 20건이어도 "xe may"가 0건이면 죽은 앱이다. **파일럿 데이터를 기다릴 이유가 전혀 없다**
3. **양방향 필요**: 질의뿐 아니라 저장 텍스트도 정규화해야 한다(판매자도 무성조로 등록한다). `title_norm` 컬럼 + 트리거 + pg_trgm GIN

**부가 효과**: 이 함수는 §7 금칙어 매칭(#22)과 §4-3 텍스트 지문(#38)에 재사용되어 **무성조 우회 입력까지 자동으로 잡는다.** 한 번 만들어 세 곳에 쓴다.

### 5-2. [P1] 랭킹 v1 — 010 정합성 결함의 해소

**판단**: **감점은 점수가 있어야 성립한다.** 현재가 최신순이면 L2 시점에 급조하게 된다. 랭킹 v1은 ML이 아니라 규칙식이며 데이터가 필요 없다:

```
score = freshness_decay(refreshed_at, 반감기 72h)
      × quality(사진 수 · 설명 길이 · phone_verified · paper_status 기재 가산)
      × trust_penalty(L2 플래그 감산 — 초기 계수 1.0 = 무효과)
```

파일럿 중엔 `trust_penalty=1.0`으로 배포해 **최신순과 거의 동일하게 동작**시키고, L2 진입 시 계수만 조정한다. **L2가 "새 시스템 구축"이 아니라 "상수 변경"이 된다.**

### 5-3. [P1] 키워드 알림 — 공급 희소 국면의 최고 효율 매칭

**사실**: 010 §7-1 "공급 0은 어떤 코드로도 못 푼다."

**판단 — 절반만 맞다.** 코드는 공급을 만들지 못하지만 **희소한 공급을 수요와 매칭하는 효율은 코드가 결정한다.** 공급이 적을수록 키워드 알림의 한계가치는 **커진다**. 당근이 초기부터 핵심 유동성 장치로 운영한 기능이다.

파일럿 시나리오: 1개 구에 주 10건 등록. 우연히 노출될 확률은 낮지만, "Honda Cub"을 등록한 수요자 5명에게 즉시 FCM이 가면 **매물 1건당 문의 확률이 구조적으로 상승**한다. 파일럿 측정 대상의 **분모를 키우는 코드**다.

구현: `saved_keyword` 테이블 + 등록 후 아웃박스(D-5 선례) 매칭 + 기존 FCM. **신규 인프라 0.**

### 5-4. 조회 이력 기반 표출 — 단계별 판정

| 단계 | 기능 | 필요 데이터 | 판정 |
|---|---|---|---|
| a | 최근 본 매물 (1행) | 본인 이력만 | **[P1] 승격**(D-17 유보 해제) — per-user라 볼륨 무관. S |
| b | 카테고리 친화 부스트 | 본인 이력 2주+ | [P2] — 랭킹 v1에 항 추가로 예약 |
| c | 함께 본 매물 (공출현) | 전체 이력, 매물 수백+ | [P2] |
| d | ML 추천 | 수천 상호작용 | [P2 후반] — 010 기각 유지 |

**해당: #17(검색 정규화) · #18(키워드 알림) · #19(랭킹 v1) · #20(최근 본 매물)**

## §6. L3 — 분석: 유입·전환·유동성

### 6-1. 010 퍼널의 구조적 한계 3가지

| # | 한계 | 결과 |
|---|---|---|
| ① | **가입 이후만 본다** | 최대 이탈 구간인 설치→열람→가입→**Zalo 인증**이 안 보인다 |
| ② | **유입 출처가 없다** | 8단계가 채널 구분 없는 단일 평균값. "필드 영업으로 온 사용자와 지인 소개로 온 사용자 중 누가 거래하는가"를 못 답한다 = **성장 자원 배분 근거 0** |
| ③ | **전환의 종착점이 앱 밖** | C2C 거래는 만나서 끝난다. `deal_complete`는 자기신고이며 하한선일 뿐 |

**판단**: ②가 가장 심각하다. 유입 귀속은 **소급이 불가능**하다 — 파일럿 4~8주 동안 온 사용자가 어디서 왔는지는 그때 기록하지 않으면 영원히 알 수 없다(B1).

### 6-2. 유입 귀속 체계

| 채널 | 성격 | 귀속 방법 |
|---|---|---|
| 필드 에이전트 대면 등록 | 유료(인건비) | 에이전트별 `ref` 코드 |
| 지인 소개 | 무료·바이럴 | 초대 코드 |
| **매물 공유 링크**(Zalo/Facebook 그룹) | 무료·판매자 주도 | 공유 URL `ref` |
| 업체 매장 QR·포스터 | B2B 연계 | 업체별 `ref` |
| 앱스토어 자연 유입 | 무료 | 잔여(unattributed) |

**최소 구현**: ① 진입 URL `?ref=` 세션 캡처 ② 가입 시 `user.acquisition_source` **고정(first-touch, 불변)** ③ 이후 모든 이벤트에 `acq_source` 스탬프.

**Android**: Google Play **Install Referrer API**는 Play 스토어 앱이 노출하는 인터페이스로, 설치 전 클릭 링크의 `utm_*`·레퍼럴 코드를 설치 후 조회할 수 있게 한다. **3자 SDK 없이** 캠페인 귀속과 친구 추천 코드 추적이 가능하다. 베트남은 Android 우위라 이것만으로 실질 커버리지가 확보된다. → Capacitor 플러그인 가용성 **V-6**.

**iOS**: 지연 딥링크 귀속이 구조적으로 어렵다. **판단** — 웹 랜딩 초대 코드 수동 입력 폴백으로 처리하고 정확도 저하를 수용한다. iOS 비중이 낮은 시장에서 이것 때문에 3자 SDK를 도입하는 것은 A1 위반.

**명시 비범위**: AppsFlyer·Adjust·Firebase Analytics(PDPL 국외 이전 + 비용), **기기 핑거프린팅**(PDPL 위반 소지).

### 6-3. 공유·초대 루프 — 공급측 유입의 유일한 무료 채널

**판단**: 베트남 C2C의 실제 유통 경로는 앱 내 검색이 아니라 **Zalo·Facebook 그룹 공유**다. 판매자가 자기 매물을 그룹에 뿌리는 행위에 `ref`를 붙이면:

- 판매자 주도 유입이 **측정 가능**해진다
- 매물 공유가 곧 사용자 획득 → **공급이 수요를 데려오는 루프**. 010 §7-1의 "공급 0"에 코드가 기여하는 두 번째 지점(첫 번째는 §5-3 키워드 알림)
- K-factor(초대당 신규 가입) 산출 가능

**게이미피케이션 연계**: SRE 스펙의 "친구 초대 1명 가입+활성 → 20 GC" 보상은 **이 귀속 체계 없이는 지급 판정 자체가 불가능**하다. #31은 게이미피케이션의 선행 인프라이기도 하다. 단 v1은 **측정만**, 보상 지급은 어뷰징 가드 확정 후.

## §7. L4 — 운영: 설정·계정

### 7-1. 벤치마크 대조

마켓플레이스 어드민 실무 표준은 **5도메인** — 사용자 관리, 거래 감독, 콘텐츠·매물 모더레이션, 재무 통제, 플랫폼 설정 — 이며, **역할 기반 접근 제어(RBAC)는 타협 불가**이고 단일 슈퍼유저 계정은 어떤 규모에서든 보안·컴플라이언스 실패로 간주된다. 국내 실무 문헌이 경고하는 전형적 실패는 **"처음엔 간단한 CRUD였던 어드민이 어느 순간 배포 없이는 컬럼 하나도 못 바꾸는 운영 병목이 되는 것"** 이다.

| 도메인 | SGR 현황 | 판정 |
|---|---|---|
| ① 모더레이션 | 도구 완성(W4) + §8 | ✅ |
| ② 거래 감독 | GMV + 스냅샷(#4) + 퍼널(#5) + §4 | ✅ |
| ③ 사용자·판매자 관리 | 제재·이력·티켓 완성 | ✅ |
| ④ 재무 통제 | 광고 수동 결제(P-6c) | ✅ 010 판단 유지 |
| ⑤ **플랫폼 설정 + 계정 체계** | **결손 2 + 확인 필요 3** | ⚠️ |

### 7-2. [P0] 금칙어의 배포 종속 — 증거는 010 안에 있었다

**사실**: 010 §5 완료 목록 "Q-1 금칙어 매물 확대 `f8fa9ff`" — 금칙어 확대가 **코드 커밋**이었다.

**판단**: 파일럿의 목적이 "배우는 것"이라면 배울 것 중 하나가 **현지 사기 어휘**다. 베트남어 선입금 유도 변형 표현은 파일럿 중 실시간으로 발견될 것이고, 발견→차단 지연이 배포 주기와 같아서는 안 된다. 금칙어는 임계값 상수(하드코딩이 옳다)와 성격이 다른 **운영 데이터**다(B2).

### 7-3. [P0] 공지·배너 부재 (V-7)

**판단**: 파일럿 운영 시나리오를 구체화하면 자명하다 — ① 점검 공지 ② "주말 ○○구 안전거래 이벤트" ③ **사기 주의보** ④ 정책 변경 고지(법무 통보 의무 직결). 넷 중 하나라도 배포로 처리하면 §7-1의 병목 패턴이다.

최소 구현: `announcement(title, body, type, starts_at, ends_at, active)` + 홈 배너 1슬롯 + 공지 목록. **풀 CMS 아님.**

### 7-4. [P1] 어드민 계정 개별화 — RBAC의 최소 형태

**판단**: "RBAC 필수"를 현 규모(운영 0.5~2인)에 그대로 적용하면 과설계다. 그러나 **하한선**은 있다: ① 1인 1계정(공유 금지) ② 모든 변경성 액션에 `actor_id` ③ 역할 2종(SUPER: 설정·계정 / OPS: 신고·검수·공지).

근거: 010 §3-2의 신고 폐루프 감사 증적은 **"누가 판정했는가"** 가 있어야 이의제기 분쟁에서 의미가 있고, 인력이 2인이 되는 순간(010 §7-3에 이미 예정) 소급 도입은 **기존 로그 전체의 행위자 불명**을 남긴다.

**해당: #22(금칙어) · #23(공지·배너) · #24(계정 개별화)**

## §8. L5 — 이슈: 4관점 사고 처리

### 8-1. 판정: 도구는 있고 체계가 없다

010 §3-2의 신고 폐루프는 잘 설계됐으나 **하나의 전제 위에 서 있다 — "문제는 신고 버튼을 통해 들어온다."** 이 전제가 4관점 중 절반에서 깨진다.

실제 유입은 4경로다: ① 신고 버튼 ② 고객문의 티켓 ③ 자동 탐지·경보 ④ **외부**(규제기관·앱스토어 리뷰·Zalo/Facebook·**영업 담당 개인 연락**).

**광고주는 신고 버튼을 누르지 않는다. 계약 상대방에게 전화한다.** 그 순간 이슈는 시스템 밖으로 새고 ① 처리 이력 무기록 ② 담당자 부재 시 정지 ③ 재발 통계 불가 ④ 분쟁 시 증적 0이라는 4중 결함이 발생한다.

### 8-3. 사고 생애주기 5단계

```
[접수] → [분류] → [처리] → [종결·통보] → [학습]
 4채널    심각도+정렬   조치+권한    결과코드+양측통보   주간 유형별 집계
  #25     010 #3 재사용  기존 도구 ○   010 #1 + #26      #26 종속
```

| 단계 | 010 현황 | 보강 |
|---|---|---|
| 접수 | 신고 큐 1채널 | **#25** — 4채널을 `source`로 구분해 단일 큐 수렴(B3) |
| 분류 | #3 우선순위 정렬(완료) | SEV1~4를 #3 가중치에 병합 — **신규 코드 아님** |
| 처리 | 도구 완성(W4) | 유형별 조치 매트릭스 = SOP-1 |
| 종결·통보 | #1 신고자 통보 | **#26** 결과 코드 없이 종결 불가(B4) |
| 학습 | **없음** | **#26** 주간 유형별 집계 |

**판단**: 가운데 3개는 010이 이미 8할을 해뒀다. 진짜 구멍은 **양 끝 — 접수와 학습**이다.

### 8-4. 법규 압력 (법무 확인)

2차 출처에 따르면 Decree 85/2021/ND-CP(52/2013 개정, 2022-01-01 시행)는 전자상거래 거래 플랫폼 사업자에게 ① 법령 위반 관련 규제당국 정보 요청에 **24시간 내 응답**할 담당 창구 지정 ② 다자 거래에서 **소비자 불만 접수 창구** 역할 ③ 주문 기록 보존 ④ 미조치 손해에 대한 **연대 배상 책임**을 부과한다. 법령 원문 인용에는 산업무역부 포털(`online.gov.vn`)을 통한 불만·신고·분쟁 정보의 접수 및 회신 체계도 언급된다.

**판단**: L-1(SGR이 "sàn giao dịch TMĐT"에 해당하는가)이 긍정이면 #25·#27은 **권장이 아니라 컴플라이언스 항목**으로 격상되며 파일럿 개시 전 필수가 된다. 파일럿을 1개 구로 좁힌 것이 법적 노출을 줄이지는 않는다 — **규모가 아니라 성격의 문제**다.

### 8-5. 파트너 보전(make-good) 정책

**문제**: #10으로 광고가 재개되면, 트래픽이 0에 가까운 파일럿에서 "약속한 노출이 안 나왔다"는 항의가 구조적으로 발생한다.

**업계 표준**: 광고 보전 조항은 통상 **과소 노출이 광고주 귀책(소재 지연·부적합·정책 미준수)인 경우, 특정 일·주 단위 분배 미달인 경우** 등을 보전 대상에서 제외한다.

| 상황 | 처리 |
|---|---|
| 플랫폼 귀책 미노출 | **기간 연장 보전** — 미노출 일수 × 1.5배 (현금 환불 아님) |
| 노출됐으나 성과 미달 | 보전 없음. 리포트 + 지면·소재 조정 제안 |
| 광고주 귀책 | 보전 없음 |
| 중도 해지 | 잔여 일할 크레딧(차기 차감), 현금은 대표 승인 건별 |

**코드는 최소**(계약 기간 연장 필드 + 감사 로그). **본체는 정책 문서이며 첫 광고주 계약서에 들어가야 한다** — 계약 후에 만들면 협상력이 0이다.

**해당: #25(통합 인테이크) · #26(유형·결과 코드) · #27(업체 창구) · #28(보전) · #29(오토바이 신고 사유)**

## §14. 결론 — 대표 보고용 7문장

1. **010의 절제는 옳고 유지한다** — ML 추천 기각, 계측 우선, 자동 차단 금지, 신규 컨테이너 금지. 지금 추천엔진을 만들면 시연 계정 188건을 학습한 엔진이 나온다.

2. **그러나 010은 "지금 안 만든다"와 "원료를 안 남긴다"를 혼동했다** — 이벤트 스키마를 퍼널 카운터로 좁게 잡아 미래 랭킹·추천·분석의 파이프라인을 끊었다. 공수 델타는 S인데 **소급 복구는 불가능**하다.

3. **매물이 "상태 없는 레코드"라 유동성 측정 자체가 불가능하다** — 등록과 삭제 사이에 무슨 일이 있었는지 기록이 없어, 파일럿의 유일한 판정 지표인 "등록 후 N일 내 전환율"을 계산할 수 없다.

4. **데이터가 필요 없는 엔진 3종이 누락됐다** — 베트남어 무성조 검색 정규화(볼륨 무관한 언어 필수 기능), 키워드 알림(공급이 희소할수록 가치가 커지는 매칭 도구), 규칙 기반 랭킹 v1(L2 감점이 성립하려면 어차피 필요한 선행 조건). 정규화 함수 하나는 검색·금칙어·지문 세 곳에 재사용된다.

5. **4관점 중 파트너가 통째로 비어 있다** — 광고주는 신고 버튼을 안 누르고 영업 담당에게 전화하며, 그 순간 이슈가 시스템 밖으로 샌다. **#27(업체 창구)은 #10(광고 재개)보다 먼저여야 한다.**

6. **업자는 배제가 아니라 라벨링이 답이다** — 공급 병목 상황에서 대량 등록자를 쫓아내는 것은 자해이고 베트남 오토바이 시장은 원래 딜러 중심이다. 문제는 업자가 아니라 **위장**이며, 양성화는 그대로 B2B 수익 경로가 된다.

7. **베트남 오토바이 거래는 대면에서 끝나지 않는다** — 공증 매매계약·번호판 회수·30일 내 신규 등록이라는 법정 절차가 존재한다. 체크리스트 1화면 + 리마인더 2건(규모 S~M)으로 "또 하나의 마켓플레이스"가 아니라 **"거래를 끝까지 책임지는 신뢰 인프라"** 가 실물이 된다. 경쟁자가 하지 않는 영역이다.

**대표 결정이 필요한 실질 3건**: **D-23**(이벤트 파이프라인을 상호작용 로그로) · **D-30**(유입 귀속 방식) · **D-31**(파일럿 유동성 목표선). 나머지 10건은 권고안대로 진행 가능하며, **#17(검색 정규화)·#36(매물 상태 기계)·#23(공지)·#29(도난 신고사유)는 결정 없이 즉시 착수**할 수 있다.
