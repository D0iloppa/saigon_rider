# 당근 비교 문서 기반 갭 트리아지 보고서

## 1. 개요

- **출처 문서**: `docs/saigon_rider_daangn_feature_page_comparison_2026-09-09 copy.pdf` (40쪽, Saigon Rider ↔ 한국 당근/Karrot 기능 비교, 89개 비교 항목)
- **조사일**: 2026-09-09
- **기준 커밋**: `8c5c7493` (feat(market): add guided manual QR transactions)
- **범위 확정 경위**: 대표가 원 문서(89개 항목) 전체를 "개선 작업 착수"로 지시했으나, 실행 방식으로 "트리아지 리포트 선행 → 승인 후 구현"을 선택. 89개 중 우선 검토 대상으로 4개 영역(거래안전·신뢰 / AI·사업자도구)을 지정했고, 이번 조사는 그 영역에서 파생된 10개 세부 항목(F018, F019, F033, F034, F049, F050, F052, F054, F061, F062)을 대상으로 함. 두 명의 read-only 분석 워커(워커 A: 거래안전·신뢰, 워커 B: AI·사업자도구)가 정적 코드 조사를 수행했고, 본 보고서는 그 결과를 종합한 것.
- **이 보고서가 아닌 것**:
  - 출시 승인 문서가 아니다. 실제 구현 착수는 대표 승인 이후.
  - 당근 대비 UX 우열을 매기는 점수표가 아니다. "당근에 있다/없다"가 아니라 "우리 코드에 실제로 무엇이 있고 무엇이 없는지"를 확인한 것.
  - 89개 전체에 대한 결론이 아니다. 이번에 다룬 것은 대표가 선택한 4개 우선 영역에서 나온 10개 항목뿐이며, 나머지 항목은 미조사.

## 2. 먼저 정정할 사실 3가지

1. **F033 (수동 QR 거래)**: "백엔드만 완료·프론트 미완"이라는 인식은 틀렸다. 오늘 커밋 `8c5c7493`으로 백엔드(`backend/app/routers/market.py`의 `report_marketplace_payment`/`confirm_marketplace_payment`/`get_marketplace_transaction`, `backend/app/routers/dm.py`의 `register_payment_qr`/`get_payment_qr_image`)와 프론트(`frontend/src/api/dm.ts`의 `registerMarketplacePaymentQr`/`fetchMarketplacePaymentQr`/`reportMarketplacePayment`, `DmDetail.tsx:1175` 렌더링), 테스트(`backend/app/tests/test_dm_payment_qr.py`, `backend/app/tests/test_marketplace_transaction.py`)까지 전부 병합 완료됐다. 남은 것은 어드민 콘솔의 분쟁 처리 화면뿐이다.

2. **F050 (피드 게시물/댓글·그룹 DM 신고)**: "미구현"이 아니다. 백엔드 라우트는 이미 존재한다 — 그룹 메시지 신고 `backend/app/routers/dm.py:1367`, 피드 게시물 신고 `backend/app/routers/feed.py:687`, 피드 댓글 신고 `backend/app/routers/feed.py:727`. 실제 격차는 프론트가 이 라우트를 호출하는 wrapper를 만들지 않아 화면에서 신고 진입점 자체가 없는 **배선 누락**이다(`frontend/src/api/feed.ts`에 report 함수 없음, `FeedDetail.tsx`에 "report" 문자열 자체 부재).

3. **F049 (매너온도)**: "노출 안 됨"이 아니다. 계산(`backend/app/routers/market.py:114 _recompute_manner_temp()`, `User.manner_temp`)은 이미 커밋돼 있고, 매물상세(`MarketDetail.tsx:362`)와 본인 프로필(`ProfileMain.tsx:413`)에는 `<TrustTierChip>`(원값이 아닌 티어 매핑, `frontend/src/lib/trustTier.ts`)로 이미 노출 중이다. 타 사용자 공개 프로필(`UserProfile.tsx`)에만 미노출인데, 이는 우연한 누락이 아니라 계약 테스트 `frontend/src/pages/profile/userProfileDiscoverability.contract.test.mjs:16`(`assert.doesNotMatch(profile, /mannerTemp|manner score/i)`)가 강제하는 **의도적 설계 결정**이다.

## 3. 항목별 판정표 (10개)

### F033 — 수동 QR 거래 (안전결제 가이드형)
- **현재 코드 상태**: 완료. DB `database/init/232_marketplace_transactions.sql`(`marketplace_transactions`, payment_status: AWAITING_PAYMENT→PAYMENT_REPORTED→PAYMENT_CONFIRMED), 백엔드 라우트·프론트 API·UI 렌더링·테스트 전부 커밋 8c5c7493에 포함.
- **실제 격차**: 어드민 콘솔에 이 거래 상태를 조회/개입하는 분쟁 처리 화면이 없음.
- **재사용 가능한 기반**: 거래 상태기계·payment_status 전이 로그가 이미 있어 어드민 조회 화면은 조회/전이 API만 얹으면 됨.
- **공수**: S~M (어드민 화면).
- **권고**: **구현 (후속)** — 기능 자체는 완료 상태이므로 남은 어드민 분쟁 처리 화면만 마무리하면 됨.

### F034 — 에스크로(안전결제 자금예치)
- **현재 코드 상태**: 미발견. 232 SQL 주석이 "인간 확인 기록일 뿐 PSP 검증을 주장하지 않는다"고 명시하며 자금 예치를 명시적으로 부정. 소비자 P2P 결제 수납 자체 없음.
- **실제 격차**: 자금 예치·정산·환불/분쟁 처리 로직 전무. Toss 연동(`backend/app/services/ad_payments/rails/toss_card.py`, `backend/app/routers/ad_contract.py`)은 광고비 전용.
- **재사용 가능한 기반**: Toss 레일의 체크아웃/웹훅 패턴은 구조적으로만 참고 가능(ad_contract에 결합돼 있어 marketplace_transaction 연결은 신규 설계 필요).
- **공수**: L (PSP 연동, 예치금 원장, 정산 배치, 환불/분쟁).
- **권고**: **보류** — 베트남 소비자 자금 예치는 규제/라이선스 사안이라 코드 판단만으로 결정 불가. 법적 검토가 선행조건.

### F052 — 사기계좌 조회/탐지
- **현재 코드 상태**: 사기계좌 조회 자체는 미발견. 존재하는 것은 `backend/app/services/listing_risk.py`의 `risk_score_sql()`(가격이상도·계정신규도·이미지지문재사용·연락처노출·선입금유도문구 근접도)뿐이며, 검수 큐 정렬 가중치로만 쓰이고 자동 차단은 없음("탐지 ≠ 차단" 주석 명시).
- **실제 격차**: 계좌 단위 조회/탐지 로직, 은행 API 연동 전무. 게다가 베트남에 사기계좌 조회 가능한 데이터 소스가 존재하는지 자체가 불명(한국 '더치트' 유사 서비스 존재 미확인).
- **재사용 가능한 기반**: risk 신호 프레임워크에 계좌 신호 편입 가능, `register_payment_qr` 시점이 명확한 후킹 지점.
- **공수**: L.
- **권고**: **보류 (리서치 선행)** — 데이터 소스 존재 여부 확인이 먼저. 변형 대안으로 QR 등록/열람 시점 경고 문구·신고 연계(공수 S)를 병기.

### F049 — 매너온도 공개 노출
- **현재 코드 상태**: 계산·티어칩 기반은 완료. 매물상세·본인 프로필에는 이미 노출. 공개 타 사용자 프로필만 계약 테스트로 노출이 금지돼 있음.
- **실제 격차**: 공개 프로필(`UserProfile.tsx`)에 티어칩 없음. 전화인증·응답률 지표 노출 여부는 이번 탐색 범위 밖(미확인).
- **재사용 가능한 기반**: `<TrustTierChip>` 컴포넌트, `trustTier.ts` 매핑 로직 그대로 재사용 가능.
- **공수**: S (티어칩만) / M (전화인증·응답률 포함 확장).
- **권고**: **구현 (조건부)** — 공개 프로필 티어칩 추가는 코드상 S로 간단하나, 현재 계약 테스트가 노출을 명시적으로 금지하고 있어 원 설계 의도를 대표에게 확인한 뒤 진행.

### F050 — 신고·차단 (피드 게시물/댓글, 그룹 DM 메시지)
- **현재 코드 상태**: 백엔드 라우트 존재(`dm.py:1367`, `feed.py:687`, `feed.py:727`). 매물/사용자/1:1 DM/업체 프로필/업체 후기 신고와 차단/해제는 이미 프론트까지 연결 완료.
- **실제 격차**: 그룹 메시지·피드 게시물·피드 댓글 3곳만 프론트 wrapper와 UI 진입점이 없음.
- **재사용 가능한 기반**: 신고 사유 바텀시트, 중복신고 가드(`_report_guard.py`)가 이미 있어 그대로 재사용 가능.
- **공수**: S (화면 3곳, 반나절~1일급).
- **권고**: **구현 (최우선)** — 백엔드가 이미 있어 프론트 wrapper + 신고 시트 연결만. 안전 기능 누락이라 방치 비용이 큼.

### F054 — 고객센터 AI(챗봇/RAG)
- **현재 코드 상태**: 완전 미구현. 백엔드 전체에 LLM 연동 코드 0건(openai/anthropic/gpt-/claude- grep 전부 0). 현재 지원 구조는 정적/수동 티켓(`frontend/src/pages/settings/CustomerSupport.tsx`)과 정적 FAQ 아코디언(`frontend/src/pages/faq/FaqList.tsx`, 텍스트 검색 UI 없음), 어드민 수동 CRUD(`backend/app/routers/admin_api/cms.py`).
- **실제 격차**: LLM 연동, 임베딩/RAG, 가드레일, 출처 표기 UI 전부 신규.
- **재사용 가능한 기반**: FAQ CMS 콘텐츠를 RAG 소스로, 티켓 시스템을 "AI 우선 응답→미해결 시 사람 인계" 구조로 확장 가능.
- **공수**: L.
- **권고**: **보류** — 오답 시 정책 오안내 리스크가 크고 공수도 큼. 변형 대안으로 FAQ 텍스트 검색 추가(공수 S~M)를 병기.

### F018 — AI 판매글 자동작성(사진→텍스트)
- **현재 코드 상태**: 매물 등록 폼(`frontend/src/pages/market/MarketCreate.tsx`)에 이미지 업로드·초안 저장은 있으나 사진→텍스트 생성 로직 전무. LLM/vision 클라이언트가 백엔드 전체에 미발견(.env.example에도 없음, 있는 외부 키는 지도/번역/날씨/SMS/Toss뿐).
- **실제 격차**: LLM 연동 자체가 코드베이스에 전무 — "호출 추가"가 아니라 역량 신설 수준.
- **재사용 가능한 기반**: 이미지 업로드(contents 경유), 초안 저장 패턴, title/description 필드.
- **공수**: L.
- **권고**: **보류** — LLM 연동 자체가 코드베이스에 전무해 신규 역량 구축이 필요. 비용/키 관리 전례 없음.

### F019 — 사진 기반 예상가 제시
- **현재 코드 상태**: 별도 가격추정/카메라 진입 페이지 미발견. 가격 필터(`market.py:344-345`, `MarketSearch.tsx`)는 있으나 완료 거래 가격 통계 집계 로직은 미발견(탐색 범위: search_graph "price", market.py).
- **실제 격차**: 사진 인식이 F018 부재로 원천 불가. 게다가 Saigon Rider는 오토바이(모델·연식·주행거리 변수多)라 당근 폰 시세 모델을 그대로 이식 불가.
- **재사용 가능한 기반**: 가격 필터 UI/쿼리, category_id 분류는 "카테고리별 시세 범위 통계"로는 재사용 가능하나 사진 기반 추정과는 다른 근사치.
- **공수**: L.
- **권고**: **보류** — F018 의존 + 오토바이 도메인 특수성 + 시세 근거 데이터 축적 여부 미확인(완료 거래 건수 자체가 미집계).

### F061 — 가게 쿠폰
- **현재 코드 상태**: (a) 레거시 `CouponShop`은 RP/게임 경제 전용으로 완전 비활성 — `backend/app/tests/test_coupon_launch_gate.py`가 3개 라우트 404를 강제, `engine/alembic/versions/062_disable_internal_coupon_catalog.py`가 되돌리지 않는 정책으로 비활성화(2026-07-22), 프론트 `CouponShop.tsx`는 App.tsx 라우트 참조가 없는 고아 페이지. (b) 단골/팔로우 관계(`biz.py:1982-2072` add_follow/add_favorite)와 업체 소식(biz news CRUD)은 존재. 쿠폰 발행/사용 흐름은 전체 미발견(search_graph "coupon" 16건 전부 레거시).
- **실제 격차**: "사업자 발행→고객 사용" 쿠폰 도메인 모델(신규 테이블/상태기계) 전무.
- **재사용 가능한 기반**: follow/favorite 관계·카운트, biz news CRUD 패턴(승인·소유권 검증), 구조 참고용으로만 reward_redemption 발급-상환 상태기계.
- **공수**: M.
- **권고**: **구현 (후보)** — 단, 레거시 CouponShop(RP 보상)은 재사용 금지. 발급 주체 모델이 근본적으로 다르고 이미 비활성 확정된 시스템이므로 신규 설계 필요.

### F062 — 예약·견적·포장주문 (사업자 도구)
- **현재 코드 상태**: /biz 라우트 전반(가격표, 뉴스, 인증 등)은 갖춰져 있으나, 공개 프로필 CTA(`BizPublic.tsx:877-885`)에는 전화 문의(tel: 딥링크) 버튼만 있음. DM 시작·예약/견적 버튼 미발견(파일 전체 grep, message/createConversation 참조 없음). 약속(appointment) 시스템(`market.py:1740-2297`)은 개인 간 매물 거래 전용이지 사업자 도구 아님.
- **실제 격차**: 사업자용 예약/견적/포장주문 전무. 지금 CTA에 전화 버튼밖에 없어 고객 문의가 새고 있음.
- **재사용 가능한 기반**: market appointment 상태기계를 biz 문의로 일반화, DM `create_conversation`(`dm.py:510`)을 BizPublic CTA에 연결, 가격표를 견적 항목 선택 UI 기반으로 확장 가능.
- **공수**: 경량(공개 업체 프로필 CTA에 DM 진입 추가) M / 풀세트(캘린더·견적서·포장주문 결제) L.
- **권고**: **변형 구현** — 당근식 예약/견적/포장주문 풀세트가 아니라, 공개 업체 프로필 CTA에 DM 진입("문의하기") 추가하는 경량판부터.

## 5. 의사결정이 필요한 질문

1. **F049**: 공개 프로필에 매너온도(티어칩)를 노출해도 되는가? — 계약 테스트가 명시적으로 금지하는 설계 결정이라, 원래 왜 막았는지(프라이버시/악용 방지 등) 의도를 대표만 알 수 있고 코드 조사로는 복원 불가.
2. **F034**: 베트남에서 소비자 자금을 예치(에스크로)하는 것이 규제/라이선스상 허용되는가? — 이는 법적 판단 영역이라 코드 조사로 답할 수 없다.
3. **F052**: 베트남에 사기계좌 조회가 가능한 데이터 소스(공공/민간)가 존재하는가? — 국내 서비스 존재 여부 자체가 조사 범위 밖이라 대표/현지 채널(히엔 선생님 등) 확인이 필요.
4. **F018/F054**: LLM 연동(비용, 키 관리, 가드레일)을 신규 역량으로 도입할 것인가? — 이는 기술 판단을 넘어 예산·운영 정책 결정이라 코드 조사만으로 착수 여부를 정할 수 없다.
5. **F061**: 가게 쿠폰이 현금성(할인·환불 연계)을 가지는가? — 정산·회계 처리 방식에 따라 설계가 달라지므로, 사업 모델 상 현금성 여부는 대표 확인이 필요하다.

## 6. 검증 범위와 한계

- 이 보고서는 **정적 코드 확인**(라우트/모델/테스트/프론트 API wrapper 존재 여부 grep·search_graph 조사)에 기반한다. 실기기 실행, 로그인 세션, 실제 결제 플로우, 운영 DB 데이터, 배포된 빌드본 실행 검증은 수행하지 않았다.
- 각 워커가 "미발견"이라고 보고한 항목(예: F019의 가격 통계 집계 로직, F052의 사기계좌 데이터 소스, F034의 자금예치 로직)은 명시된 **탐색 범위 내에서 찾지 못했다는 뜻**이며, 코드베이스 전체에 절대 존재하지 않는다는 확정이 아니다. 특히 grep/search_graph 키워드가 실제 구현의 네이밍과 다르면 놓칠 수 있다.
- 어드민 콘솔(F033), 정산/회계 처리(F061), 실제 전화인증·응답률 노출 여부(F049)처럼 이번 워커들의 탐색 범위 밖에 있던 인접 영역은 별도 확인이 필요할 수 있다.

# 2차 라운드 — 나머지 "당근 확장" 9건 트리아지 (2026-09-09)

1차는 대표가 고른 4개 우선영역(10항목)만 다뤘다. 이 라운드는 **그때 트리아지조차 하지 않았던 당근 확장 9건**을 판정한다. `codebase-memory` MCP 연결 실패로 grep/find 기반 bounded search 를 썼다(그래프 조회 대비 커버리지 한계 있음).

## 결론 먼저 — 9건 중 6건은 폐기다

이 6건(F036 · F042 · F069 · F076 · F077+F078 · F079)은 **코드로 풀 문제가 아니라 시장 전제가 없는 문제**다. 한국 고유 인프라에 의존하거나, 애초에 당근 본체가 아닌 별도 사업부 제품이다:

- **F042 아파트 실거주 인증** — 핵심 메커니즘이 **정부24 등본 연동**이다. 베트남엔 등가물이 없다(hộ khẩu 는 지역별 전산화 수준이 다르고 공개 API 가 없다). 인증 수단이 없으면 "주민만 들어올 수 있다"는 이 기능의 유일한 가치가 성립하지 않는다.
- **F077+F078 부동산** — 집주인 인증은 **등기부등본**, 시세는 **국토부 실거래가 공개데이터** 전제다. 베트남 부동산 등기(핑크북)는 인민위원회·토지관리사무소 수기 처리가 많아 API 자동 검증이 불가능하고, 실거래가 공공데이터도 없다.
- **F069 POS 연동** — **원문 스스로 "당근도 MOU/단계적 추진 중, 완료 아님"** 이라고 적고 있다. 벤치마크 대상으로 부적절하다. 게다가 당근도 자체 구축이 아니라 토스플레이스 파트너십이라, SR 이 하려면 VN 현지 POS 벤더(KiotViet/Sapo 등) 파트너십이 별도로 필요하다 — 코드 문제가 아니다.
- **F076 알바** — 당근 본체가 아니라 **당근알바(별도 사업부)** 기능이다. 이걸 비교표에 넣은 것 자체가 과대 스코프다. SR 도메인과 무관하고 VN 구인 시장은 이미 포화(VietnamWorks, TopCV 등).
- **F036 e쿠폰 C2C 재판매** — 한국 기프티콘 유통 생태계 전제. **베트남에 재판매할 e쿠폰 시장이 존재하는지부터 불확실**하고, 성립해도 F034(에스크로) 규제 문제가 그대로 따라온다.
- **F079 자동차 전용 거래** — SR 은 오토바이/라이더 특화 정체성으로 서 있다(정비소·침수지도·주유소·서류명의). 자동차까지 넓히면 **핵심 정체성이 희석된다.** "당근에 있으니"는 이유가 되지 못한다.

## 건질 것은 F080 하나 — 그마저도 "만들 것"이 아니라 "다시 켤지"의 문제

**F080 동네걷기·방문 보상**(공수 M~L, **보류**)만이 유일하게 재사용 가능한 자산 위에 있다. `backend/app/quest_card_map.py`(퀘스트 25종, RD=RIDING 포함), `backend/app/jobs/retry_quest_rewards.py`, RP 경제가 **살아있는 코드로 남아 있고**, `coupons.py` 의 RP→쿠폰 교환은 당근머니→가맹점 사용과 구조가 같다. 즉 SR 은 이미 이 모양을 한 번 만들어봤다가 접었다.

그런데 `engine/alembic/versions/062_disable_internal_coupon_catalog.py` 가 **"되돌리지 않는다"는 정책을 명시**해 비활성화했다(2026-07-22). 그러니 이건 코드 판단이 아니라 **대표가 그 정책을 번복할지에 대한 경영 판단**이다.

만약 번복한다면, 이식할 것은 만보기가 아니라 **라이더 특화 미션**이다 — 정비소 방문 체크인, 침수지도 제보, 주유소 방문. `/info/repair`·`/info/flood`·`/info/gas` 가 이미 있으니 방문 기록만 얹으면 된다. 그리고 보상 사용처는 이번에 만든 **F061 가게 쿠폰과 그대로 연결**된다.

## 이 라운드의 한계

- `codebase-memory` MCP 연결 실패로 그래프 조회 대신 키워드 grep 을 썼다. 네이밍이 예상과 다른 구현은 놓쳤을 수 있다.
- "미발견"은 탐색 범위 내에서 못 찾았다는 뜻이지 부재 확정이 아니다.
- 베트남 시장·법제 판단(등기 전산화 수준, 기프티콘 유통, POS 벤더)은 **현지 확인이 필요한 추정**이다. 폐기 판정의 근거가 흔들릴 수 있는 지점이므로, 뒤집을 근거가 나오면 재검토 대상이다.
