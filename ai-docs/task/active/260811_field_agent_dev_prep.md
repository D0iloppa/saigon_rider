## T-1. 업체 계정 매물 등록 경로 — **최우선 · 본투입 전 필수**

대표 결정 D-1 의 옵션 1. 승인 전제로 착수 준비만 해두고, 승인 나면 바로 들어간다.

### 지금 왜 막혀 있나 (코드 확인 완료)

1. **매물 등록에 개인 휴대폰 인증이 서버에서 강제된다.**
   `backend/app/routers/market.py` 등록 핸들러:
   ```python
   if body.seller_id != _session_uid:                      # impersonation 차단
       raise HTTPException(403, "Forbidden")
   seller = await db.get(User, _session_uid)
   if seller is None or seller.phone_verified_at is None:  # ← 이 게이트
       raise HTTPException(403, "Phone verification required to list items")
   ```
   현장에서 사장 폰으로 SMS 를 받아야 하고, 안 오면 그 업체 매물은 0건이 된다.

2. **`marketplace_listings` 에 업체 FK 가 없다.** 판매자는 `seller_id`(User) 뿐이다
   (`backend/app/models.py` `MarketplaceListing` — `business_profile` 컬럼 없음 확인).
   가입시킨 가게 페이지에 그 가게 물건이 안 붙고, 매물은 개인 판매자로 표시된다.

3. **`backend/app/routers/biz.py` 에 매물 관련 코드가 전무하다.** 업체 도메인은 신청·검증·관리·
   소식·광고까지 있으나 매물 등록 경로가 없다.

### 재사용할 선례

**광고 도메인에 이미 같은 패턴이 있다.** `marketplace_ads.owner_business_profile_id`
(`models.py:838`)와 `backend/app/modules/ads/application.py` 의 조회/필터 코드를 그대로 본뜨면 된다.
새 설계를 만들 필요 없다.

### 작업 항목

| # | 내용 | 비고 |
|---|---|---|
| 1-1 | `marketplace_listings.business_profile_id` 컬럼 + 마이그레이션 | nullable. `marketplace_ads` 패턴 미러링 |
| 1-2 | 등록 게이트에 업체 경로 추가 — 사업자 검증(`biz_verification`)을 `phone_verified_at` **대체 인증**으로 인정 | 개인 경로의 기존 게이트는 **건드리지 않는다**(회귀 방지) |
| 1-3 | 프론트 진입점 — 업체 프로필 → 매물 등록 | `frontend/src/pages/market/MarketCreate.tsx` 필수값: 사진·제목·지역 |
| 1-4 | 매물 상세/목록에서 판매자를 업체로 표기 + 업체 페이지에 그 가게 매물 노출 | |

### 완료 판정

- 업체 계정으로 **SMS OTP 없이 매물 1건 등록 성공**
- 그 매물이 **해당 업체 페이지에 노출**되고 판매자가 업체명으로 표시됨
- 개인 사용자 매물 등록 경로는 **무변화**(기존 테스트 통과)

### 이게 되면

전화 인증 단계(업체당 3.5분, 하루 28분)가 사라진다. 단가 문서 §3 소요시간표를 그만큼 갱신해야 한다.

## T-3. 업체당 매물 상한 5건 — 강제 여부 결정

### 문제

**코드에 상한이 없다.** `backend/app` 전체에서 업체당/판매자당 매물 수 제한 로직을 찾지 못했다
(참고: `biz.py:71` 의 `MAX_PROFILES_PER_USER=3` 은 프로필 수 제한이지 매물 수가 아니다).

단가 문서 §5 는 상한 5건을 **검수 기준**으로만 두고 있다. 매물 건당 7,000동이 걸린 구조라
한 가게에서 무한 등록할 유인이 생긴다 — 이번 범위 확장의 최대 신규 리스크로 지목된 항목이다.

### 결정이 필요하다

- **A. 서버 강제** — 6건째 등록 시 422. 확실하지만 정상 대형 매장도 막힌다
- **B. 검수 단계 반려** — 유연하지만 검수 부하가 늘고 이미 지급된 건 회수가 번거롭다

권고는 **A + 예외 화이트리스트 없음**(초기엔 단순하게). 정상 대형 매장은 파일럿에서 나오면 그때 푼다.

## T-4. 매물 검수 큐 — 하루 54건 유입 대비

### 현황 (확인 완료)

어드민에 매물 화면이 **이미 있다** — `admin-frontend/src/pages/listings/`
(`ListingListPage.tsx` · `ListingDetailPage.tsx`). status 필터와 `StatusTag` 가 붙어 있다.

**미확인** — 목록에서 일괄 승인/반려 액션이 되는지는 코드를 더 봐야 한다. 이어받는 세션이 먼저 확인할 것.

### 작업 항목

| # | 내용 |
|---|---|
| 4-1 | 일괄 승인/반려 액션 유무 확인 → 없으면 추가 |
| 4-2 | 검수 6기준 중 **기계 판정 가능한 것**을 자동 플래그 — 사진 2장 미만 / 가격 0동 / 카테고리 미지정 / 업체당 5건 초과 / 동일 업체 내 제목·사진 중복 |
| 4-3 | 배정표 기준 하루 유입량으로 부하 산정 — 본투입일 매물 54건 + 가입 36곳 |

기계 판정이 되면 사람은 "실물 사진인가 / 거래 장소가 실제 가게인가" 두 가지만 보면 된다.

### 4-3 후속 (구현 세션 완료, 부하 산정)

일괄 승인/반려(`POST /admin/api/listings/bulk-moderate`)와 자동 플래그(사진 2장 미만 / 가격 0동 /
카테고리 미지정 / 근접중복)를 구현 완료했다. **"업체당 5건 초과" 플래그는 구현하지 않았다** —
T-3 가 등록·재판매 시점에 6건째를 422 로 이미 막아서, 노출 중인 매물이 5건을 넘는 상태 자체가
서버를 거치는 한 발생할 수 없다(죽은 코드를 만들지 않기로 함).

`260810_field_agent_schedule.html` 의 본투입 1주차 산출물("업체 144곳 + 매물 216건", 작업자 4×4일)
기준 **피크 일일 유입은 매물 54건 + 가입 36곳**이다(216÷4, 144÷4 — 태스크 프롬프트가 인용한
수치와 일치, 2주차도 동일 규모라 1주차만 피크가 아니라 본투입 8일 내내 이 수준이 유지된다).

기계 플래그로 걸러지는 비율을 가정하면(사진부족·가격0·카테고리없음·근접중복 중 하나라도 걸리는
매물은 대략 일부일 것 — 실측 전이라 추정치임을 전제) 사람이 실제로 "실물 사진인가/실제 가게인가"
두 가지만 봐야 하는 항목은 54건보다 줄어든다. 다만 **깨끗하다고 플래그가 안 걸려도 그 두 가지
수동 판단은 항목마다 여전히 필요**하고, 일괄 승인/반려는 여러 건을 "같은 사유로 한 번에" 처리할
때만 부하를 줄인다 — 항목별 판단 자체를 없애주지는 않는다. 검수자 1인이 매물당 평균 30초씩
수동 판단한다고만 잡아도 54건 = 27분/일, 여기에 가입 36곳 심사(계정·사업자 확인)가 별도로 얹힌다.
검수자가 현장 감독자 겸임이라면(문서 상단 "감독자 현장 작업 겸직" 전제) 이 시간이 현장 업무와
경합할 수 있다 — **인력 배분(검수 전담 여부)은 코드로 해결되는 부분이 아니라 대표 결정이 필요한
리소스 이슈로 남긴다.**

## T-6. `wards` 폴리곤 부재 (후순위)

`wards` 테이블에 `center_lat`/`center_lng` 만 있고 **폴리곤이 없다**(`database/init/159_wards_seed.sql`,
37개 동). 그래서 이번 배정표·링크리스트의 구역 배정은 **최근접 중심점(보로노이 근사)** 이고
실제 행정경계와 어긋날 수 있다.

현장에는 "동 이름"이 아니라 순서·좌표·지도 링크로 주도록 회피해뒀으므로 **투입 전 필수는 아니다.**
다만 구역지도 정확도와 `service_area.py` 판정에 함께 걸리는 문제라 언젠가는 봐야 한다.

## T-7. 가입 확정분 일괄 등록 경로 점검

`backend/scripts/import_business_csv.py` 가 이미 있다 — CSV(`name,category,address,latitude,longitude,phone,intro`)를
받아 `status=APPROVED`, `user_id=NULL` 로 직접 삽입한다(2026-08-02 작성, 어드민 UI 수십 건 입력 비효율 해소용).

**확인 필요** — 현장 가입은 사장님 Zalo 계정이 붙는 경로다. `user_id=NULL` 로 들어간 레코드와
사장 계정 연결이 나중에 어떻게 이어지는지, 두 경로가 충돌하지 않는지 봐야 한다.

수집한 명단 CSV 는 이 스크립트 포맷에 맞춰 뽑아뒀으므로 그대로 넣을 수 있다.
