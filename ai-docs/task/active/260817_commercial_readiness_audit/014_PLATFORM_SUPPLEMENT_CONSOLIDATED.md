## §1. 종합 판정 — 한 장 요약

**010에 대한 총평: 판단은 대부분 옳고, 시야가 한 층 좁다.**

010이 옳게 판정한 것 — ML 랭킹·추천 기각, 계측 최우선, 자동 차단 대신 triage, 신규 컨테이너 금지, 사전승인 큐 금지, 외부 계측 SaaS 기각 — 은 **전부 유지한다.** 특히 "매물 213건 중 188건이 단일 계정, 실거래 스냅샷 1건" 상태에서 추천엔진을 만들면 시연 데이터를 학습한 엔진이 나온다는 판단은 정확하다. 콜드스타트 실무 정석도 휴리스틱 → 데이터 축적 → 단순 모델 → 고도화의 진화형이다.

**그러나 010은 5개 지점에서 구조적으로 좁다:**

| # | 결손 | 성격 | 단계 |
|---|---|---|---|
| ① | **이벤트 스키마를 퍼널 카운터로 설계** — 미래 랭킹·추천·분석의 유일한 원료를 "8단계 일별 카운트"로 좁힘 | "지금 안 만든다"와 "설계조차 안 한다"의 혼동 | **P0** |
| ② | **검색이 문서 전체에서 부재** — 베트남어 무성조 입력 정규화는 데이터 볼륨과 무관한 언어 필수 기능 | 맹점 | **P0** |
| ③ | **유입 출처 귀속(attribution) 부재** — 8단계 퍼널이 채널 구분 없는 단일 평균값. 어디서 왔는지 모르면 성장 의사결정 불가 | 맹점 | **P0** |
| ④ | **비즈니스 파트너 이슈 경로 0** — 광고주는 신고 버튼을 안 누른다. 영업 담당에게 전화한다 | 전제 붕괴 | **P0** |
| ⑤ | **운영 데이터의 배포 종속** — 금칙어 변경이 코드 커밋(Q-1 `f8fa9ff`) | 운영 병목 | **P0** |

**내부 정합성 결함 1건**: 010 §3-1 L2 "위험 매물 노출 저하(랭킹 감점)"는 **감점을 적용할 랭킹 함수가 먼저 존재해야 성립**하는데, 현재는 최신순 고정(확인 필요)이다. L2는 랭킹 v1 없이는 실행 불가능한 설계다.

**파일럿 판정 기준 부재 (본 문서 최대 발견)**: 010 §1-1은 파일럿 목적을 "이 동네에서 거래가 실제로 일어나는가를 측정"으로 정의했으나, **무엇이 성공이고 무엇이 실패인지 정량 기준이 없다.** 마켓플레이스에서 이 질문의 표준 답은 **유동성(liquidity)** — 매물이 합리적 시간 내에 매칭될 확률 — 이며, 이는 §7-6의 5개 지표로 정의된다. 이 기준 없이 파일럿을 돌리면 4~8주 후 "느낌"으로 판단하게 된다.

**보강: 20개 항목(#16~#35) + 미결 결정 9건 + 법무 확인 5건 + SOP 4건.** 010의 절제 원칙은 전 계층에 동일 적용 — 기각 목록은 §11에 통합했다.

## §3. 기반 계층 — 데이터 파이프라인

> **모든 것의 전제.** §4 랭킹, §6 재발 통계, §7 분석 전부가 이 위에 선다.

### 3-1. [P0] 이벤트 스키마의 근시안

**사실**: 010 #5는 "핵심 이벤트 8종이 이벤트 테이블에 쌓이고 어드민에서 일별 단계 수를 조회"로 완료 조건을 정의했다. D-18 권고는 (a) 자체 이벤트 테이블.

**판단**: 자체 테이블 채택은 옳다(PDPL 국외 이전 리스크 회피 — 010 판단 유지). 문제는 **스키마의 폭**이다. 카운터성 스키마는:

- §4 랭킹 v1의 입력(매물별 조회·문의 수)을 못 준다
- §4 최근 본 매물·카테고리 친화의 원료(user×item 상호작용)를 못 준다
- §6 오탐률 실측(플래그된 매물의 실제 전환)을 못 준다
- §7 채널별 퍼널·코호트 리텐션·유동성 지표를 **전부** 못 준다
- 향후 추천 모델의 학습 데이터가 못 된다

→ **파일럿 4~8주치 데이터가 통째로 재사용 불가.**

**보강안 (공수 델타 S)**: 처음부터 **상호작용 로그**로 잡는다.

```sql
CREATE TABLE app_events (
  event_id      BIGSERIAL PRIMARY KEY,
  event_type    VARCHAR(40) NOT NULL,   -- 백엔드 Enum 검증 (D-19 방식 승계)
  user_id       BIGINT,                 -- 비로그인 NULL
  anon_id       UUID,                   -- 비로그인 열람 퍼널 (010 구매자 문턱이 비로그인부터 시작)
  subject_type  VARCHAR(20),            -- 'listing' | 'ad' | 'biz' | 'user' | 'search'
  subject_id    BIGINT,
  surface       VARCHAR(30),            -- D-19 카탈로그 재사용
  session_id    UUID,
  acq_source    VARCHAR(40),            -- §7 유입 귀속 (세션 시작 시 스탬프)
  props         JSONB DEFAULT '{}',     -- dwell_ms, position, query, ward 등
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_events_subject ON app_events (subject_type, subject_id, created_at);
CREATE INDEX idx_events_user    ON app_events (user_id, created_at);
CREATE INDEX idx_events_type_at ON app_events (event_type, created_at);
```

퍼널 8종은 `event_type`의 부분집합일 뿐이다. 010 #5의 일별 롤업 잡은 그대로 성립한다. **추가되는 것은 컬럼 몇 개와 인덱스 3개** — L급 항목의 규모는 변하지 않는다.

**결정 연계**: D-18을 "퍼널 계측 방식"이 아니라 **"플랫폼 이벤트 파이프라인 방식"** 으로 격상해 1회 결정할 것 → **D-23**.

### 3-2. 검색 로그 계측 — 공급 영업의 조준경

`event_type='search'` + `props.query` + `props.result_count` 를 같은 파이프라인에 적재하면, 어드민에서 **"결과 0건 검색어 상위 N"** 을 뽑을 수 있다. 판단: 이것은 단순 로그가 아니라 **"수요는 있는데 공급이 없는 품목"의 직접 관측**이며, 010 §7-1 공급 영업의 타깃 리스트가 된다. 필드 에이전트 재가동 시 "무엇을 모아올 것인가"를 감이 아니라 데이터로 정한다.

## §4. 발견 엔진 계층 — 검색·랭킹·매칭

### 4-1. [P0] 베트남어 검색 정규화 — 볼륨 문제가 아니다

**사실**: 010은 §1~§8 전체에서 검색을 한 번도 다루지 않았다. 현재 구현 방식(ILIKE 추정) 자체가 **확인 필요**.

**판단 — 010 최대의 맹점.** 근거 3가지:

1. **베트남어 입력 현실**: 모바일에서 성조·다이어크리틱 없이 입력하는 것이 매우 흔하다("xe máy"→"xe may", "Hà Nội"→"Ha Noi"). PostgreSQL `unaccent` 확장이 표준 해법이나, **기본 rules 파일은 베트남어 전체 문자(ơ, ư, đ, 성조 조합)를 완전히 커버하지 못해** 베트남 개발 관행상 rules 보강 또는 전용 변환 함수 추가가 통용된다. `đ→d` 매핑은 특히 기본 규칙에서 빠지기 쉽다.
2. **볼륨 무관성**: 매물이 20건이어도 "xe may"가 0건을 반환하면 죽은 앱이다. 계측·공급과 달리 **파일럿 데이터를 기다릴 이유가 전혀 없다.**
3. **양방향 필요**: 질의뿐 아니라 저장 텍스트도 정규화해야 한다(판매자도 무성조로 등록한다). `title_norm` 컬럼 + 트리거 + pg_trgm GIN 인덱스.

**부가 효과**: 이 정규화 함수는 §5 금칙어 매칭(#22)에 재사용되어 **금칙어 무성조 우회 입력까지 자동으로 잡는다.**

### 4-2. [P1] 랭킹 부재 — 010 내부 정합성 결함

**판단**: **감점(penalty)은 점수(score)가 있어야 성립한다.** 현재가 순수 최신순이면 L2 시점에 감점을 붙일 대상 함수가 없어 급조하게 된다. 랭킹 v1은 ML이 아니라 규칙식이며 데이터가 필요 없다:

```
score = freshness_decay(refreshed_at, 반감기 72h)
      × quality(사진 수 정규화 · 설명 길이 · phone_verified 가산 · 서류보유 표시 가산)
      × trust_penalty(L2 플래그 감산 — 초기 계수 1.0 = 무효과)
```

파일럿 중엔 `trust_penalty=1.0`으로 배포해 **최신순과 거의 동일하게 동작**시키고, L2 진입 시 계수만 조정한다. 이러면 L2가 "새 시스템 구축"이 아니라 **"상수 변경"** 이 된다. 끌올과의 상호작용은 `refreshed_at` 기준으로 해소.

### 4-3. [P1] 키워드 알림 — 공급 희소 국면의 최고 효율 매칭

**사실**: 010 §7-1 "공급 0은 어떤 코드로도 못 푼다."

**판단 — 절반만 맞다.** 코드는 공급을 만들지 못하지만 **희소한 공급을 수요와 매칭하는 효율은 코드가 결정한다.** 공급이 적을수록 키워드 알림의 한계가치는 **커진다**. 당근마켓이 초기부터 핵심 유동성 장치로 운영한 기능이며, 사용자가 키워드를 등록해두면 해당 매물 등록 시 알림을 받는 구조다.

파일럿 시나리오: 1개 구에 주 10건 등록. 열람 시점에 우연히 노출될 확률은 낮지만, "Honda Cub"을 등록한 수요자 5명에게 즉시 FCM이 가면 **매물 1건당 문의 발생 확률이 구조적으로 상승**한다. 이는 파일럿 측정 대상("거래가 일어나는가")의 **분모를 키우는 유일한 코드**다.

구현: `saved_keyword` 테이블 1개 + 등록 트랜잭션 후 아웃박스(D-5 선례) 매칭 잡(§4-1 정규화 재사용) + 기존 FCM. **신규 인프라 0.**

### 4-4. [P1→P2] 조회 이력 기반 표출 — 대표 요청의 착지점

"조회 이력에 맞는 선별 리스트 재구성"의 실현 형태를 데이터 요구량 순으로:

| 단계 | 기능 | 필요 데이터 | 판정 |
|---|---|---|---|
| a | 최근 본 매물 (1행) | 본인 이력만 | **[P1] 승격** — per-user라 전체 볼륨 무관. 규모 S. #16 선행 |
| b | 카테고리 친화 부스트 | 본인 이력 2주+ | [P2] — 랭킹 v1에 항 추가로 예약 |
| c | 함께 본 매물 (공출현) | 전체 이력, 매물 수백+ | [P2] |
| d | ML 추천 | 수천 상호작용 | [P2 후반] — 010 기각 유지 |

## §5. 운영 관리 계층 — 설정·계정

### 5-1. 벤치마크 대조

마켓플레이스 어드민 실무 표준은 **5도메인** — 사용자 관리, 거래 감독, 콘텐츠·매물 모더레이션, 재무 통제, 플랫폼 설정 — 이며, **역할 기반 접근 제어(RBAC)는 타협 불가**이고 단일 슈퍼유저 계정은 어떤 규모에서든 보안·컴플라이언스 실패로 간주된다. 국내 실무 문헌이 경고하는 전형적 실패는 **"처음엔 간단한 CRUD였던 어드민이 어느 순간 배포 없이는 컬럼 하나도 못 바꾸는 운영 병목이 되는 것"** 이다.

| 도메인 | SGR 현황 | 판정 |
|---|---|---|
| ① 모더레이션 | 신고·제재 도구 완성(W4) + 본 문서 §6 | ✅ |
| ② 거래 감독 | GMV 집계 + 스냅샷(010 #4) + 퍼널(#5) | ✅ |
| ③ 사용자·판매자 관리 | 제재·이력·티켓 완성 | ✅ |
| ④ 재무 통제 | 광고 수동 결제(P-6c) | ✅ 010 판단 유지 — 광고주 소수 구간 수동이 정답 |
| ⑤ **플랫폼 설정 + 계정 체계** | **결손 2 + 확인 필요 3** | ⚠️ |

### 5-2. [P0] 금칙어의 배포 종속 — 증거는 010 안에 있었다

**사실**: 010 §5 완료 목록 "Q-1 금칙어 매물 확대 `f8fa9ff`" — 금칙어 확대가 **코드 커밋**이었다.

**판단**: 파일럿의 목적이 "배우는 것"이라면 배울 것 중 하나가 **현지 사기 어휘**다. 베트남어 선입금 유도 변형 표현은 파일럿 중 실시간으로 발견될 것이고, 발견→차단 지연이 배포 주기와 같아서는 안 된다. 금칙어는 임계값 상수(하드코딩이 옳다)와 성격이 다른 **운영 데이터**다(원칙 B2).

### 5-3. [P0] 공지·배너 부재 (추정 — 확인 필요)

**판단**: 파일럿 운영 시나리오를 구체화하면 자명하다 — ① 점검 공지 ② "주말 ○○구 안전거래 이벤트" ③ **사기 주의보** ④ 정책 변경 고지(법무 통보 의무 직결). 넷 중 하나라도 배포로 처리하면 §5-1의 병목 패턴이다. 최소 구현: `announcement(title, body, type, starts_at, ends_at, active)` + 홈 배너 1슬롯 + 공지 목록. **풀 CMS 아님.**

### 5-4. [P1] 어드민 계정 개별화 — RBAC의 최소 형태

**판단**: 벤치마크의 "RBAC 필수"를 현 규모(운영 0.5~2인)에 그대로 적용하면 과설계다. 그러나 **하한선**은 있다: ① 1인 1계정(공유 금지) ② 모든 변경성 액션에 `actor_id` 기록 ③ 역할 2종(SUPER: 설정·계정 / OPS: 신고·검수·공지).

근거: 010 §3-2가 설계한 신고 폐루프의 감사 증적은 **"누가 판정했는가"** 가 있어야 이의제기(#2) 분쟁에서 의미가 있고, 인력이 2인이 되는 순간(010 §7-3에 이미 예정) 소급 도입은 **기존 로그 전체의 행위자 불명**을 남긴다.

## §6. 이슈 운영체계 — 4관점 사고 처리

### 6-1. 판정: 도구는 있고 체계가 없다

010 §3-2의 신고 폐루프는 잘 설계됐으나 **하나의 전제 위에 서 있다 — "문제는 신고 버튼을 통해 들어온다."** 이 전제가 4관점 중 절반에서 깨진다.

실제 유입은 4경로다: ① 신고 버튼 ② 고객문의 티켓 ③ 자동 탐지·경보 ④ **외부**(규제기관·앱스토어 리뷰·Zalo/Facebook·**영업 담당 개인 연락**).

**광고주는 신고 버튼을 누르지 않는다. 계약 상대방에게 전화한다.** 그 순간 이슈는 시스템 밖으로 새고 ① 처리 이력 무기록 ② 담당자 부재 시 정지 ③ 재발 통계 불가 ④ 분쟁 시 증적 0이라는 4중 결함이 발생한다.

### 6-3. 오토바이 특유 위험 — `B-STOLEN` 별도 취급

**판단**: 주력 카테고리가 오토바이이고, 도난 차량 유통은 ① 형사 사안 ② 구매자에게 **차량 몰수**라는 회복 불가 손해 ③ 플랫폼 **연대 배상 책임**(§6-5)과 직결된다. "허위 매물"의 하위 유형이 아니라 별도 SEV1 사유다.

**최소 대응**:
- **[파일럿, S]** 신고 사유 `STOLEN_GOODS` + SEV1 가중치 → 큐 최상단
- **[파일럿, S]** 오토바이 등록 시 **서류 보유 여부 선택 필드**(`cà vẹt` 보유/미보유/미확인) — 강제 아님, 표시만. 판단: 미보유 표시가 구매자 경고 신호이자 §4-2 랭킹의 품질 항이 된다. 010의 "컨디션 필드 후순위" 판정과 성격이 다르다 — 편의 정보가 아니라 **위험 신호**다
- **[비범위]** 차대번호 조회·정부 DB 연동 — UDI 판단과 동일 논리

### 6-4. 사고 생애주기 5단계

```
[접수] → [분류] → [처리] → [종결·통보] → [학습]
 4채널    심각도+정렬   조치+권한    결과코드+양측통보   주간 유형별 집계
  #25     010 #3 재사용  기존 도구 ○   010 #1 + #26      #26 종속
```

| 단계 | 010 현황 | 보강 |
|---|---|---|
| 접수 | 신고 큐 1채널 | **#25** — 4채널을 `source` 필드로 구분해 단일 큐 수렴 |
| 분류 | #3 우선순위 정렬(설계 완료) | SEV1~4를 #3 가중치 테이블에 병합 — **신규 코드 아님** |
| 처리 | 도구 완성(W4) | 유형별 조치 매트릭스는 SOP-1(코드 밖) |
| 종결·통보 | #1 신고자 통보 | **#26** 결과 코드 없이 종결 불가 |
| 학습 | **없음** | **#26** 주간 유형별 집계 — "무엇을 고칠까"의 유일한 근거 |

**판단**: 5단계 중 가운데 3개는 010이 이미 8할을 해뒀다. 진짜 구멍은 **양 끝 — 접수와 학습**이다.

### 6-5. 법규 압력 (법무 확인 필수)

**2차 출처 기반**: Decree 85/2021/ND-CP(52/2013 개정, 2022-01-01 시행)는 전자상거래 거래 플랫폼 사업자에게 ① 법령 위반 관련 규제당국 정보 요청에 **24시간 내 응답**할 담당 창구 지정 ② 다자 거래에서 **소비자 불만 접수 창구** 역할 ③ 주문 기록 보존 ④ 플랫폼 내 위반을 처리하지 않아 발생한 손해에 대한 **연대 배상 책임**을 부과한다. 법령 원문 인용에는 산업무역부 전자상거래 관리 포털(`online.gov.vn`)을 통한 **불만·신고·분쟁 정보의 접수 및 회신** 체계도 언급된다.

**010 §7-2에 추가할 법무 확인 4건** → §10 L-1~L-4.

**판단**: L-1(SGR이 "sàn giao dịch TMĐT"에 해당하는가)이 긍정이면 #25·#27은 **권장이 아니라 컴플라이언스 항목**으로 격상되며 파일럿 개시 전 필수가 된다. 파일럿을 1개 구로 좁힌 것이 법적 노출을 줄이지는 않는다 — 규모가 아니라 성격의 문제다.

### 6-6. 파트너 보전(make-good) 정책

**문제**: #10으로 광고가 재개되면, 트래픽이 0에 가까운 파일럿에서 "약속한 노출이 안 나왔다"는 항의가 구조적으로 발생한다(010 §3-3이 정직하게 인정한 "0을 정확히 계측하는 국면").

**업계 표준**: 광고 보전 조항은 통상 **과소 노출이 광고주 귀책(소재 지연·부적합·정책 미준수)인 경우, 특정 일·주 단위 분배 미달인 경우** 등을 보전 대상에서 제외한다.

**SGR 최소 정책안 (판단)**:

| 상황 | 처리 |
|---|---|
| 플랫폼 귀책 미노출(버그·설정 오류) | **기간 연장 보전** — 미노출 일수 × 1.5배 (현금 환불 아님) |
| 노출됐으나 성과 기대 미달 | 보전 없음. 리포트 제공 + 지면·소재 조정 제안 |
| 광고주 귀책(소재 지연·반려 후 미교체) | 보전 없음 |
| 중도 해지 | 잔여 일할 크레딧(차기 계약 차감), 현금 환불은 대표 승인 건별 |

**코드 소요 최소**: 계약 기간 연장 필드 + 사유·승인자 감사 로그(#28). **본체는 정책 문서**이며 **첫 광고주 계약서에 들어가야 한다** — 계약 후에 만들면 협상력이 0이다.

**해당 항목: #25(통합 인테이크) · #26(유형·결과 코드) · #27(업체 창구) · #28(보전 처리) · #29(오토바이 위험 신호)**

## §7. 유입·전환 분석 체계 — **신규**

> 대표 지시: "사용자 유입과 전환 등 다양한 분석 관련 기능도 함께 고려"

### 7-1. 판정 — 010 퍼널의 3가지 구조적 한계

010 #5의 8단계 퍼널(가입·매물조회·등록·문의·가격제안·약속·완료·후기)은 방향은 맞지만 세 곳이 끊겨 있다:

| # | 한계 | 결과 |
|---|---|---|
| ① | **가입 이후만 본다** | 진짜 최대 이탈 구간인 **설치→첫 실행→열람→가입→인증**이 안 보인다. Zalo OAuth 인증 단계는 구조적 이탈 지점인데 측정 불가 |
| ② | **유입 출처가 없다** | 8단계가 채널 구분 없는 **단일 평균값**. "필드 영업으로 온 사용자와 지인 소개로 온 사용자 중 누가 거래하는가"를 못 답한다 = 성장 자원 배분 근거 0 |
| ③ | **전환의 종착점이 앱 밖** | C2C 거래는 만나서 끝난다. "거래 완료"는 **자기신고**이며 실제 거래의 하한선일 뿐. 대리 지표(proxy)가 필요 |

**판단**: ②가 가장 심각하다. 유입 귀속은 **소급이 불가능**하다 — 파일럿 4~8주 동안 온 사용자들이 어디서 왔는지는 그때 기록하지 않으면 영원히 알 수 없다. #16 스키마와 동일한 논리다.

### 7-2. 유입(Acquisition) 귀속 체계

**SGR의 실제 유입 채널** (파일럿 1개 구 기준):

| 채널 | 성격 | 귀속 방법 |
|---|---|---|
| 필드 에이전트 대면 등록 | 유료(인건비) | 에이전트별 `ref` 코드 |
| 지인 소개 | 무료·바이럴 | 초대 코드 |
| **매물 공유 링크**(Zalo/Facebook 그룹) | 무료·판매자 주도 | 공유 URL의 `ref` 파라미터 |
| 업체 매장 QR·포스터 | B2B 연계 | 업체별 `ref` 코드 |
| 앱스토어 자연 유입 | 무료 | 잔여(unattributed) |

**최소 귀속 구현**:
1. 모든 진입 URL에 `?ref=` 파라미터 → 세션 시작 시 캡처
2. 가입 시 `user.acquisition_source` 에 **고정(불변)** — 최초 귀속(first-touch) 모델. 판단: 멀티터치 어트리뷰션은 현 규모에서 과설계
3. 이후 모든 이벤트에 `acq_source` 스탬프(§3-1 스키마)

**Android 설치 귀속**: Google Play **Install Referrer API**는 Play 스토어 앱이 노출하는 인터페이스로, 설치 전 클릭 링크의 `utm_*`·레퍼럴 코드를 설치 후 앱이 조회할 수 있게 해준다. **3자 SDK 없이** 캠페인 귀속과 친구 추천 코드 추적이 가능하다는 점이 핵심이다. 베트남은 Android 우위 시장이므로 이것만으로 실질 커버리지가 확보된다. → **Capacitor 플러그인 가용성 확인 필요.**

**iOS**: 지연 딥링크 귀속이 구조적으로 어렵다. 판단 — 웹 랜딩에서 초대 코드 수동 입력 폴백으로 처리하고, 정확도 저하를 수용한다. iOS 비중이 낮은 시장에서 이것 때문에 3자 SDK를 도입하는 것은 원칙 A1 위반.

**명시적 비범위**: AppsFlyer·Adjust·Firebase Analytics 등 외부 귀속 SaaS(PDPL 국외 이전 + 비용, 010 판단 승계), **기기 핑거프린팅**(PDPL 위반 소지 — 명시 금지).

### 7-3. 공유·초대 루프 — 공급측 유입의 유일한 무료 채널

**판단**: 베트남 C2C의 실제 유통 경로는 앱 내 검색이 아니라 **Zalo·Facebook 그룹 공유**다. 판매자가 자기 매물을 그룹에 뿌리는 행위는 이미 일어나고 있으며(또는 일어나야 하며), 여기에 `ref`를 붙이면:

- 판매자 주도 유입이 **측정 가능**해진다
- 매물 공유가 곧 사용자 획득이 되어 **공급이 수요를 데려오는 루프**가 생긴다 — 010 §7-1의 "공급 0" 문제에 코드가 기여할 수 있는 두 번째 지점(첫 번째는 §4-3 키워드 알림)
- K-factor(초대당 신규 가입 수) 산출이 가능해진다

**게이미피케이션 연계**: 기존 SRE 스펙의 "친구 초대 1명 가입+활성 → 20 GC" 보상은 **본 귀속 체계 없이는 지급 판정 자체가 불가능**하다. #31은 게이미피케이션의 선행 인프라이기도 하다. 단 v1은 **측정만**, 보상 지급은 어뷰징 가드(30일/300km 조건) 확정 후.

### 7-6. 마켓플레이스 유동성 지표 — **파일럿 성패 판정 기준**

**업계 정의**: 마켓플레이스 유동성은 **매물이나 요청이 합리적 시간 내에 매칭될 확률**이다. 규모와 다르다 — 매물 100만 건이어도 구매자가 매칭을 못 찾으면 비유동적이고, 수백 건이어도 대부분의 검색이 거래로 끝나면 고유동적이다. 중요한 것은 원시 개수가 아니라 **성사율**이다. 측정은 단일 숫자가 아니라 **수요측 최소 1개 + 공급측 최소 1개**를 함께 봐야 하며, 한쪽만 최적화해 다른 쪽을 굶기지 않도록 해야 한다. 또한 **도시 전체 평균은 특정 지역이 죽어 있는 것을 숨기므로 세그먼트별로 봐야 한다.**

**SGR 유동성 패널 5지표 (판단)**:

| # | 지표 | 측면 | 정의 | 파일럿 목표(제안) |
|---|---|---|---|---|
| L-1 | **매물 문의 전환율** | 공급 | 등록 후 14일 내 1건 이상 문의를 받은 매물 비율 | ≥ 40% |
| L-2 | **매물 거래 전환율** | 공급 | 등록 후 30일 내 거래(자기신고 또는 연락처 교환) 비율 | ≥ 15% |
| L-3 | **검색 0건 비율** | 수요 | 결과 0건 검색 / 전체 검색 | ≤ 20% |
| L-4 | **첫 문의까지 시간(중위)** | 양측 | 등록 → 첫 문의 | ≤ 72h |
| L-5 | **주간 신규 활성 판매자 수** | 공급 | 해당 주에 매물 1건 이상 등록한 **고유 계정**(시연 계정 제외) | 우상향 |

**판단 — 이것이 010의 가장 큰 공백이다.** 010 §1-1은 파일럿 목적을 "거래가 실제로 일어나는가 측정"으로 정의했으나 **성공/실패 임계값이 없다.** 위 5개는 제안값이며 대표가 조정해야 하지만, **개시 전에 숫자가 확정돼야 한다**(원칙 B6). 확정되지 않으면 4~8주 후 "느낌"으로 판단하게 되고, 그 판단은 반드시 낙관 편향된다.

**L-5의 시연 계정 제외**가 특히 중요하다 — 현재 213건 중 188건이 단일 계정인 상태에서 이 필터가 없으면 모든 지표가 오염된다.

### 7-7. 파트너(B2B) 분석 — 광고 가치의 유일한 증거

|---|---|

        ↓

        ↓

## §13. 결론 — 대표 보고용 5문장

1. **010의 절제는 옳고 유지한다** — ML 추천 기각, 계측 우선, 자동 차단 금지, 신규 컨테이너 금지. 지금 추천엔진을 만들면 시연 계정 188건을 학습한 엔진이 나온다.

2. **그러나 010은 "지금 안 만든다"와 "원료를 안 남긴다"를 혼동했다** — 이벤트 스키마를 퍼널 카운터로 좁게 잡아 미래 랭킹·추천·유입 분석의 파이프라인을 끊었다. 공수 델타는 S인데 소급 복구는 불가능하다.

3. **데이터가 필요 없는 엔진 3종이 누락됐다** — 베트남어 무성조 검색 정규화(볼륨 무관한 언어 필수 기능), 키워드 알림(공급이 희소할수록 가치가 커지는 매칭 도구), 규칙 기반 랭킹 v1(L2 감점이 성립하려면 어차피 필요한 선행 조건).

4. **운영 계층에서 4관점 중 파트너가 통째로 비어 있다** — 광고주는 신고 버튼을 안 누르고 영업 담당에게 전화하며, 그 순간 이슈가 시스템 밖으로 샌다. **#27(업체 창구)은 #10(광고 재개)보다 먼저여야 한다.**

5. **파일럿에 성공 기준이 없다** — "거래가 일어나는가"의 정량 정의는 유동성 5지표(§7-6)이며, 시연 계정 제외 필터와 함께 **개시 전에 목표선이 확정돼야 한다.** 대표 결정이 필요한 것은 실질 3건 — **D-23**(이벤트 파이프라인을 상호작용 로그로), **D-30**(유입 귀속 방식), **D-31**(파일럿 임계값)이다.
