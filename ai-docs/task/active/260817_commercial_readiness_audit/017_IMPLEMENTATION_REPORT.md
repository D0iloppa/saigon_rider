## §4. 리뷰에서 잡은 결함 1건

**검색 이벤트가 페이지네이션마다 중복 적재되던 문제** (`market.py`, #21)

`get_listings` 는 페이지네이션 엔드포인트인데 SEARCH 이벤트 적재에 offset 조건이 없었다. "honda cub" 으로 5페이지를 스크롤하면 이벤트가 5건 쌓인다.

**단순 중복이 아니다**: 결과 0건 검색은 페이지가 1개뿐이라 부풀지 않고, **결과가 있는 검색만 부푼다.** 따라서 **L-3(검색 0건 비율)의 분모만 커져 체계적으로 과소 산출**된다 — 파일럿 성패 판정 지표가 편향된다.

→ `if search_query_norm is not None and offset == 0:` 가드 추가. 주석에 사유 명기.

## §12. 환경 이슈 (재발 대비)

**`/mnt/c` 가 WSL 9p(drvfs) 마운트라 세션 중 광범위한 `Input/output error` 가 발생해 작업이 한 차례 중단됐다.** `wsl --shutdown` 후 복구했고, `git fsck --connectivity-only` 결과 dangling 객체만(정상) 손상은 없었다.

> 🔴 **재발 시 git 복구 명령(`gc` / `fsck --fix` / `reset --hard` / `.git` 삭제)을 절대 실행하지 마라.** 그때 git 이 내는 `fatal: your current branch appears to be broken` 은 **읽기 실패로 인한 거짓 신호**이며, 복구 명령을 돌리면 멀쩡한 저장소를 실제로 망가뜨린다. 조치는 `wsl --shutdown` 하나다.

**근본 해법**: 레포를 WSL 네이티브 파일시스템으로 이전. 9p 는 이 규모 레포에서 원래 불안정하다.

## §12-B. 신규 발견 — 사용자 관점 신고 생애주기 부재 (2026-08-18, 대표 지적)

실기기 테스트 중 대표가 지적한 갭이다. **010 에도 016 에도 없는 항목** — 두 문서 모두 신고를 **운영자 관점**(신고 큐·검수·제재·결과 코드)에서만 다뤘고, **신고한 사용자가 그 뒤에 무엇을 볼 수 있는가**는 어디에도 정의돼 있지 않다.

### 코드 실측 결과

| 사용자가 기대하는 것 | 현황 | 근거 |
|---|---|---|
| 내가 신고한 목록 보기 | ❌ **없음** | 사용자용 조회 라우트 전무. `users.py` 의 신고 관련 라우트는 `POST /{user_id}/report`(접수) **하나뿐** |
| 신고 취소 | ❌ **없음** | DELETE/cancel 계열 API 전무 |
| 신고 처리 결과 확인 | ⚠️ **1회성** | 운영자가 종결하면 `admin_api/reports.py:344+` 가 `Notification` 을 1건 발송한다. 알림함에서 **그때 한 번** 볼 수 있을 뿐, 신고 건에 붙어 있지 않아 **나중에 다시 조회할 방법이 없다** |
| 이미 신고한 컨텐츠인지 표시 | ❌ **없음** | 매물/유저 응답 스키마에 `is_reported` 계열 필드가 없다. **눌러봐야 409 로만 알 수 있다** — 이번에 고친 중복 토스트 사고의 근인이기도 하다 |

### ✅ 차단 / 신고 두 축 분리는 이미 올바르다

대표가 지적한 *"차단한 것은 리스트에 안 보이되, 신고한 컨텐츠는 리스트에 보여야 한다"* 는 **이미 그렇게 동작한다.**

- **차단 → 숨김**: `market.py:437-444` 가 `UserBlock` 을 양방향으로 조회해 차단한/차단당한 사용자의 매물을 목록에서 제외한다.
- **신고 → 유지**: 신고는 어떤 노출 제어도 하지 않는다. 016 **M1(탐지≠차단)** 과 **A2(오탐 1건 = 공급 1건 손실)** 를 그대로 따른 결과다 — 신고했다고 매물이 사라지면 악의적 신고 하나로 공급이 죽는다.

**즉 축은 맞게 서 있고, 빠진 것은 "신고한 사용자에게 돌아오는 피드백 루프" 다.**

### 판단 — 왜 이게 중요한가

010 §3-2 는 신고 폐루프를 *"신고 → 검수 → 조치 → **신고자 통보**"* 로 설계했다. 그런데 **통보가 휘발성 알림 1건**이라 실제로는 폐루프가 아니다. 사용자 입장에서는:

1. 신고했는지 기억나지 않아 **같은 매물을 또 신고하려 시도**한다 → 409
2. 결과 알림을 놓치면 **"신고했는데 아무 일도 안 일어났다"** 로 인식한다 → 016 §14-5 가 파트너에 대해 지적한 것과 같은 구조의 신뢰 손실이 **일반 사용자에게** 발생
3. 오신고를 되돌릴 방법이 없다

016 이 *"또 하나의 마켓플레이스가 아니라 **신뢰 인프라**"* 를 지향한다면, **신고가 어떻게 처리됐는지 보이는 것 자체가 신뢰 자산**이다(§6-7 의 "작은 숫자를 정확히 보여주는 것이 신뢰 자산"과 같은 논리).

### 권고 구현 — **고객센터에 편입** (대표 결정 2026-08-18)

초판은 "프로필 하위 신규 화면"을 제안했으나 **대표 제안(고객센터 편입)이 더 낫다.** 실측해보니 고객센터에 **필요한 패턴이 이미 전부 있다**:

```
GET  /support/tickets              내 문의 목록
GET  /support/tickets/{id}         상세
POST /support/tickets/{id}/replies 답글
→ pages/settings/CustomerSupport.tsx (목록) + SupportDetail.tsx (상세)
→ /settings/support · /settings/support/:id
```

즉 **"내가 제기한 것 → 운영진 답변 → 다시 확인"** 루프가 **이미 완성돼 있다.** 문의에 대해서만. 신고만 그 루프가 없다.

**왜 여기가 맞는가**

1. **016 B3 와 대칭이다.** B3(*"모든 유입은 하나의 큐로 수렴 — 채널은 `source` 필드일 뿐"*)는 **운영자 쪽 원칙**인데, 사용자 쪽에도 같은 대칭이 필요하다 — *"내가 운영진에게 말한 건 한 곳에서 본다."* 지금은 운영자만 통합 큐를 갖고 **사용자 쪽만 파편화**돼 있다.
2. **#25 가 이미 절반을 해뒀다.** `support_tickets` 에 `category`·`severity`·`source`·`persona`·`result_code` 가 들어가 운영자 쪽은 신고·문의·외부건이 한 큐로 흐른다. 사용자 화면만 붙이면 양쪽이 맞물린다.
3. **신규 화면 설계 0.** 목록·상세·상태표시·답글이 이미 있어 **탭 하나** 추가로 끝난다.

| 항목 | 내용 | 규모 | 상태 |
|---|---|---|---|
| **R-1** 내 신고 목록 | 고객센터에 **[문의 \| 신고] 2탭** + `GET /support/reports`(조회 전용). `reports` 테이블은 그대로 두고 조회만 추가 | S | ✅ **완료 (2026-08-18)** |
| **R-2** 이미 신고 표시 | 매물/유저 상세 응답에 `is_reported_by_me: bool` 1필드 → 신고 버튼을 "신고함"으로 비활성. **409 를 UI 가 먼저 막는다** | S | ✅ **완료 (2026-08-18)** |
| **R-3** 신고 취소 | `DELETE /support/reports/{id}` — **PENDING 한정 · 소프트 취소(행 보존) · 재신고 불가**(대표 확정 2026-08-18) | S | ✅ **완료 (2026-08-18)** |
| **R-4** 결과 영속 조회 | R-1 목록의 상태 3단계 표시로 해결(원본 `result_code` 는 노출하지 않음 — 결정 ① 참조) | (R-1 포함) | ✅ **완료 (2026-08-18)** |

**구현 방식**: `reports` 조회만 추가하는 **(a) 탭 분리**를 택한다. *(b) 신고 접수 시 `support_ticket` 동시 생성*은 **비권장** — 같은 사건이 두 테이블에 기록돼 이중 관리·정합성 문제가 생긴다.

### 함께 결정해야 할 것 3가지

| # | 사항 | 권고 |
|---|---|---|
| **①** | **신고 결과를 어디까지 노출할 것인가** | `result_code` 원본을 그대로 보여주면 **상대방에게 어떤 제재가 갔는지 드러난다** — 개인정보이자 보복 위험이다. 사용자에겐 *"검토 완료 / 조치함 / 위반 아님"* 수준으로 뭉개고 **세부 제재는 운영자 전용**으로 둘 것 |
| **②** | **정지된 사용자의 신고 이력 접근** | **허용 권고.** D-22 로 *"정지자도 자기 티켓은 열람 가능"*(`verify_user_session_allow_suspended`)이 이미 구현돼 있다. 정지가 부당하다고 이의제기하려면 자기가 무엇을 신고했는지 볼 수 있어야 한다 — **같은 규칙을 적용하는 것이 일관적이다** |
| **③** | **R-3 취소 허용 여부** | ✅ **확정(2026-08-18): 허용 — PENDING 한정 · 소프트 취소 · 재신고 불가.** 판단 근거로 실측한 사실: **신고 접수 시 피신고자에게 알림이 가지 않는다**(조치 후에만 알림). 따라서 *"신고 취소해줄테니 깎아달라"* 협박은 신고자가 DM 으로 직접 알려야만 성립하고, 그 DM 자체가 `B-HARASS` 신고 대상이다 — 어뷰징 리스크가 당초 평가보다 낮았다. 대신 **재신고 불가**로 "취소 = 최종"을 만들어 협박 카드를 원천 차단했고, **행 보존**으로 취소 반복자를 R-5 `cancelled_count` 로 추적한다 |

### 함께 확인된 것 — 신고 다중성 구조는 정확하다 (2026-08-18)

*"상품 A를 a·b·c·d 가 각각 신고할 수 있어야 한다(한 사람이 여러 번이 아니라)"* 를 DB 제약까지 실측 확인했다.

```
uq_reports_listing_once  UNIQUE (listing_id, reporter_id) WHERE target_type = 'LISTING'
```

`listing_id` **단독** UNIQUE 가 아니라 **신고자와의 복합** UNIQUE 다 → **n 명이 같은 매물을 신고할 수 있고, 같은 사람만 재신고가 막힌다.** 5개 타겟 유형(`LISTING`·`USER`·`DM`·`POST`·`COMMENT`) 전부 동일 패턴이며 **partial unique index** 라 유형별로 독립 동작한다. 실데이터로도 확인(매물 1건에 서로 다른 신고자 2명). **R-2 의 `is_reported_by_me` 조회 조건도 이 중복 검사와 동일하게 맞췄다** — 남이 신고한 매물은 내가 여전히 신고할 수 있다.

### ⚠️ 허위신고 집계 부재 — `S-FALSE-REPORT` 의 절반만 구현됨

016 §8-2 는 판매자 관점 사고 유형에 **`S-FALSE-REPORT`(허위 신고 피해, SEV3)** 를 정의하고 현황을 *"접수 ○ / 집계 ✗"* 로 적었다. **이 판정은 2026-08-18 현재도 그대로다.**

- 판매자가 "허위신고를 당했다"고 이의제기하는 경로는 있다(`support_tickets`, 010 #2 로 폐루프)
- 그러나 **누가 허위신고를 반복하는지 집계·추적할 경로가 없다**

**데이터는 이미 다 있다.** `reports` 에 `reporter_id` 가 있고, 운영자가 기각하면 `status='REJECTED'` 와 `result_code` 가 남는다. 즉 **"신고자별 기각률"은 쿼리 하나로 산출 가능**하며 — R-1 과 정확히 같은 성격의 갭이다(**필드는 있고 조회 경로만 없다**).

**왜 지금 중요한가**: 이것은 **R-3(신고 취소) 허용 여부 판단의 전제**다. 취소를 열면 *"신고 → 판매자 압박 → 취소"* 어뷰징이 가능해지는데, **허위·반복 신고자를 식별할 수단이 없는 상태에서 취소를 열면 어뷰징을 탐지할 방법이 전혀 없다.** 순서상 집계가 먼저다.

| **R-5** 신고자 신뢰도 집계 | `GET /admin/api/reports/reporters` — 신고자별 총 신고수·기각수·기각률 | S | ✅ **완료 (2026-08-18)** |
