## 0. 이 문서가 별도로 답하는 질문

기존 사용성 진단은 “어느 화면의 무엇이 불편한가”를 정리한다. 이 문서는 그 목록을 반복하지 않고 다음을 판단한다.

1. 사용자가 가입 전에 서비스 가치를 이해할 수 있는가
2. 원하는 매물을 발견한 사용자가 실제 거래까지 진행할 수 있는가
3. 앱이 일반 마켓 + 메신저보다 만남의 수고를 줄이는가
4. 거래가 끝난 뒤 신뢰 데이터와 재방문 이유가 남는가
5. 운영팀이 이탈 원인을 공급 문제와 UX 문제로 구분할 수 있는가

현재 코드에는 매물·채팅·가격 제안·약속·길찾기·완료 기능이 존재한다. 문제는 **기능의 존재가 하나의 서비스 경험으로 이어지지 않는 것**이다.

## 1. 최종 서비스 판정

### 1.1 사용자가 겪는 현재 서비스

| 여정 | 사용자의 질문 | 현재 앱의 답 | 결과 |
|---|---|---|---|
| 첫 방문 | “여기서 무엇을 얻지?” | 퀘스트 슬로건 뒤 즉시 로그인 | 목적 불명확·가입 이탈 |
| 가치 확인 | “내가 살 만한 게 있나?” | 가입·프로필·위치 판단 뒤 확인 | 가치보다 비용이 먼저 보임 |
| 탐색 | “근처에 없으면 다른 곳은?” | 3km 0건이면 첫 판매 권유 | 빈 서비스로 인식 |
| 문의 | “상대 답장이 왔나?” | 채팅함이 프로필 안에 숨음 | 응답 지연·거래 이탈 |
| 합의 | “이제 무엇을 해야 하지?” | 가격·약속 기능이 입력창 메뉴에 숨음 | 일반 채팅 왕복 |
| 만남 | “어디서 안전하게 만나지?” | 시간 입력 + 지도 핀 직접 선택 | 다른 지도 앱에서 재조사 |
| 이동 | “약속 장소로 어떻게 가지?” | 자체 엔진 실패 시 인앱 경로 중단 | 핵심 차별점 신뢰 저하 |
| 완료 | “거래를 끝내고 리뷰할 수 있나?” | 판매자만 완료 가능 | 구매자 거래·리뷰 정체 |
| 재방문 | “다시 열 이유가 있나?” | 키워드 알림은 있으나 빈 상태와 단절 | 리텐션 루프 약화 |

### 1.2 서비스 관점의 핵심 문제

문제는 기능 부족보다 **순서와 연결**이다.

- 가치가 인증 뒤에 있다.
- 제품의 첫 약속과 실제 핵심 기능이 다르다.
- 위치 개인화가 공급 밀도보다 먼저 적용된다.
- 거래 상태가 대화 속 메시지로 흩어진다.
- 약속은 저장하지만 결정의 수고를 줄이지 않는다.
- 완료 권한이 한쪽에만 있어 신뢰 데이터가 쌓이지 않는다.
- 이탈 퍼널이 계측되지 않아 개선의 효과를 판단할 수 없다.

따라서 지금 필요한 것은 새 대형 기능이 아니라 **사용자 목적 순서로 기존 기능을 다시 연결하는 일**이다.

## 2. 상용 서비스의 기준 여정

Saigon Rider가 마켓 우선 제품이라면 한 문장 약속은 다음 수준으로 단순해야 한다.

> **호치민에서 오토바이 물품을 가까운 사람과 찾고, 안전한 만남과 이동까지 한 흐름으로 끝내는 서비스**

목표 여정은 다음과 같다.

| 단계 | 목표 경험 | 인증·권한 원칙 |
|---|---|---|
| 1. 발견 | 공유 링크·검색·앱 첫 화면에서 실제 매물을 바로 본다. | 익명 허용 |
| 2. 판단 | 사진·가격·지역·판매자 신뢰·응답 정보를 본다. | 익명 허용 |
| 3. 관심 행동 | 찜·채팅·알림을 누르면 이유를 설명하고 로그인한다. | 이 시점에 인증 |
| 4. 문의·합의 | 대화 상단에서 현재 거래 단계와 다음 행동을 본다. | 로그인 필요 |
| 5. 약속 | 양측 이동 부담과 안전성을 고려한 장소 후보를 고른다. | 대략적 위치만 사용 |
| 6. 이동 | 약속 카드에서 인앱 경로 또는 정상 폴백으로 이어진다. | 출발 시 위치 권한 |
| 7. 완료 | 양측이 완료 상태를 확인하고 리뷰한다. | 거래 참여자만 |
| 8. 재방문 | 답장·새 매물·약속·리뷰처럼 명확한 이유로 돌아온다. | 카테고리별 알림 동의 |

핵심 원칙은 **로그인·전화·위치 권한을 없애는 것이 아니라, 사용자가 그 필요를 이해하는 순간까지 늦추는 것**이다.

## 3. 여정을 끊는 6개 서비스 단절

### JCR-1 · P0 — 가치 확인보다 가입이 먼저다

프론트는 `/market`, `/market/:id`, `/biz/:id`를 모두 `PrivateRoute`로 막는다. 반면 백엔드 매물 목록·상세와 업체 공개 상세는
이미 익명 세션을 지원한다(`backend/app/routers/market.py:244, 409`, `backend/app/routers/biz.py:1036-1041`).

이는 구현 불가능 문제가 아니라 **서비스 게이트의 위치 문제**다. 신규 사용자는 공급과 품질을 확인하지 못한 상태에서 소셜 계정,
닉네임, 라이더 유형, 동의를 먼저 제공해야 한다. 공개 목록을 먼저 제공하는
[Chợ Tốt Xe 공식 탐색 면](https://xe.chotot.com/mua-ban-xe-may)과도 반대 순서다.

**서비스 개선**

- 공개: 매물 목록·검색·상세, 업체 목록·상세.
- 행동 시 로그인: 채팅, 찜, 키워드 알림 저장, 팔로우.
- 판매 시 신뢰 인증: 게시 직전 전화 인증.
- 로그인 화면에는 “채팅 후 이 매물로 돌아갑니다”처럼 목적과 복귀를 표시한다.

**성공 판정**

- 공유 매물 링크를 받은 사용자가 가입 전에 사진·가격·지역을 확인한다.
- 인증 완료 후 원래 매물 또는 대화로 정확히 복귀한다.
- `랜딩 → 첫 매물 확인` 비율이 상승하고 `인증 시작 전 이탈`이 감소한다.

### JCR-2 · P0 — 퀘스트 약속과 마켓 가치가 충돌한다

스플래시는 “모든 라이드는 퀘스트”라고 말하고 가입은 라이더 유형을 묻지만, 실제 1차 탭에는 퀘스트가 없다.
홈·프로필에는 RP·레벨·퀘스트 흔적이 남아 실제 거래 신뢰 정보와 경쟁한다.

이 문제는 문구 한 줄의 오타가 아니라 **어떤 사용자를 왜 다시 오게 할지 결정되지 않은 상태**다.

**권장 결정: 마켓 우선**

- 스플래시: 주변 오토바이 중고거래와 만남 편의 약속.
- 가입: 필수 동의와 자동 닉네임만으로 첫 가치를 보게 한다.
- 기본 진입: 마켓.
- 핵심 신뢰: 거래 수, 리뷰, 응답 속도, 전화 인증.
- 퀘스트·RP·레벨: 실제 리텐션 효과를 검증할 때까지 핵심 면에서 숨긴다.

퀘스트 우선 제품을 원한다면 반대 결정을 내려도 된다. 단, 그 경우에는 스플래시뿐 아니라 탭·홈·첫 미션·보상 사용처·재방문까지
전부 퀘스트 중심으로 다시 설계해야 한다. 두 제품을 동시에 약속하는 현행은 선택지가 아니다.

**성공 판정**

- 베트남 사용자 5명 중 4명 이상이 첫 화면만 보고 같은 핵심 문제를 설명한다.
- 스플래시의 약속이 첫 세션 안에서 실제 행동으로 이어진다.

### JCR-3 · P0 — 위치 개인화가 공급 밀도보다 먼저 온다

표시 범위 기본은 GPS 3km이고 홈은 진입 즉시 위치 확인과 여러 도메인 API를 시작한다. 공급이 충분하지 않은 초기 서비스에서
정교한 근거리 필터는 개인화가 아니라 **빈 결과 생성기**가 될 수 있다.

또한 매물·날씨·침수·업체·피드를 하나의 홈에서 동시에 로드해, 사용자가 가장 먼저 판단할 매물 가치가 비핵심 데이터와 경쟁한다.

**서비스 개선**

- 초기 기본은 전체 지역 또는 파일럿 구 목록.
- `내 주변`을 누를 때 위치 권한을 요청한다.
- 3km 결과가 0건이면 전체 지역 재조회와 키워드 알림을 제안한다.
- 첫 화면은 실제 매물과 진행 중 거래를 먼저 렌더하고 날씨·침수·업체·피드는 독립적으로 늦게 로드한다.
- 파일럿 구의 공급 밀도가 목표를 넘을 때만 기본 반경 축소를 실험한다.

**성공 판정**

- 위치를 거부해도 첫 세션에서 매물 상세까지 도달한다.
- 파일럿 구 핵심 카테고리의 0건 결과율이 20% 미만이다.
- 첫 실제 매물 카드 노출이 목표 네트워크에서 p75 3초 이내다.

### JCR-4 · P1 — 거래 기능은 있지만 사용자를 다음 단계로 이끌지 않는다

가격 제안과 약속은 DM 입력창 확장 메뉴 안에 있다. 가격이 수락돼 약속 기능이 열려도 다음 단계가 주 CTA로 바뀌지 않는다.
완료도 타임라인의 약속 카드에서 판매자에게만 나타난다.

사용자에게 대화는 수단이고 목적은 거래 완료다. 현재 DM은 메시지를 잘 보여주지만 **거래 상태를 운영하는 공간**은 아니다.

**서비스 개선: Deal Cockpit**

- DM 상단에 `문의 → 가격 합의 → 약속 → 만남 → 완료` 상태를 고정한다.
- 상태별 주 CTA는 하나만 보여준다.
  - 협상 중: 가격 제안
  - 가격 수락: 약속 잡기
  - 약속 수락: 경로 보기·출발
  - 약속 경과: 완료 또는 취소 확인
- 상대 응답 대기, 내가 해야 할 일, 약속까지 남은 시간을 같은 영역에 표시한다.
- 채팅함은 프로필 하위가 아니라 1차 내비게이션으로 올린다.

**성공 판정**

- 가격 수락 뒤 처음 온 사용자도 메뉴를 열지 않고 약속을 만든다.
- 모든 1차 화면에서 채팅함에 한 번의 탭으로 도달한다.
- 첫 문의 응답시간과 `가격 수락 → 약속 수락` 전환이 개선된다.

### JCR-5 · P1 — 약속을 저장하지만 만남의 수고는 줄이지 못한다

현재 약속은 시간·장소명·위경도·상태를 저장하고 사용자가 지도에 핀을 직접 찍는다. 경로 연결은 이미 있지만 장소 결정은
일반 지도보다 나아지지 않는다. 서비스 구상서의 차별점인 “어디서 언제 만날지 돕기”가 아직 데이터 입력 기능에 머문다.

**최소 차별점**

1. 판매 위치와 구매자가 선택한 대략적 동의 중간권역을 계산한다.
2. 영업 중인 공개 장소 후보 3개를 보여준다.
3. 양측 예상 이동시간, 주차 가능성, 밝은 장소·사람이 있는 곳 같은 추천 근거를 표시한다.
4. 약속 당일 `출발`, `도착` 상태를 공유하되 정확한 실시간 위치는 별도 동의 없이는 공유하지 않는다.
5. 약속 수락 직전에 공개 장소, 현장 확인, 과도한 선입금 금지, 신고 경로를 짧게 안내한다.

자체 라우팅 엔진의 실패 회복도 이 여정에 포함된다. 현재 외부 Google URL은 `travelmode=two_wheeler`를 쓰지만
[Google Maps URL 공식 값](https://developers.google.com/maps/documentation/urls/get-started)은 `two-wheeler`이고,
[베트남은 공식 지원 지역](https://developers.google.com/maps/documentation/routes/coverage-two-wheeled)이다. 파라미터 수정과 실기기 검증이 필요하다.

**성공 판정**

- 별도 지도 검색 없이 추천 후보로 약속을 확정한다.
- 양측이 같은 카드에서 시간·장소·이동방식·상태를 확인한다.
- 자체 엔진 장애를 주입해도 한 번의 추가 탭 이내로 정상 폴백한다.

### JCR-6 · P0 운영 — 완료·신뢰·재방문 루프를 측정할 수 없다

판매자만 거래 완료를 실행할 수 있어 판매자가 돌아오지 않으면 구매자의 리뷰와 거래 이력이 막힌다. 동시에 저장소에는
스플래시 이탈, 로그인 벽, 위치 거부, 빈 결과, 단계별 거래 이탈을 연결하는 제품 퍼널 계측이 확인되지 않았다.

이 상태에서는 “사용자가 불편해서 나갔는지”, “주변 공급이 없어서 나갔는지”, “판매자가 답하지 않아 거래가 깨졌는지”를 구분할 수 없다.

**서비스 개선**

- 구매자에게 `거래 완료 요청`을 제공하고 판매자에게 확인 알림을 보낸다.
- 약속 시간이 지난 뒤 양측에게 완료·취소를 반복 확인한다.
- 분쟁·노쇼 정책이 정해지기 전에는 자동 완료하지 않는다.
- 빈 결과 사용자에게 전체 지역 탐색과 키워드 알림을 연결해 재방문 이유를 만든다.
- 한 개 파일럿 구의 매물 수·응답시간·거래 닫힘률을 앱 릴리스와 별도의 운영 지표로 관리한다.

**성공 판정**

- 판매자가 앱을 닫아도 구매자가 완료 요청을 시작하고 상태를 추적한다.
- 수락된 약속의 80% 이상이 완료 또는 명시적 취소로 닫힌다.
- 구역·카테고리별 빈 결과와 거래 단계별 이탈을 하나의 퍼널로 본다.

## 4. 권장 정보구조

### 권장안 — 마켓 우선 5개 탭

| 탭 | 사용자 목적 |
|---|---|
| 마켓 | 매물 발견·검색·목록/지도 전환 |
| 동네가게 | 정비·주유·용품점 발견 |
| 채팅 | 문의와 진행 중 거래 관리 |
| 커뮤니티 | 지역 관계와 정보 교환 |
| 나 | 판매글·거래 이력·리뷰·설정 |

일반 홈은 제거하고 마켓을 기본 진입으로 두는 것이 가장 단순하다. 홈을 반드시 유지해야 한다면 다음 세 블록만 남긴다.

1. 내가 지금 처리해야 할 거래
2. 내 주변 또는 파일럿 구의 새 매물
3. 오늘 이동에 필요한 날씨·침수

업체 소식과 커뮤니티 인기 글까지 다시 복제하지 않는다.

## 5. North Star와 퍼널 계측

### 5.1 North Star

단순 DAU, 지도 조회, RP 적립보다 다음 지표가 서비스 가치에 가깝다.

> **파일럿 구에서 주간 활성 구매자·판매자당 정상적으로 닫힌 거래 수**

여기서 “닫힌 거래”는 완료뿐 아니라 양측이 명시적으로 취소한 경우도 포함한다. 그래야 미완료 데이터가 무한히 쌓이지 않는다.

### 5.2 최소 이벤트

| 구간 | 이벤트 |
|---|---|
| 유입 | `landing_view`, `public_listing_view` |
| 인증 | `auth_prompted(reason)`, `auth_completed`, `profile_setup_skipped/completed` |
| 위치·탐색 | `location_prompt_result`, `market_results_loaded(count_bucket, ward_id)` |
| 대화 | `chat_started`, `first_reply` |
| 합의 | `offer_proposed`, `offer_accepted` |
| 약속·이동 | `appointment_proposed`, `appointment_accepted`, `route_result(mode)` |
| 완료·신뢰 | `trade_completion_requested`, `trade_completed`, `review_submitted` |

정확한 좌표, 전화번호, 메시지 본문은 분석 이벤트에 저장하지 않는다. `ward_id`, 결과 건수 구간, 진입 경로면 충분하다.

### 5.3 초기 파일럿 게이트

현재 성과가 아니라 첫 2주 베이스라인을 위한 제안값이다.

| 지표 | 초기 게이트 |
|---|---:|
| 첫 세션 실제 매물 도달률 | 70% 이상 |
| 첫 실제 매물 노출 시간 | p75 3초 이내 |
| 핵심 카테고리 0건 결과율 | 20% 미만 |
| 운영시간 첫 판매자 응답 | 중앙값 30분 이내 |
| 가격 수락→약속 수락 | 50% 이상 |
| 수락 약속의 완료·취소 닫힘률 | 80% 이상 |
| 경로 성공 또는 정상 폴백 | 99% 이상 |
| 활성 사용자 D7 | 베이스라인 후 개선 목표 확정 |

## 6. 검증 순서 — 큰 기능보다 작은 가설부터

### 실험 1 · 가입 전에 보여주면 활성화가 오르는가

- 변경: 공개 매물 목록·상세.
- 비교: 현행 로그인 선행 vs 행동 시 로그인.
- 성공: 첫 매물 도달률 상승, 채팅 시점 인증 완료율 유지 또는 상승.

### 실험 2 · 전체 지역 폴백이 빈 앱 인식을 줄이는가

- 변경: 0건에서 전체 지역 보기 + 키워드 알림.
- 성공: 빈 결과 직후 세션 종료 감소, 7일 내 알림 재방문 증가.

### 실험 3 · 거래 단계 스트립이 약속 전환을 높이는가

- 변경: 가격 수락 뒤 DM 상단에 `약속 잡기` 주 CTA.
- 성공: 일반 메시지 왕복 수 감소, 가격 수락→약속 시간 단축.

### 실험 4 · 안전한 장소 후보가 실제 수고를 줄이는가

- 변경: 공개 장소 후보 3개와 양측 ETA.
- 성공: 장소 수정 횟수와 약속 취소율 감소, 사용자 인터뷰에서 다른 지도 검색 감소.

한 실험의 결과를 보기 전에 다음 대형 기능을 쌓지 않는다.

## 9. 하지 말아야 할 투자

- 첫 가치와 거래 성사 퍼널을 고치기 전에 RP·뱃지·가챠를 확대하지 않는다.
- 한 개 구의 공급과 응답 속도가 확보되기 전에 광고 상품을 확장하지 않는다.
- 안전한 만남 후보의 효과를 보기 전에 완전한 턴바이턴 내비게이션부터 크게 만들지 않는다.
- 전화 인증을 없애지 않는다. 사용자 의도가 생긴 게시 직전으로 옮기고 초안을 보존한다.
- 분쟁 정책 없이 자동 거래 완료를 만들지 않는다.
- 홈에 새로운 요약 카드를 더하지 않는다.

## 10. 결론

Saigon Rider의 기술적 거래 뼈대는 이미 존재한다. 상용화의 병목은 기능 수가 아니라 다음 세 가지다.

1. **사용자가 가입 전에 실제 가치를 볼 수 있는가**
2. **앱이 가격 합의에서 안전한 만남과 완료까지 사용자를 이끄는가**
3. **한 개 구에서 공급·응답·완료가 실제로 개선되는지 측정할 수 있는가**

이 세 가지를 닫기 전의 전면 공개는 사용자 획득비를 써서 이탈 원인을 학습하지 못하는 상태가 된다.
반대로 한 개 구 파일럿에서 이 여정만 검증하면, 새 대형 기능 없이도 서비스의 존속 가능성을 판단할 수 있다.
