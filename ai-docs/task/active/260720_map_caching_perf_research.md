# 동네지도 클라이언트 캐싱 + 렌더 성능 조사 (2026-07-20)

read-only 조사 문서. 코드 수정 없음. 근거는 전부 파일:라인.

## 배경 요구사항 (재확인)
1. POI/랜드마크를 앱 실행 시 캐싱, TTL 1시간.
2. 지도 지오메트리도 캐싱 검토 — 인터랙션 경험 저하.
3. 이미 캐싱돼 있다면 다른 최적화 전략 — "지도가 다른 앱 대비 느리다"는 체감.

**결론 선반영**: POI는 **캐싱 전혀 없음**(매 bbox 변경마다 재조회) — 캐싱 도입이 유효한 개선. 지도 지오메트리(depth2/depth3)는 **세션 내 메모리 캐시가 이미 있음**(ward 단위, 재조회 안 함) — 다만 (a) 콜드 재시작 시 캐시 소멸 + HTTP 캐시 헤더 미설정, (b) 캐싱과 무관하게 **렌더링(DOM 노드 수)이 인터랙션 지연의 유력 원인**으로 보임. 즉 사용자 3번 관찰("느리다")은 캐싱 문제가 아니라 렌더 성능 문제일 가능성이 높다.

### 요약
- **POI/업체/매물/피드: 캐싱 0.** 사용자가 요청한 "TTL 1시간 캐싱"은 실제로 아직 구현돼 있지 않음 — 도입 여지 있음.
- **지도 지오메트리: 세션 메모리 캐시 이미 있음.** ward 재방문 재요청 없음. 개선 여지는 "콜드 스타트 영속화"와 "HTTP 캐시 헤더" 정도 — 근본적 데이터 재조회 문제는 아님.
- **사용자가 느끼는 "인터랙션 반응 저하"는 캐싱 미스가 아니라 §2의 렌더링 병목일 가능성이 높다** — 캐시된 데이터라도 매 렌더마다 수천 개 SVG DOM 노드를 그리는 구조이기 때문.

## §2. 성능 병목 진단

### 2-1. SVG DOM 노드 규모 (유력 후보, 근거 있음)

depth3.json 37개 ward 실측(`python3` json 파싱):

| 항목 | 평균/ward | 최대(an-khanh) |
|---|---|---|
| 건물(bldg) | 684 | 1,923 |
| 도로(roads) | 870 | 1,708 |
| 수면(water) | 13 | 126 |
| 하안선(wline) | 8 | 47 |

렌더 코드(`SaigonMapV5.tsx:940-970`)에서 화면에 들어온(`wardInView`) **각 ward의 전체 배열을 그대로 `.map()`** — ward 단위로만 컬링하고, ward 내부 개별 피처의 뷰포트 내/외 여부는 필터링하지 않음(`SaigonMapV5.tsx:950,958,960,964` — `d.d3.water`/`d.d3.bldg`/`d.d3.roads` 전체를 map).

- 건물은 폴리곤 1개 = DOM 노드 1개. 그림자(`bldgShadow`)가 켜지면(`SaigonMapV5.tsx:812` — `vb.w < L3_VBW * 0.5`, **더 깊이 줌인할수록** 켜짐) 건물 노드가 **2배**(`953-957`).
- 도로는 2-pass 렌더(`959-967`) — casing(있는 경우) + fill 각각 별도 `<polyline>` = 도로 1개당 최대 **2개** DOM 노드.
- 평균 ward 1개 기준 추정 DOM 노드: 건물 684~1,368(그림자 포함 시) + 도로 최대 1,740 + water/wline 21 ≈ **약 2,500~3,100개**. 최대 ward(an-khanh)는 그림자 포함 시 **약 7,000개**.
- 뷰포트가 ward 경계 근처에 있으면 2~3개 ward가 동시에 화면에 걸쳐 각각 이 수량을 렌더 — 순간 DOM 노드가 **1만 개 이상**까지 갈 수 있음(추정, 실측 미실시).

**체감 영향(추정): 높음.** 수천~1만 개의 SVG 도형 노드는 (a) 최초 마운트/ward 전환 시 React가 한 번에 삽입 → 레이아웃/페인트 비용, (b) WKWebView/Android WebView는 데스크톱 Chrome 대비 SVG 래스터화 성능이 낮아 팬/핀치 중 브라우저 자체 리페인트가 프레임을 깎아먹을 가능성. 단 아래 2-2에서 보듯 팬/핀치 자체는 React 리렌더를 안 일으키므로(이미 최적화됨), 문제는 "React 리렌더" 보다 "브라우저가 그 순간 화면에 유지해야 하는 SVG 노드 수" 쪽에 가깝다.

**확인 방법**: Chrome DevTools remote debug(Android WebView 연결) → Performance 탭에서 팬 제스처 캡처 → Layout/Paint 항목 시간, `document.querySelectorAll('svg *').length`로 실제 노드 수 카운트.

### 2-2. 리렌더 트리거 (이미 최적화 — 병목 아님, 확인용으로 기록)

- 팬/핀치 중에는 `setVBAttr`(`SaigonMapV5.tsx:314-319`)이 viewBox를 **DOM 속성으로 직접** 설정하고 React state(`vbSnap`)를 건드리지 않음(주석 `317`: "팬/핀치 중에는 vbSnap 재렌더가 없으므로"). `vbSnap`은 LOD 게이트를 넘거나 제스처가 끝났을 때만 증가(`setVbSnap` 호출 지점 9곳, 모두 이산 이벤트 — 마운트/포커스/게이트 전환/제스처 종료).
- 라벨 디클러터(`visibleLabelIds`, `865`)도 `vbSnap` deps라 제스처 종료 시 1회만 재계산 — 사용자가 언급한 "최근 라벨 디클러터" 최적화는 사실 확인됨, OK.
- 컴포넌트 자체가 `memo(SaigonMapV5)`(`1263`)로 감싸져 있어 부모(NeighborhoodMap) 리렌더가 props 불변이면 전파되지 않음.
- **결론**: React 리렌더 빈도는 이미 잘 억제돼 있음 — 이 축은 추가 최적화 여지가 크지 않음.

### 2-3. 페치 블로킹 (부분적 후보)

- ward 전환 시 `loadWardData`가 depth2(+필요 시 depth3) fetch를 병렬로 날리고(`SaigonMapV5.tsx:414-449`) 완료 후 `setWardData` → 리렌더. fetch 자체는 비동기라 인터랙션(팬/줌)을 블로킹하지 않지만, **응답이 오면 그 순간 새 ward의 수백~수천 노드를 한 번에 mount**하는 리렌더가 발생 — 이때 프레임이 끊길 수 있음(2-1과 결합된 문제).
- depth3 파일 크기(평균 ~130KB, 최대 364KB, `du -sh` 실측)는 로컬/CDN 정적 파일이라 순수 네트워크 왕복 자체는 크지 않을 것(추정) — 병목이라면 파싱+DOM 마운트 쪽이지 네트워크 쪽이 아닐 가능성.

**체감 영향(추정): 중간.** "느리다"의 원인이 바로 이 순간(신규 ward 진입 직후 프레임 드랍)일 가능성 있음.

### 2-4. 좌표 변환/레이아웃 계산

- `clampVB`/`applyZoom`(`333-365`) 등은 매 프레임 호출되지만 산술 연산뿐 — `getBBox`/DOM 측정 호출은 `updateAnchorOverlay`(`288-312`, 말풍선 오버레이 위치 계산, 팬마다 호출)에서 `el.offsetWidth`/`offsetHeight` 읽음. 이건 이미 렌더된 오버레이 엘리먼트 1개뿐이라 강제 리플로우 비용은 낮을 것(추정) — 병목 후보 아님.

### 진단 요약 (유력도 순)
1. **SVG DOM 노드 과다 (건물+도로, ward당 최대 ~7,000개, 그림자·2-pass 도로가 배수)** — 가장 유력. 코드 근거 확실(§2-1), 체감 영향은 추정.
2. **신규 ward 데이터 도착 시 대량 마운트로 인한 프레임 드랍** — 유력, §2-1과 결합.
3. 리렌더 빈도·좌표계산은 이미 잘 억제됨 — 병목 아님(확인 완료).

## §3. 캐싱 + 최적화 전략 옵션

**아키텍처 제약 (감독 지시, 필수 반영)**: 동네지도는 이미 프론트 컴포넌트/백엔드 코어/API 계약으로만 연결되는 별도 모듈로 분리돼 있다. 캐싱을 도입한다면 **지도 모듈 내부에 캡슐화**해야 한다 — 즉 `frontend/src/api/poi.ts`, `frontend/src/components/maps/*`, `frontend/src/pages/map/*` 등 지도 모듈 파일 안에서만 사는 캐시 계층(모듈 스코프 변수, 지도 전용 훅/유틸)으로 구현하고, 앱 전역 React Query client·전역 Zustand 스토어(`useLocationStore`/`useUserStore` 같은 전역 상태)에 지도 캐시를 얹거나 앱 전체 공용 캐싱 인프라를 신설하는 방식은 **채택하지 않는다** — 아래 각 옵션에도 이 원칙을 반영했다(전역 인프라 방식은 "비추천 대안"으로만 언급).

### 3-A. POI 캐싱 (TTL 1시간) — 신규 도입 (§1에서 "캐싱 없음" 확인됨)

| 옵션 | 효과 추정 | 구현 스케치 | 영향/위험 | 공수 |
|---|---|---|---|---|
| **In-memory 모듈 스코프 캐시 + TTL** (권장 후보 1) | bbox 재방문 시 재조회 제거. 콜드 재시작에는 무효(추정 — 세션 내 이득만) | `poi.ts` 파일 안에 모듈 스코프 `Map<bboxKey, {items, fetchedAt}>`를 두고 `fetchPoiMapItems` 호출 전 TTL(1h) 체크 후 hit면 즉시 반환 — `SaigonMapV5.tsx`의 `cacheRef`(ward geometry 캐시, `256`)와 완전히 동일한 패턴이라 지도 모듈 내부에서 자족적으로 캡슐화된다. bbox 키는 반올림된 격자 셀 단위로 정규화(연속값 bbox를 그대로 키로 쓰면 캐시 히트율 0에 수렴) | `NeighborhoodMap.tsx:599-613` 이펙트는 그대로, `poi.ts` 내부만 변경 — 호출부 무변경, 지도 모듈 경계를 벗어나지 않음. 회귀 위험 낮음 | 낮음 (반나절) |
| **영속 캐시(localStorage/IndexedDB)** | 콜드 재시작에도 즉시 표시(그 다음 백그라운드 갱신) 가능 — "앱 실행 시 캐싱" 요구를 문자 그대로 만족 | stale-while-revalidate: 저장된 캐시 있으면 즉시 `setPoiItems`(오래돼도 우선 보여줌) + 병렬로 fetch해 갱신 시 덮어쓰기. TTL 1h는 "완전 재조회를 강제하는 하드 만료"가 아니라 "이 이후엔 백그라운드 갱신을 반드시 트리거"하는 신호로 쓰는 편이 UX상 낫다(사용자 요구의 "TTL 1h" 의도 — POI가 바뀔 수 있으니 — 를 만족하면서 화면 깜빡임/빈 상태 없음). localStorage 키는 지도 모듈 전용 네임스페이스(`VIEWPORT_KEY`/`RECENT_SEARCH_KEY`처럼 `sgr.map.*` 접두, `NeighborhoodMap.tsx:52,55` 기존 관례 준수)로 한정 — 앱 전역 storage 스키마에 얹지 않는다 | bbox 격자 키가 여러 개 생기므로 저장 용량 관리 필요(오래된 키 정리) | 중간 (1일) |
| **앱 실행 시 전체 프리페치** | 이번 감사에서 POI 전체 규모(총 row 수)를 확인 못함 — `backend/app/routers/map/poi.py:45` 서버가 bbox당 `limit(200)`만 반환하는 걸 보면 전역 규모가 작지 않을 가능성. 규모 모르는 채로 "전체 프리페치"를 권하기엔 근거 부족 | (규모 확인 후 결정, 프리페치를 하더라도 지도 모듈 마운트 시점의 모듈 내부 호출로 — 앱 부트스트랩 레벨 전역 프리페치 훅으로 만들지 않는다) | 규모가 크면 오히려 초기 로드 지연 유발 — 역효과 가능 | 규모 확인 전까지 보류 |
| *(비추천 대안)* 앱 전역 React Query client 도입 | bbox 캐시·TTL·재검증을 라이브러리가 대신 해주므로 구현은 더 간결해질 수 있음 | 앱 루트에 `QueryClientProvider` 신설, `fetchPoiMapItems`를 `useQuery`로 래핑 | **감독 제약 위반** — 지도 모듈 경계를 넘어 앱 전역 인프라(새 provider, 새 의존성)를 신설하게 되고, 다른 화면(매물/피드/업체)도 같은 client를 공유하게 되면 지도 모듈이 "프론트 컴포넌트/API 계약으로만 연결" 원칙에서 벗어남 | 채택 안 함 |

**추천**: bbox 재방문 캐시(옵션1)를 먼저, 이어서 stale-while-revalidate 영속화(옵션2)를 확장 — 둘 다 지도 모듈 파일(`poi.ts`) 내부 구현으로 끝난다. 전체 프리페치는 POI 총량 확인 후 재검토(§4 결정 필요 항목). React Query 등 전역 인프라 도입은 감독 제약상 배제.

| 옵션 | 효과 추정 | 구현 스케치 | 현행코드 영향 | 회귀위험 | 공수 |

## §4. 미결정 / 사용자 결정 필요

0. **(제약, 결정 완료 — 구현 시 반드시 준수)** 캐싱은 지도 모듈 내부에 캡슐화한다. 대상 파일은 `frontend/src/api/poi.ts`, `frontend/src/components/maps/SaigonMapV5.tsx`, `frontend/src/pages/map/NeighborhoodMap.tsx` 등 지도 모듈 경계 안으로 한정 — 앱 전역 React Query client, 전역 Zustand 스토어(`useLocationStore`/`useUserStore`), 범용 서비스워커 등 앱 전체 인프라에 지도 캐시를 얹지 않는다. §3-A/§3-B의 각 옵션은 이미 이 제약을 반영해 "모듈 스코프 변수/훅" 형태로만 기술했다 — 향후 구현 단계에서 이 경계를 벗어나는 방식(예: 전역 provider 신설)이 필요해 보이면 구현 전에 재확인할 것.

1. **POI 총 데이터 규모** — bbox당 `limit(200)`(`backend/app/routers/map/poi.py:45`)만 확인, 전체 row 수는 미확인. "앱 실행 시 전체 프리페치" 실익 판단에 필요 — DB에서 `SELECT count(*) FROM poi WHERE published` 확인 요망.
2. **POI 캐시 정책: 하드 TTL vs stale-while-revalidate** — 사용자 원 요구는 "TTL 1시간"이지만, §3-A에서 제안한 SWR(캐시 즉시 표시 + 백그라운드 갱신) 쪽이 UX상 나을 수 있음. 어느 쪽을 원하는지 결정 필요.
3. **POI 캐시 영속 계층** — in-memory(세션 내만) vs localStorage/IndexedDB(콜드 재시작에도 유지) 중 어디까지 갈지. "앱 실행 시 캐싱"이라는 표현이 콜드 스타트 캐시까지 포함하는 의도인지 확인 필요.
4. **depth2/3.json 배포 방식** — nginx 장기 캐시(`expires 1y immutable`) 적용 시, ward geometry 파일이 수정 배포될 때 URL이 바뀌는지(파일명 해시 등) 아니면 같은 경로를 덮어쓰는지 확인 필요. 덮어쓰기 방식이면 장기캐시 도입 시 캐시 무효화 수단(쿼리 버전 등)을 반드시 같이 넣어야 함 — 배포 파이프라인 확인 필요.
5. **뷰포트 컬링 강화의 정확도 기준** — 화면 경계에서 폴리곤이 잘려 보이지 않게 하는 여유 마진을 얼마로 둘지(성능 vs 정확도 트레이드오프)는 실측(DevTools Performance) 후 조정값 결정 필요.
6. **그림자/도로 2-pass 축소가 시각 품질에 미치는 영향** — 디자인 판단 필요, 카파시 원칙상 Fable 검토 권장.

## §5. 빠른 개선(low-hanging) vs 큰 개선

### 빠른 개선 (낮은 공수, 낮은 위험)
- POI in-memory bbox 캐시 + TTL 1h (§3-A 옵션1) — `poi.ts` 내부만 수정, 호출부 무변경.
- nginx `.json` 장기 캐시 헤더 추가 (§3-B) — 단, §4-4(배포 방식) 확인 후.
- 도로 casing 렌더 조건 완화 검토 (§3-C 옵션3) — 이미 부분 적용된 패턴 확장.

### 큰 개선 (중간~높은 공수, 검증 필요)
- ward 내부 피처 단위 뷰포트 컬링 (§3-C 옵션1) — 렌더 병목의 근본 해결책으로 추정되나 전처리·경계 마진 설계 필요.
- POI 영속 캐시 + stale-while-revalidate (§3-A 옵션2) — "앱 실행 시 캐싱" 요구를 문자 그대로 만족시키려면 이 단계까지 필요.
- 건물 그림자 렌더 방식 변경 (§3-C 옵션2) — 디자인 트레이드오프 포함.
- 캔버스 스냅샷화 (§3-C 옵션4) — 효과는 크지만 공수·회귀 범위가 가장 큼, 뷰포트 컬링만으로 부족할 때 재검토.
