## 1. 근본 원인 — 폴백 규칙이 "화면 성격"을 구분하지 않는다

`service-rules.md` §폴백 정책의 표는 **전 화면 단일 규칙**이다.

| 상황 | 결과 mode | `coordsSource` | 기준 좌표 |
|---|---|---|---|
| 측위 성공 & 서비스 권역 밖 | `gps` | `fallback` | `BEN_THANH_FALLBACK`(중심가) |

이 규칙이 만들어진 맥락은 **"목록이 통째로 빈다"** 는 문제였다 — 즉 *탐색형 화면* 얘기다. 같은 규칙을 경로안내에 적용한 것이 이번 결함의 근본 원인이다.

**판정 축을 하나 추가한다: 위치 데이터가 그 화면에서 어떤 역할인가.**

| 계층 | 위치의 역할 | 해당 화면 | 권역 밖 처리 | 근거 |
|---|---|---|---|---|
| **탐색형** (browse) | 조회 기준점 (결과를 좁히는 필터) | 홈·마켓·동네지도·정보 목록(주유/정비/날씨/침수) | **현행 유지** — 중심가 폴백 + 사유 토스트 | 폴백해도 결과가 거짓이 아니다. "호치민 중심가 매물 39건"은 사실이다 |
| **실행형** (act) | **입력값** (내 위치가 결과를 결정) | 경로안내(`RideNav` nav)·퀘스트 수행(`RideNav` quest) | **차단** + 사유별 안내 | 폴백하면 **거짓 결과**를 준다. 내가 있지 않은 곳에서 출발하는 경로는 안내가 아니다 |
| **기록형** (record) | **저장값** (DB에 영속) | 침수/주유/정비 제보, 피드 위치 태그 | **차단** (폴백은 데이터 위조) | 폴백 좌표를 제보로 저장하면 DB 오염 — 어드민 수동 삭제만이 복구 수단 |

**핵심**: 대표 지시는 실행형·기록형에만 적용한다. 탐색형까지 차단하면 2026-08-06에 고친 회귀("모든 화면이 아무 설명 없이 Bến Thành 으로 수렴" / "목록이 통째로 빈다")가 재발한다.

## 2. 확정 결정 (D-1 ~ D-6)

### D-1. 차단 화면의 Google 지도 핸드오프 — ⚠️ 대표 승인 대기

**권고: 사유별로 분기한다.**

| 차단 사유 | Google 버튼 | 근거 |
|---|---|---|
| 권역 밖(`outside_area`) | **제거** | "우리 서비스 범위가 아니다"가 메시지인데 대안 앱을 주면 그 메시지가 무너진다 |
| 측위 실패(권한/타임아웃/불가) | **유지** | 원인이 우리 쪽(신호·권한)이므로 대안 제공이 사용자 이익에 맞다 |

브랜드·서비스 정체성 판단이 섞여 있어 이 항목만 대표 결재 대상으로 남긴다. 미승인 시 기본값은 위 권고안.

### D-2. 권역 밖 경로안내 → 완전 차단 (경고 후 강행 불가)

- 오토바이 주행 중 잘못된 경로는 **안전 문제**다.
- 경로 API(Google Routes)는 **호출당 과금** — 무의미한 호출에 비용이 나간다(현행은 이탈 재탐색으로 건당 최대 3회).
- "정확도 보장 못 함" 경고 후 허용은 채택하지 않는다. 사용자가 경고를 읽고도 주행 중 경로를 신뢰하는 것이 정상 행동이므로, 경고는 책임 회피일 뿐 결함을 막지 못한다.

### D-3. 측위 실패도 차단 — 단 사유별 문구 분리

`classifyLocationError`(`RideNav.tsx:43-49`)가 이미 3분류(`permission`/`timeout`/`unavailable`)를 하고 있으므로 그대로 재사용한다. 여기에 **정확도 미달(`inaccurate`)** 을 4번째 사유로 추가한다(§D-5).

**필수 추가**: `permission` 사유에는 **OS 설정 앱 딥링크 버튼**이 있어야 한다. 현행은 "설정에서 위치 권한을 허용해 주세요" 문구만 있고(`RideNav.tsx:684`) 이동 수단이 없어 사용자가 앱 안에서 탈출할 수 없다.

### D-4. 안내 중 권역 이탈 → 진행 중 건은 끝까지 안내

- 시작 시점에 권역 안이었다면 외곽으로 나가는 것 자체가 **정상 주행**이다(호치민 → 근교).
- 주행 중 안내를 끊는 것이 더 위험하다.
- 대신 `watchLocation` 콜백의 **이탈 판정만** 권역 밖 tick 에서 스킵한다 — `useLocationStore.ts:272`가 이미 하는 것과 동일한 처리를 `RideNav` 에도 적용(현재 비대칭).

### D-5. 정확도 게이트를 최초 측위에도 적용

현행은 watch tick 에만 `accuracy > GPS_ACCURACY_LIMIT_M(35m)` 게이트가 있고(`RideNav.tsx:299`), 최초 측위(`fetchRoute` → `resolveOrigin`)에는 없다. 실내에서 오차 2km 좌표로 경로를 계산하면 밖에 나가는 순간 이탈이 확정된다.

**동일 임계값(35m)을 최초 측위에도 적용**하고, 미달 시 `inaccurate` 사유로 차단 + 재시도 유도한다.

### D-6. 퀘스트는 "수행 시작" 단계에서 차단

- 보상이 걸려 있어 **어차피 서버가 인정하지 않는다**(진행도 검증 = Engine).
- 현행은 시작은 되고 진행도만 영구히 0 → 사용자는 이유를 모르고 시간을 버린다.
- 차단 지점은 `RideNav` 진입 후가 아니라 **`QuestDetail` 의 "수행 시작" 버튼**(`QuestDetail.tsx:97`) — 세션을 만들기 전에 막아야 서버에 고아 세션이 남지 않는다.

## 3. 구현 설계 — 판정을 한 곳으로 모은다

### 3-A. 현행 문제

`inServiceArea` 호출부가 **11곳**에 흩어져 각자 다르게 처리한다(`serviceArea.ts:38` 기준 grep). 같은 상황에 화면마다 다른 결과가 나오는 구조적 원인이다.

- `SaigonMapV5.tsx:517` — 폴백이면 내 위치 점을 **안 찍는다**(`noMeDot`)
- `RideNav.tsx:366` — 폴백이어도 내 위치 점을 **찍는다** → §4 결함 #1의 직접 원인
- `InfoFloodReport.tsx:42` — 검사 자체가 **없다** → §4 결함 #7

### 3-B. 확정 설계

`lib/serviceLocation.ts` 에 실행형·기록형 전용 게이트를 신설한다. **기존 `resolveServiceLocation`(중심가 폴백)은 탐색형 전용으로 존치**하되, 용도가 이름에 드러나게 한다.

```ts
export type LocationGateReason =
  | 'outside_area' | 'permission' | 'timeout' | 'unavailable' | 'inaccurate';

/**
 * 실행형·기록형 화면 전용 — 폴백하지 않는다. 실패 시 사유를 반환하고 호출부가 차단 UI 를 띄운다.
 * 탐색형(홈·마켓·동네지도·정보 목록)은 종전대로 resolveServiceLocation() 을 쓴다.
 */
export function requireServiceLocation(): Promise<
  | { ok: true; coords: Coords }
  | { ok: false; reason: LocationGateReason }
>;
```

- 정확도 판정(D-5)이 이 함수 한 곳에 들어가 §4 결함 #4가 자동으로 닫힌다.
- 사유 4종은 `classifyLocationError` 를 그대로 재사용 — 새 분류 체계를 만들지 않는다.
- 차단 UI 는 공통 컴포넌트 1개(`components/location/LocationGateBlock.tsx`)로 두고 사유만 넘긴다. 화면마다 문구를 따로 쓰면 다시 갈린다.

### 3-C. 불변식 (회귀 방지)

1. **실행형·기록형 화면은 `BEN_THANH_FALLBACK` 을 import 하지 않는다.** import 가 있으면 폴백 경로가 살아 있다는 뜻이다 — 린트 규칙 후보.
2. **`origin` 과 `dotPos` 는 항상 같은 출처여야 한다.** 하나는 폴백, 하나는 실측인 상태를 만들지 않는다(결함 #1의 정의).
3. **`native.getLocation()` 직접 호출 금지** — `service-rules.md` 원칙 4가 이미 규정. 현재 9곳 위반(§4 결함 #11).

## 6. `service-rules.md` 개정 문안 (구현 시 반영)

§폴백 정책 절 앞에 다음을 삽입한다:

> ### 폴백 적용 범위 — 화면 계층 (2026-08-13 개정, 대표 지시)
>
> 아래 폴백 정책표는 **탐색형 화면에만** 적용한다. 위치가 입력값이거나 저장값인 화면은 폴백하지 않고 **차단**한다.
>
> | 계층 | 화면 | 권역 밖·측위 실패 |
> |---|---|---|
> | 탐색형 | 홈·마켓·동네지도·정보 목록 | 폴백표대로 (중심가 / `'all'`) |
> | 실행형 | 경로안내·퀘스트 수행 | **차단** — `requireServiceLocation()` |
> | 기록형 | 제보(침수/주유/정비)·피드 위치 태그 | **차단** — 폴백 좌표 저장은 데이터 위조 |
>
> 실행형·기록형 화면은 `BEN_THANH_FALLBACK` 을 import 하지 않는다. `origin` 과 화면에 찍히는 내 위치 점은 **항상 같은 출처**여야 한다 — 하나는 폴백 하나는 실측인 상태가 카메라 튐(2026-08-13 대표 보고)의 원인이었다.
>
> 안내 **중** 권역 이탈은 차단하지 않는다 — 시작 시점에 권역 안이었다면 외곽 주행은 정상이다. 이탈 판정 tick 만 스킵한다(원칙 7과 동일 처리).

원칙 8("여전히 유효한 GPS 경로: 경로안내, 제보")도 위 계층 분류를 참조하도록 개정한다.
