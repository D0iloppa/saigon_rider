## 0. 한 장 요약

지금 마켓 기본 정렬은 **최신 등록순(`bumped_at DESC`)** 하나뿐이고, 홈 화면이 "내 주변 인기 상품"이라는 라벨로 부르는 섹션도 실은 인기순이 아니라 **거리순**이다(`HomePage.tsx:257` `sort: 'distance'`) — 라벨과 실제 정렬 기준이 어긋나 있다. 문제는 정렬 로직 자체보다 **"사용자가 실제로 어떻게 찾는지"를 증명할 데이터가 이 서비스에 전혀 없다는 것**이다 — 퍼널 계측 0건, 조회 이력/최근 본 매물 저장 0건. 매물 213건 중 188건(88%)이 단일 계정 소유인 콜드스타트 상태에서 정교한 개인화 랭킹을 설계하는 것은 과설계다. 제안은 (1) 지금 있는 재료(거리·카테고리·`view_count`/`like_count`)로 즉시 가능한 저비용 조정, (2) 계측 후에만 판단 가능한 것, (3) 공급이 늘어야 의미 있는 것 3단으로 나눈다.

## 2. 이미 다른 세션이 진행 중인 변경 (`git diff` 확인, 중복 제안 방지용)

워킹트리에 **커밋되지 않은 마켓 UI 변경**이 있다. 아래는 리스트 구성 관점에서 이미 착수된 것 — 이번 제안에서 재차 올리지 않는다.

- **정렬/카테고리 시각적 위계 분리** — 정렬을 고정 pill로, 카테고리를 별도 가로 스크롤 레일로 분리(`MarketMain.tsx:483-512`, `MarketMain.module.css` `.filterRow`/`.sortChip`). 스크롤 밀림 시에만 좌측 마스크 페이드(`handleRailScroll`). 이건 "정렬 기준이 뭔지 보이게" 만드는 시각 작업으로, 본 보고서가 제안할 "정렬 옵션 자체를 바꾸자"는 것과는 다른 층위 — 겹치지 않는다.
- **썸네일 확대(104→128px) + 카드 레이아웃 재정렬** — 가격을 메타 바로 아래로 붙이고, 반응 카운트(찜/채팅)를 카드 우하단으로 이동(`ListingCard.tsx`, `ListingCard.module.css`). 정보 밀도·시각 스캔 개선이며, 카드에 **어떤 정보를 넣을지**(view_count 등)는 본 보고서 §6에서 별도로 다룬다.
- **키워드 알림을 바텀시트 → 전용 페이지로 승격**(`/market/keyword-alerts`) — `MarketMain.tsx`에서 `alertOpen`/`alerts`/`addKeywordAlert` 등 인라인 상태를 통째로 제거하고 `navigate('/market/keyword-alerts')`로 전환. 이 페이지 자체(신규 파일)는 이번 diff에 파일 목록으로 보이지 않아 미검증 — 라우트만 확인.
- **정렬 라벨 번역 수정**: "가격 낮은순/높은순" → "저가순/고가순" (`translation.json`).
- **ProfileMain.tsx의 피드 카드 클릭 라우팅 정리** — 마켓과 무관(개인 피드 이미지 뷰어를 인라인 모달에서 페이지 이동으로 전환). 본 보고서 범위 밖.

## 3. 제약 인정

- **매물 공급 0에 가까움** — 213건 중 188건(88%)이 단일 계정 `SaigonRider` 소유(감사 티켓 실측치, 이번 세션 재검증 안 함). 실사용자 공급 매물이 극소수라, "인기순"이든 "개인화순"이든 정렬을 바꿔도 **체감 차이가 거의 없을 규모**다.
- **조회패턴 실증 데이터가 이 서비스에는 존재하지 않는다.** 퍼널 계측(`trackEvent`/PostHog/Mixpanel/Amplitude) grep 결과 0건, 최근 본 매물·검색 이력 테이블도 없다. 즉 "사용자들은 보통 거리순으로 본다" 또는 "가격 낮은 순을 많이 쓴다" 같은 주장은 **이 코드베이스 안에서는 근거가 없다** — 아래 모든 제안은 (i) 업계 통용 패턴, (ii) 우리 데이터 구조상 가능한 것, (iii) 계측 필요 항목으로 명확히 구분해 표기한다.
- 서비스 대상은 호치민 현지 사용자, Capacitor WebView 모바일 하이브리드 — 데스크톱 UX 참고는 제한적으로만 참조.
- district/ward 기반 서비스 권역 개념은 이미 코드에 있다(`useLocationStore`, `resolveDistrict`) — 위치 축은 재료가 있는 유일한 "개인화" 신호다.

**정직한 한계**: 세 서비스 모두 카드 노출 정보·명시적 콜드스타트 처리 로직에 대한 1차 출처(공식 디자인 문서·기술 블로그)를 찾지 못했다. 확인된 것은 "첫 화면 기준이 최신순 단일에서 다변화/개인화로 진화해 왔다"는 방향성 정도이며, 이는 **공급이 풍부한 성숙 서비스의 이야기**다 — 매물 213건(그마저 88%가 한 계정) 규모에는 그대로 적용할 근거가 아니다.

## 5. 제안

각 제안에 **데이터 존재 여부 / 구현 규모 / 콜드스타트 동작 여부**를 표기한다.

### 5-A. 지금 데이터로 바로 가능

1. **홈 "내 주변 인기 상품" 라벨을 실제 정렬과 맞추기**(라벨을 "거리순"류로 바꾸거나, 실제로 `like_count`/`view_count` 가중 정렬로 바꾸기 중 택1)
   - 데이터: **있음** — `distance` 정렬은 이미 동작 중(`HomePage.tsx:257`), `like_count`/`view_count`도 DB에 있음(`models.py:492-493`).
   - 규모: 라벨만 바꾸면 **한 줄**(`translation.json` 문구), 실제 인기순 정렬을 새로 만들면 백엔드에 `sort=popular`(예: `like_count DESC, view_count DESC`) 분기 추가 — **수십 줄**.
   - 콜드스타트: 라벨 정정은 즉시 동작. 인기순 정렬은 매물이 적으면(213건, 대부분 좋아요 0) **변별력이 거의 없음** — 콜드스타트에서 효과 낮음.
   - 카파시 관점: 라벨 정정이 먼저다. 인기순 정렬 신설은 이 볼륨에서는 과설계에 가깝다.

2. **검색 화면 정렬에 `distance` 옵션 추가**(현재 `recent/price_low/price_high`만 있고 거리순 없음, `MarketSearch.tsx:28`)
   - 데이터: **있음** — 목록 API는 이미 `sort=distance`를 지원(`market.py:387-388`), 검색 화면만 UI에서 빼놓은 상태.
   - 규모: **한 줄~수 줄**(`SORTS` 배열에 추가 + 좌표 전달 배선 확인).
   - 콜드스타트: 위치는 매물 수와 무관하게 항상 존재하는 신호 — 동작함.

3. **카드에 `view_count` 노출 여부 검토**(현재 API 응답엔 있으나 카드에 미노출)
   - 데이터: **있음**(`market.py:581` 응답 포함).
   - 규모: **한 줄**(카드 컴포넌트에 조건부 렌더 추가, `likeCount>0` 패턴과 동일).
   - 콜드스타트: 조회수 0인 매물이 대부분이라(신규 서비스) 오히려 "안 팔리는 매물"처럼 보일 위험 — **득실 불확실, 결정 필요 항목으로 분류**(§9).

### 5-B. 계측 후 가능

4. **"최근 본 매물" 섹션/재노출**
   - 데이터: **없음** — 조회 이력 테이블이 없다(§1-4). `view_count`는 매물당 누적치일 뿐 사용자별 기록이 아니다.
   - 규모: **신규 모듈** — 테이블 신설(`user_id, listing_id, viewed_at`), 상세 진입 시 upsert, 목록/홈에 노출 API 추가.
   - 콜드스타트: 매물 공급과 무관하게 개인 행동 기록이라 **콜드스타트에서도 의미 있음**(오히려 공급 부족 시 "내가 봤던 거 다시 보기"가 재방문 유인이 될 수 있음 — 단, 이는 추정이며 계측 없이 확정 불가).

5. **사용자별 정렬 기본값 기억(마지막 선택 정렬을 다음 방문에 유지)**
   - 데이터: **부분 있음** — 현재도 `localStorage`(`STORAGE_KEY = 'mkt_filter_v3'`)에 세션 범위로 저장하고 있음(`MarketMain.tsx:47,60-73`). 서버 영속(로그인 기기 간 동기화)은 없음.
   - 규모: 클라이언트 유지 확장은 **미미**(이미 거의 되어 있음), 서버 동기화는 **수십 줄**(User 테이블 컬럼 추가 + API).
   - 콜드스타트: 영향 없음(개인 설정이라 매물 수와 무관).

6. **카테고리 선호 기반 정렬/섹션 가중**
   - 데이터: **없음** — 세션 내 필터 상태만 있고 영속 선호 카테고리 필드가 User에 없음(§1-4).
   - 규모: **신규 모듈**(선호도 추론 로직 + 저장 + 정렬 가중).
   - 콜드스타트: 매물이 카테고리당 소수라 가중해도 **체감 차이 거의 없음** — 지금 볼륨에서는 과설계.

### 5-C. 공급 확보 후에나 의미 있는 것

7. **개인화 추천 랭킹(ML/협업 필터링 등)** — 당근이 "고정 노출 → 개인화 모델"로 옮겨간 사례가 있으나, 이는 **일간 활성 매물이 수만~수십만 건 규모일 때** 얘기다. 매물 213건(그중 188건 단일 계정)에 추천 모델을 앉히는 것은 **명백한 과설계**(카파시 #2) — 학습시킬 사용자 행동 데이터도, 변별력을 낼 매물 볼륨도 없다. **제안하지 않는다.**
8. **"방금 등록된 매물" 실시간 배지·긴급 노출** — 등록 빈도가 낮으면(88%가 한 계정) 오히려 반복적으로 같은 판매자만 부각되는 역효과. 공급 다변화 이후 재검토.

## 6. 선행 계측 제안 (방식은 미결 — D-10 계류 중)

**주의: 계측 방식(자체 테이블 vs PostHog/Mixpanel 같은 외부 SaaS)은 감사 티켓 D-10이 미결이라 이 문서에서 확정하지 않는다.** 아래는 방식과 무관하게 "무엇을 찍어야 조회패턴을 알 수 있는가"만 나열한다.

- 목록 화면 진입 시: 진입 경로(홈 섹션 A/B, 마켓 탭, 검색, 딥링크), 초기 정렬값, 표시범위 모드(gps/all)
- 정렬 변경 이벤트: 어떤 정렬로 바꿨는지, 몇 번째 세션 방문에서 바꿨는지(기본값 유지 vs 능동 변경 비율)
- 카테고리 칩 클릭: 어떤 카테고리를 얼마나 자주 누르는지(대분류 선호 분포)
- 카드 클릭 위치: 리스트 내 몇 번째 카드를 눌렀는지(스크롤 깊이 대비 클릭 위치 — "위쪽만 본다"를 검증할 유일한 신호)
- 무한스크롤 도달 깊이: 평균 몇 페이지까지 내리는지
- 검색 사용 여부·키워드: 카테고리 탐색 vs 키워드 검색 중 실제로 뭘 더 쓰는지(현재는 추정 불가)
- 상세 진입 후 이탈 시점: 뒤로가기까지 체류시간(카드 정보만으로 판단이 끝나는지, 상세까지 봐야 하는지)
- 빈 상태 CTA 클릭률: "전체 지역에서 찾아보기" vs "키워드 알림 받기" 중 어느 쪽을 더 쓰는지(§ B-2 표시범위 3km 문제와 직결)

## 7. 단계별 착수안

- **지금 당장 가능** (§5-A): 홈 "인기 상품" 라벨 정정(또는 실제 인기순 전환 여부 대표 결정), 검색 화면에 거리순 옵션 추가. 코드 변경 규모 작고 회귀 위험 낮음.
- **계측 후** (§5-B, §6): 최근 본 매물, 사용자별 정렬 기본값 서버 동기화, 카테고리 선호 가중 — 계측 방식(D-10) 결정과 최소 1~2주 실사용 데이터 축적이 선행돼야 방향을 정할 수 있다.
- **공급 확보 후**: 개인화 랭킹, 실시간 긴급 노출류(§5-C) — 매물 공급이 단일 계정 의존을 벗어나기 전까지는 착수 자체가 낭비.

## 8. 미결정 사항 (대표 결정 필요)

1. 홈 "내 주변 인기 상품" — **라벨만 정정**(정렬은 거리순 유지) vs **실제 인기순 정렬로 전환**(`like_count`/`view_count` 가중). 후자는 매물 수가 적어 효과가 제한적이라는 트레이드오프가 있다.
2. 카드에 `view_count`(조회수) 노출 여부 — 신뢰 신호가 될 수도, "안 팔리는 매물" 낙인이 될 수도 있다. 노출한다면 임계치(예: N회 이상만 노출) 필요 여부도 함께 결정 필요.
3. 검색 화면에 `distance` 정렬을 추가할지, 아니면 검색은 키워드 관련도 중심으로 남기고 목록(피드)에서만 거리를 다룰지 — 두 화면의 역할 분리 원칙을 어떻게 가져갈지.
4. 계측 방식(D-10, 자체 테이블 vs 외부 SaaS)이 결정돼야 §6의 항목들을 실제로 어디에 쌓을지 설계 가능 — 이 문서는 "무엇을 찍을지"까지만 제안하고 "어떻게"는 열어둔다.
5. "최근 본 매물" 기능 자체를 만들지 여부 — 계측 데이터 없이도 업계 관행상 타당해 보이지만, 이 서비스 사용자가 실제로 재방문해 이전 매물을 다시 찾는지는 미검증(§4의 "정직한 한계" 참조).

## 9. 미검증 영역

- **`backend/app/modules/ads/application.py`의 광고 가중치 알고리즘 전체** — `/market/ads` 엔드포인트 존재만 확인, 내부 로직(tier/fee 가중 방식)은 미독. 리스트 구성 제안이 "6개마다 1개, 서버 순서 유지"만 지키면 충돌 없다고 판단했으나, 알고리즘 세부를 모르는 상태의 판단이다.
- **`/market/keyword-alerts` 신규 페이지 실체** — `MarketMain.tsx`가 이 경로로 `navigate`하도록 바뀌었으나(§2), `git status`로 확인한 결과 `frontend/src/pages/market/MarketKeywordAlerts.tsx`(+`.module.css`)가 **미커밋 신규 파일**로 존재한다(신규 파일이라 `git diff`엔 안 잡히고 `git status`에만 보임). 내용은 이번 세션에서 읽지 않았다 — 라우트 배선만 확인.
- **실사용자 행동** — 이 보고서 전체의 핵심 전제(계측 부재)이자 한계. 정적 코드 분석만으로는 "사용자가 정렬을 얼마나 바꾸는지", "카테고리 칩을 쓰는지" 등 실제 조회패턴을 알 수 없다.
- **외부 레퍼런스의 카드 스펙·콜드스타트 로직** — 당근·FB Marketplace·Chợ Tốt 모두 1차 기술 문서를 찾지 못해 "미확인"으로 남긴 항목이 많다(§4). Mercari/Carousell은 이번 세션에서 아예 검색하지 않았다.
- **매물 213건/188건 단일계정 비율의 최신성** — 감사 티켓이 제공한 수치를 그대로 인용했을 뿐, 이번 세션에서 DB를 직접 조회해 재검증하지 않았다.
