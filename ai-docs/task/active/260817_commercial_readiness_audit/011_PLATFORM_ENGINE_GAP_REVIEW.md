## §0. 한 장 요약

**대표 지적에 대한 판정: 절반 인용, 절반 기각.**

- **기각 부분**: "조회 이력 기반 ML 추천·개인화 랭킹을 지금 만들어야 한다"는 방향이라면 기각한다. 010 §4의 판단(매물 213건·188건 단일 계정·실거래 스냅샷 1건 → 학습할 데이터가 원리적으로 없음)은 **사실이고 옳다**. 업계 실무 문헌도 동일하다: 초기 단계에서는 큐레이션·휴리스틱으로 시작하고, 클릭스트림 데이터를 모은 뒤 단순 협업 필터링으로, 그다음에 복잡도를 얹는 진화형 설계가 정석이며, 콜드스타트는 즉시 풀 ML 문제가 아니라 **데이터 수집을 설계하는 제품 문제**다. 지금 ML 추천을 만들면 188건짜리 시연 계정 매물을 학습한 엔진이 나온다.

- **인용 부분**: 그러나 010은 **"지금 안 한다"와 "설계조차 안 한다"를 구분하지 못했다.** 이것이 010의 진짜 결함이며 대표 직감이 정확히 짚은 지점이다. 구체적으로 4건:
  1. **[P0] #5 이벤트 스키마가 퍼널 카운터로 설계됨** — 미래 랭킹·추천·개인화의 유일한 원료가 될 상호작용 로그를, "8종 단계 카운트"로 좁게 정의했다. 지금 스키마를 넓게 잡으면 추가 공수 거의 0, 안 잡으면 6개월 뒤 전면 재작업 + 그동안의 데이터 전량 유실.
  2. **[P0] 검색이 문서 전체에서 부재** — 010은 4관점 어디에도 검색을 다루지 않았다. 베트남어 무성조 입력("xe may" → "xe máy") 정규화는 데이터 볼륨과 무관한 **언어적 필수 기능**이며, 안 되면 매물 20건짜리 파일럿에서도 검색 0건 결과가 나온다.
  3. **[P1] 수요측 유동성 도구(키워드 알림) 부재** — 010 §7-1은 "공급 0은 코드로 못 푼다"고 했다. 절반만 맞다. 코드는 공급을 만들지 못하지만 **희소한 공급을 수요와 매칭하는 효율은 코드가 결정한다**. 공급이 적을수록 키워드 알림의 가치는 커진다.
  4. **[P1] 랭킹이 "최신순 고정"에서 멈춤** — ML 없이도 규칙 기반 스코어(신선도 감쇠 + 품질 신호)는 가능하며, 010 §3-1 L2의 "노출 저하"가 성립하려면 어차피 **감점을 적용할 랭킹 함수가 먼저 존재해야 한다**. L2는 랭킹 v1 없이는 실행 불가능한 설계다 — 010 내부 정합성 결함.

**보강 리스트: 6건 신설**(§4, #16~#21) + **미결 결정 2건 추가**(D-23·D-24). 010 §5의 15건과 착수 순서는 유지하되, #16(스키마 확장)은 D-18 결정에 병합해야 하므로 **D-18 확정 전에 이 문서가 먼저 검토돼야 한다.**

## §2. 010의 결손 — 냉정한 판정 5건

### 2-1. [P0] 이벤트 스키마의 근시안 — "퍼널 카운터"는 미래를 버리는 설계

**사실**: 010 §5 #5는 "핵심 이벤트 8종(가입·매물조회·등록·문의·가격제안·약속·완료·후기)이 이벤트 테이블에 쌓이고, 어드민에서 일별 단계 수를 조회"로 완료 조건을 정의했다. D-18 권고는 (a) 자체 이벤트 테이블.

**판단**: 자체 테이블 채택(D-18 a)은 옳다(PDPL 국외 이전 리스크 회피 — 010 §4 판단 유지). 문제는 **스키마의 폭**이다. "일별 단계 수"만 목적이면 카운터성 스키마로 충분하지만, 그렇게 만든 테이블은:

- 랭킹 v1(#19)의 입력(매물별 조회·문의 수)을 못 준다
- 최근 본 매물(#20)·카테고리 친화(#20)의 원료(user×item 상호작용 이력)를 못 준다
- L2 오탐률 실측(010 §3-1)에 필요한 "플래그된 매물의 실제 전환" 추적을 못 준다
- 향후 추천 모델의 학습 데이터가 못 된다 → **파일럿 4~8주치 데이터가 통째로 재사용 불가**

**보강안(공수 델타 최소)**: 이벤트 테이블을 처음부터 **상호작용 로그**로 잡는다.

```sql
CREATE TABLE app_events (
  event_id      BIGSERIAL PRIMARY KEY,
  event_type    VARCHAR(40) NOT NULL,   -- 백엔드 Enum 검증 (D-19 방식 승계)
  user_id       BIGINT,                 -- 비로그인 NULL 허용
  anon_id       UUID,                   -- 비로그인 열람 퍼널용 (010 §1-1 구매자 문턱이 "비로그인 열람"부터 시작함)
  subject_type  VARCHAR(20),            -- 'listing' | 'ad' | 'biz' | 'user' | NULL
  subject_id    BIGINT,
  surface       VARCHAR(30),            -- D-19 카탈로그 재사용
  session_id    UUID,
  props         JSONB DEFAULT '{}',     -- dwell_ms, position, query 등 — 컬럼 증설 없이 확장
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_events_subject ON app_events (subject_type, subject_id, created_at);
CREATE INDEX idx_events_user    ON app_events (user_id, created_at);
```

퍼널 8종은 이 스키마의 `event_type` 부분집합일 뿐이다. 일별 롤업 잡(010 #5의 완료 조건)은 그대로 성립한다. **추가되는 것은 컬럼 몇 개와 인덱스 2개** — L급 항목의 규모는 변하지 않는다. 대신 `listing_view` 이벤트에 `subject_id`가 실리는 순간, #19·#20과 L2 실측의 원료가 자동으로 쌓이기 시작한다.

**결정 연계**: 이 확장은 **D-18 확정 내용에 병합**돼야 한다(별도 항목 아님). D-18을 "퍼널 계측 방식"이 아니라 **"플랫폼 이벤트 파이프라인 방식"** 으로 격상해 1회에 결정할 것. → §5 D-23.

### 2-2. [P0] 검색 부재 — 베트남어 정규화는 볼륨 문제가 아니다

**사실**: 010은 §1~§8 전체에서 검색(search)을 한 번도 다루지 않았다. 002 팩트시트 인용에도 검색 관련 항목이 없다 — 현재 검색이 어떤 방식인지(ILIKE 추정) 자체가 "확인 필요"다.

**판단**: 이것은 010 최대의 맹점이다. 근거:

1. **베트남어 입력 현실**: 베트남 사용자는 모바일에서 성조·다이어크리틱 없이 입력하는 경우가 매우 흔하다("xe máy"를 "xe may"로, "Hà Nội"를 "Ha Noi"로). PostgreSQL `unaccent` 확장이 표준 해법이나, **기본 unaccent.rules는 베트남어 전체 문자(ơ, ư, đ, 성조 조합 등)를 완전히 커버하지 못해 베트남 개발 커뮤니티에서는 rules 파일 보강 또는 전용 변환 함수(`vn_unaccent`) 추가가 통용되는 관행**이다. đ→d 매핑은 특히 기본 규칙에서 빠지기 쉬운 항목이다.
2. **볼륨 무관성**: 매물이 20건이어도 "xe may" 검색이 "xe máy" 매물을 0건 반환하면 사용자에겐 죽은 앱이다. 계측·공급과 달리 **파일럿 데이터를 기다릴 이유가 전혀 없다.**
3. **양방향 정규화 필요**: 질의뿐 아니라 저장 텍스트도 정규화해야 한다(판매자도 무성조로 등록할 수 있다). 정규화 컬럼(`title_norm`) + 트리거 + GIN(pg_trgm) 인덱스가 현 규모의 정답이다.

**명시적 비범위(과설계 방지 — 010 정신 승계)**: Meilisearch/Typesense/OpenSearch 등 외부 검색엔진은 **[P2]로 명시 보류**. 매물 수천 건 + 다중 필터 + 오타 교정 수요가 실증되기 전까지 신규 컨테이너 금지 원칙(010 §4) 적용. Postgres `unaccent`(+베트남어 rules 보강) + `pg_trgm` 이면 파일럿~전면 구간을 커버한다. 형태소 분석(vi tokenizer)도 [P2].

### 2-3. [P1] 키워드 알림 부재 — 공급 희소 국면의 최고 효율 매칭 도구

**사실**: 010 §7-1 "공급 0(213건 중 188건 단일 계정)은 어떤 코드로도 못 푼다." 010 §4는 이메일/SMS 인프라 비범위, 인앱+FCM은 완성(002_trust B-7 인용).

**판단**: "공급은 코드로 못 만든다"는 맞지만 결론이 하나 빠졌다 — **공급이 희소할수록, 나타난 공급 1건을 원하는 수요자에게 즉시 꽂는 매칭의 한계가치가 극대화된다.** 이것이 당근마켓의 키워드 알림이며, <cite index="19-1">사용자가 키워드를 등록해두면 동네에서 해당 키워드 관련 매물이 올라올 때 알림을 받는</cite> 구조다. Daangn 은 이를 초기부터 핵심 리텐션·유동성 장치로 운영했고, <cite index="20-1">찜한 매물의 가격 인하 알림</cite>도 같은 계열이다.

파일럿 시나리오로 검증: 1개 구에 활성 매물이 주 10건 올라온다고 하자. 열람 시점에 우연히 노출될 확률은 낮지만, "Honda Cub" 키워드를 등록한 수요자 5명에게 등록 즉시 FCM이 가면 **매물 1건당 문의 발생 확률이 구조적으로 상승**한다. 이는 010 §1-1 파일럿의 목적("이 동네에서 거래가 실제로 일어나는가를 측정")의 **분모를 키우는 코드**다.

**구현 스케치(전부 기존 선례 위)**: `saved_keyword(user_id, keyword_norm, created_at)` 테이블 1개 + 매물 등록 트랜잭션 후 아웃박스(D-5 선례) 경유 매칭 잡(정규화 §2-2 재사용, `title_norm LIKE`) + 기존 FCM 발송. 규모 M. 신규 인프라 0.

### 2-4. [P1] 랭킹 부재 — 010 §3-1 L2는 랭킹 없이는 실행 불가

**사실**: 010 §2-4에 어드민 큐 정렬은 설계됐으나, **사용자 대면 피드의 정렬은 언급이 없다**(최신순 고정 추정 — "확인 필요"). §4는 "인기 정렬 실구현(D-14 b)" 유보. 한편 §3-1 L2는 "위험 매물 노출 저하(검색 랭킹 감점)"을 파일럿 4~8주 후 단계로 확정했다.

**판단 — 내부 정합성 결함**: **감점(penalty)은 점수(score)가 있어야 성립한다.** 현재가 순수 최신순이면 L2 시점에 "감점"을 붙일 대상 함수가 없어 그때 랭킹을 급조하게 된다. 랭킹 v1은 ML이 아니라 규칙식이며, 데이터가 필요 없다:

```
score = freshness_decay(created_at, 반감기 72h)
      × quality(사진수 정규화, 설명 길이, phone_verified 가산)
      × trust_penalty(L2 플래그 시 감산 — 파일럿 후 활성화, 초기 계수 1.0)
```

파일럿 중에는 `trust_penalty=1.0`(무효과)으로 배포해 **최신순과 거의 동일하게 동작**시키고, L2 진입 시 계수만 조정한다. 이러면 L2가 "새 시스템 구축"이 아니라 "상수 변경"이 된다. 끌올(refresh) 기능과의 상호작용은 `refreshed_at`을 감쇠 기준으로 쓰면 해소. 규모 M, 계측(#5 확장 스키마)과 무관하게 착수 가능하나 조회수 가중은 #16 데이터 축적 후.

### 2-5. [P2] 조회 이력 기반 표출 — 대표 요청의 정확한 착지점

**사실**: 010 §4는 최근 본 매물(D-17)·카드 조회수(D-15)를 "계측·공급 후 재판단"으로 유보.

**판단**: 대표가 요청한 "조회 이력에 맞는 선별 리스트 재구성"의 실현 가능 형태를 데이터 요구량 순으로 배열하면:

| 단계 | 기능 | 필요 데이터 | 판정 |
|---|---|---|---|
| a | 최근 본 매물 (수평 스크롤 1행) | 본인 조회 이력만 (#16이 자동 축적) | **[P1]로 승격 권고** — per-user 데이터라 전체 볼륨 무관, 유보 근거가 약하다. 규모 S(이벤트 테이블 SELECT + 프론트 1행). 단 #16 선행 |
| b | 카테고리 친화 부스트 (최근 N회 조회 카테고리 매물에 랭킹 가산) | 본인 조회 이력 2주+ | [P2] — 랭킹 v1(#19)에 항 하나 추가하는 구조로 예약 |
| c | 함께 본 매물 (item-item 공출현) | 전체 사용자 조회 이력, 매물 수백+ | [P2] — 전면 후 |
| d | ML 추천 (협업 필터링 이상) | 수천 상호작용 | [P2 후반] — 010 기각 유지 |

a·b가 대표 요청의 "당연한 플랫폼 기능"에 해당하며, **둘 다 #16 스키마가 전제**다. 여기서도 결론은 같다 — 지금의 병목은 추천 알고리즘이 아니라 **원료 파이프라인의 설계 폭**이다.

## §4. 보강 구현 리스트 — 010 §5 에 추가 (#16~#21)

규모·표기 규약은 010 §5 승계. 010의 착수 순서(∥A → D-18·D-19 → #5·#6 → ∥B → #10)는 **변경하지 않는다.** 추가 항목의 삽입 위치만 명시한다.

| # | 항목 | 관점 | 규모 | 단계 | 선행 의존 | 완료 검증 조건 |
|---|---|---|---|---|---|---|
| 16 | **이벤트 스키마 확장** — #5를 상호작용 로그(subject/surface/session/anon_id/props)로 설계 | 전체 | (#5에 병합, 델타 S) | 파일럿 | **D-23 확정**(D-18에 병합 결정) | `listing_view` 이벤트에 `subject_id`·`surface`·`session_id`가 실려 적재되고, 동일 테이블에서 010 #5의 일별 퍼널 집계와 매물별 조회 수 집계가 **둘 다** 쿼리 1개로 산출된다 |
| 17 | **베트남어 검색 정규화** — `unaccent` + 베트남어 rules 보강(đ 포함), `title_norm` 컬럼+트리거, pg_trgm GIN 인덱스, 질의측 동일 정규화 | 사용자·판매자 | M | **파일럿** | 없음(∥A와 병렬 가능) | "xe may" 질의가 "Xe Máy Honda" 매물을 반환하고, 역방향("xe máy" 질의 → 무성조 등록 매물)도 반환한다(테스트 고정). EXPLAIN 상 인덱스 사용 확인 |
| 18 | **키워드 알림(저장 검색)** — `saved_keyword` 테이블 + 등록 후 아웃박스 매칭 + FCM. 사용자당 키워드 상한(예: 5)·일 발송 상한 상수 | 사용자·판매자 | M | **파일럿 권고** (최소 전면) | #17(정규화 재사용) | 키워드 "cub" 등록 사용자에게, 타 계정이 "Honda Cub 82" 등록 시 60초 내 FCM+인앱 알림 1건 도달. 본인 매물은 제외. 상한 초과 시 미발송(테스트 고정) |
| 19 | **규칙 기반 피드 랭킹 v1** — freshness decay × quality, `trust_penalty` 항 예약(초기 1.0) | 사용자·운영자 | M | 전면 | #16(조회 가중 시), 단 기본식은 즉시 가능 | 정렬 옵션 "추천순"이 존재하고, 사진 0장·미인증 매물이 동조건 매물보다 하위 정렬. `trust_penalty` 계수 변경만으로 L2 노출 저하가 발동(테스트 고정) |
| 20 | **최근 본 매물 행** — #16 이벤트 SELECT + 홈/마켓 상단 1행 | 사용자 | S | 전면 (010 D-17 유보를 승격) | #16 데이터 2주+ | 본인이 조회한 매물이 최신순으로 홈에 노출되고, 타인 이력은 절대 섞이지 않는다 |
| 21 | **검색 로그 계측** — 검색어·결과 수·클릭 여부를 #16 파이프라인에 적재 (`event_type='search'`, props.query) | 운영자 | S | 파일럿 (#16과 동시) | #16 | 어드민에서 "결과 0건 검색어 상위 N"을 조회할 수 있다 — **수요는 있는데 공급이 없는 품목의 직접 관측** = §7-1 공급 영업의 타깃 리스트가 된다 |

**착수 순서 갱신안**: ∥A(010 #1·2·3·4·9) **+ #17**(결정 불요·의존 없음 — ∥A에 편입) → **D-23**(D-18 병합)·D-19 확정 → #5(+#16)·#6·#21 → ∥B(#7·8) → #18 → #10 → 파일럿 개시 → 전면(010 #11~15 + #19·#20).

**판단 — #18을 파일럿에 넣는 이유**: 010 §6-1의 우선순위 논리("광고 가치는 트래픽에서, 트래픽은 신뢰에서")에 한 단계를 추가한다 — **트래픽은 신뢰에서, 그리고 매칭 효율에서 나온다.** 파일럿의 측정 대상인 "거래 발생"의 분모(문의 수)를 코드로 키울 수 있는 유일한 항목이 #18이다. 다만 파일럿 일정이 빡빡하면 전면으로 미루는 것은 수용 가능(§6 트레이드오프 참조).

대표 요청 취지가 "다 만들자"로 오독되지 않도록, 이 문서가 **명시적으로 자르는 것**:

| 항목 | 이유 |
|---|---|
| ML 추천·협업 필터링·임베딩 검색 | 010 기각 유지. #16 데이터 수천 상호작용 축적 후 [P2 후반] 재상정 |
| 외부 검색엔진(Meilisearch 등) 컨테이너 | Postgres unaccent+trgm으로 파일럿~전면 커버. 신규 컨테이너 금지 원칙 유지 |
| 외부 계측 SaaS | 010 §4 유지 (PDPL) |
| 실시간 개인화 피드(세션 기반 재정렬) | 요청 안 된 유연성. #19+#20 조합이 현 단계 상한 |
| 광고 타겟팅 엔진·파트너 개방 API | [P2]. 파일럿은 1개 구·광고주 소수 — 010 §3-3 비범위 판단 유지 |

| 알림 오케스트레이션 계층(채널 라우팅·빈도 관리 엔진) | #18의 상수 상한으로 충분. 알림 유형이 5종을 넘는 시점의 과제 |

## §7. 코드로 해결할 수 없는 것 — 추가 1건

010 §7에 추가: **#21(0건 검색어 로그)은 §7-1 공급 영업의 조준경이다.** "무엇을 공급해야 하는가"를 감이 아니라 수요 로그로 판단할 수 있게 된다 — 필드 에이전트 재가동 시 타깃 품목 리스트의 데이터 소스로 지정할 것.

## §8. 결론 — 대표 보고용 3문장

1. 010의 절제(ML 기각·계측 우선·자동차단 금지)는 옳으며 유지한다 — 지금 추천엔진을 만들면 시연 계정 188건을 학습한 엔진이 나온다.
2. 그러나 010은 이벤트 스키마를 좁게 잡아 **미래 엔진의 원료 파이프라인을 끊었고**, 검색(베트남어 무성조)·키워드 알림·랭킹 v1 이라는 **데이터 불요 엔진 3종을 누락**했다 — 이것이 "플랫폼이라면 당연한 기능"의 정확한 결손 목록이다.
3. 필요한 대표 결정은 **D-23 한 건**(이벤트 파이프라인을 상호작용 로그로 — D-18에 병합, 공수 델타 S)이며, #17(검색 정규화)은 결정 없이 ∥A와 함께 즉시 착수 가능하다.
